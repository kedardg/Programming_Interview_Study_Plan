System Design for Interviews

1. The 4-step framework (and the clock)

A system design interview is 45 minutes of structured collaboration, not a monologue. The framework from the plan, with a realistic clock:

StepTimeWhat you doWhat they score
1. Understand & scope5–10 minAsk about users, scale (DAU, QPS), features in vs out, read/write mix, latency and consistency needs. Write the agreed requirements down.Do you design for the actual problem or a memorized one?
2. High-level design10–15 minDraw the end-to-end box diagram: clients → LB → services → cache → storage → async pipelines. Get buy-in before going deep.Can you decompose a system and defend each box?
3. Deep dive10–15 minThe interviewer (or you) picks 1–2 components: data model, sharding, the hot path, a failure mode. This is where seniority shows.Depth, tradeoff fluency, bottleneck instinct.
4. Wrap-up~5 minBottlenecks, failure handling, monitoring, what you'd do with more time. Never say "it's done."Operational maturity.

Two habits separate strong candidates: they quantify before designing (step 2 of the book is back-of-the-envelope for a reason — a 3K-QPS system and a 300K-QPS system are different designs), and they volunteer tradeoffs ("fanout-on-write gives cheap reads but celebrities break it, so for them I'd…") instead of waiting to be cross-examined.

2. Back-of-the-envelope estimation

The point is not precision — it's catching order-of-magnitude design errors in 90 seconds. Memorize three anchors: 1 day ≈ 86,400 s (round to 100K for mental math), 1M requests/day ≈ 12 QPS, and the latency ladder below. Then every estimate is multiplication.

3. The building blocks

Load balancers. The front door. L4 balances on IP/port (fast, blind to content); L7 reads the request (can route by path, cookie, or model name — an LLM gateway is an L7 balancer). Health checks plus a second LB in standby remove the single point of failure. Behind the LB, keep web tier stateless — session state goes to a shared store — so any server can serve any request and autoscaling is just adding boxes.

Caching. The 80/20 rule: a cache sized for 20% of daily objects serves ~80% of reads. Cache-aside (app reads cache, misses to DB, fills cache) is the default; write-through keeps cache and DB in sync at write cost. Set TTLs, pick an eviction policy (LRU almost always), and defend against the thundering herd — one hot key expiring and 10K requests stampeding the DB — with request coalescing or staggered TTLs. CDNs are the same idea pushed to the network edge for static (and increasingly dynamic) content.

Sharding. When one database can't hold the data or the write load, split rows across shards by key. Hash sharding spreads load evenly but kills range queries; range sharding keeps scans cheap but invites hotspots. Two interview-famous pains: resharding (adding a shard under naive hash % N moves nearly every key — consistent hashing below is the fix) and the celebrity problem (Bieber's row melts its shard; fix with dedicated shards or app-level splitting).

Replication. Leader takes writes, followers serve reads and take over on failure. Async replication is fast but can lose the last writes in a failover; sync is safe but slow across regions. Mention replication lag whenever you put a read replica in a design — "read your own writes" breaks the moment a user's read hits a stale follower.

Animation: consistent hashing — why keys barely move

Keys and nodes hash onto the same circle; each key belongs to the first node clockwise. Add or remove a node and watch: only the keys in the affected arc change owner (flashing), everything else stays put — versus hash % N, where changing N remaps almost every key. Real systems give each physical node many virtual nodes to even out the arcs; this demo uses 3 per node.

Message queues. A buffer between producers and consumers: the web tier acknowledges fast, workers process at their own pace, and traffic spikes become queue depth instead of dropped requests (backpressure made visible). They decouple failure domains — a dead thumbnail worker doesn't take down uploads. Kafka is a replayable, ordered log for streams and fan-out at scale; RabbitMQ is a classic broker for task queues. In an interview, a queue is the answer whenever work can be async: notifications, feed fanout, video transcoding, analytics.

Animation: rate limiting with a token bucket

The bucket holds up to 10 tokens and refills at a steady rate; each request spends one. A burst drains saved-up tokens (allowed!), then further requests bounce with 429 until refill catches up. That's the token bucket's signature: it permits short bursts while enforcing a long-run average — which is why it guards most public APIs. Alternatives trade differently: leaky bucket smooths to a constant outflow; fixed windows are simple but allow 2× bursts at window edges; sliding window fixes that for more memory.

Animation: Snowflake IDs — time-ordered, no coordination

64 bits: 1 sign + 41 timestamp (ms) + 5 datacenter + 5 machine + 12 sequence. Each machine mints up to 4096 IDs per millisecond with zero coordination, and IDs sort by creation time — which a UUID can't do and an auto-increment column can't do across shards. Generate a few in a row: the timestamp field ticks, the sequence counts within a millisecond.

4. Storage engines and distributed KV stores

SQL vs NoSQL, honestly. Start with a relational database: transactions, joins, secondary indexes, and 50 years of tooling are features you give up, not defaults you escape. Reach for NoSQL when you have a concrete reason — write volume beyond what sharded SQL handles gracefully, genuinely schema-less data, or access patterns that are pure key-value at massive scale. "NoSQL because scale" without a QPS number is an interview red flag; "DynamoDB because our access pattern is get/put by user_id at 500K QPS" is the sentence they want.

Inside a Dynamo-style KV store (book Ch. 6 — the deepest chapter and a favorite deep-dive):

  • Quorum N/W/R — each key lives on N replicas; a write succeeds after W acks, a read queries R. If W + R > N, read and write sets overlap, so a read sees at least one up-to-date copy. Tune it: W=1 fast writes, R=1 fast reads, W=R=⌈(N+1)/2⌉ balanced.
  • Vector clocks — version counters per replica that detect concurrent writes (neither happened-before the other). The store keeps both siblings and the client reconciles — or you accept last-write-wins and quietly drop data (what many real systems choose).
  • Merkle trees — hash trees over key ranges; two replicas compare roots and descend only into differing subtrees, syncing gigabytes of divergence by exchanging kilobytes of hashes (anti-entropy).
  • Hinted handoff — if a replica is briefly down, another node accepts its writes with a "hint" and replays them when it returns: availability through temporary stand-ins, repaired by Merkle sync if the outage was long.

Animation: LSM tree — how write-optimized storage works

Writes go to an in-memory memtable (sorted, fast). When it fills, it's flushed as an immutable sorted file (SSTable) — sequential I/O, the thing disks love. Reads check memtable, then SSTables newest-first (Bloom filters skip files that can't contain the key). Compaction merges SSTables, dropping overwritten and deleted versions. B-trees (Postgres, MySQL) instead update pages in place: faster point reads, slower random writes. LSM = Cassandra, RocksDB, LevelDB — the write-heavy half of every "design a chat system / metrics store" answer.

5. CAP, consistency, and exactly-once

CAP in one breath: when a network partition happens (and it will), you choose — refuse requests to stay consistent (CP) or answer with possibly-stale data to stay available (AP). No partition, no tradeoff; "CA" is a fiction in distributed systems. Banks pick CP for balances; social feeds pick AP and converge later (eventual consistency). The useful interview move is picking per-feature: the payment ledger is CP, the like counter is AP, and you say so.

Idempotency is how retries become safe: give every mutating request a client-generated key, dedupe server-side, and a retried payment charges once. This is also the honest story behind "exactly-once delivery": messaging systems give you at-least-once, and exactly-once processing is at-least-once delivery plus idempotent consumers. Say that sentence in an interview and watch the interviewer relax.

7. LLM-flavored system design

Increasingly the deep-dive is "design an LLM serving system" — and this repo has a whole chapter of the internals. The sketch interviewers expect:

client → API gateway (auth, token-bucket rate limit, usage metering) → router: prefix-aware + load-aware (send same-session traffic where its KV cache lives) → prefill pool (compute-bound; chunked prefill; TP across GPUs for big models) → KV transfer (NIXL/RDMA) → decode pool (bandwidth-bound; continuous batching; speculative decoding) → token stream back via SSE/WebSocket

Then hit the systems notes: SLOs are TTFT and TPOT, not just availability; autoscale on goodput (SLO-passing requests), scaling prefill and decode pools independently (that's the point of disaggregation); KV cache is the scarce resource, so admission control and preemption replace naive queueing; multi-tenancy needs fair scheduling in tokens, not requests. A "design a RAG pipeline / AI assistant" question is the Agents chapter drawn as boxes: ingestion DAG (chunk → embed → index) as the write path, retrieve → rerank → generate as the read path, with evals and feedback loops as the ops story.
