There is a skill that separates engineers who have shipped these systems from engineers who have only read about them, and it is not knowing more flags. It is the habit of reading an issue tracker before adopting a framework, and reading it again the moment something breaks. This chapter is a tour of what the trackers and forums actually say about the frameworks in this notebook, gathered in early November twenty twenty six, and more importantly it is a method for reading them yourself, because every number here will be stale within months.

Start with the method. An issue tracker carries four signals that matter. Reactions tell you how many people hit a problem. Comment counts tell you how long it stayed unresolved, or how many workarounds were traded in the thread. Maintainer labels and linked pull requests tell you whether a fix exists and in which release. And the version in the original report tells you whether the issue even applies to you, because an out of memory report from version zero point seven says nothing about version zero point eleven. The most reacted threads on almost every tracker are roadmaps and day zero support trackers for new models, and those are planning inputs in their own right: they tell you what the maintainers are prioritizing this quarter.

The working habit is simple. Before you adopt a framework for an engagement, read its ten most reacted open issues and its troubleshooting page. Pin every version in the stack, not just the framework but CUDA, PyTorch, flash attention, nickel, and the container tag. When you hit a bug, reduce it to a minimal reproduction with exact versions and shapes before deciding whether to work around it with a pin, a flag, or a local patch, or to wait because a linked pull request already exists. Filing that reproduction is also how you get capability gaps closed, which is the same discipline the hardware chapter describes for working with the Neuron team.

Now the frameworks, three problem classes each, and what each class teaches about the system underneath.

V L L M first. The dominant class is memory, and nearly every thread is the same arithmetic. The error that says the model's maximum sequence length is larger than what the K V cache can store means that after weights and activations, the pool reserved by the G P U memory utilization flag cannot hold one full length sequence, and the fix is to lower the maximum model length, raise utilization, quantize, or add tensor parallelism. The error about no available memory for cache blocks, or an out of memory during sampler warmup, means something outside the pool took the memory, often CUDA graph capture, and the answers are a lower maximum number of sequences, eager mode, or freeing the G P U. The K V cache calculator in the inference chapter predicts these errors before you see them. The second class is format plumbing: the chat template, the reasoning parser, and the tool call parser are three separate contracts that must agree with how the model was trained, and the long threads about G P T O S S producing seven output messages instead of two, or Qwen three thinking that cannot be disabled, are all that contract breaking. The third class is hardware generations: consumer Blackwell cards like the R T X fifty eighty need the newer CUDA wheels and some attention backends lag, and the community setup thread for those cards has well over a hundred comments.

S G lang's troubleshooting page is unusually good and maps symptom to flag directly. Out of memory during prefill means lower the chunked prefill size. Out of memory during decode means lower the maximum running requests, or lower the static memory fraction to zero point eight or zero point seven at the cost of concurrency. And an illegal memory access error is often just out of memory wearing a disguise, so check the available memory line at startup first. One caution: several third party pages invent flags that do not exist; the radix cache is on by default and there is a flag to disable it, so verify every flag against the help output. The five hundred comment thread on running DeepSeek with large scale prefill decode disaggregation and expert parallelism is the best public record of what that architecture costs in practice.

Verl's failures are the trainer rollout machine made concrete. In colocated mode the trainer, the reference model, and the inference engine share the same G P Us, so rollout out of memory is a budget problem solved by lowering the engine's utilization fraction, offloading optimizer state, or moving to F S D P two for leaner resharding. Verl also patches V L L M internals, so each V L L M release can break the patch, and the release notes pin a version range for a reason. The repository moved to the verl project organization, and its most reacted threads are roadmaps and an agent abstraction proposal, which is where multi turn reinforcement learning is heading.

Miles and slime teach the fragility of the weight sync path in a disaggregated system. A run that hangs on the actor's update weights call looks like training simply stopped, with no error, and one open issue describes a failed engine apply being silently swallowed so the sender believes it is ahead of the receiver. Make weight sync observable by logging the version applied on the engine side before you scale out. Host memory also matters here, with a reported C P U RAM leak over long runs and Ray going out of memory on checkpoint save.

F S D P two's errors are the sharding layout leaking through. The message about mixed tensors and D tensors means something was not wrapped or the optimizer was created before sharding. The metadata mismatch during activation checkpoint recompute happens because autocast is lost during recomputation, so use the mixed precision policy instead. Saving sharded state with plain torch save is a trap; use distributed checkpointing, which also reshards on load. Each of these is a reminder that a D tensor is a tensor with a placement, and every A P I that touches state has to know it.

Megatron is a parallelism compiler with a strict environment contract. The attribute error saying transformer engine has no attribute pytorch is an A B I mismatch between transformer engine and PyTorch, solved by the matching container. The attention mask being ignored with packed sequences teaches that packing needs cumulative sequence lengths, not a mask. And there is an open issue about silent numerical correctness bugs when composing parallelisms, which is why you run a parity test whenever you change the parallel layout.

NeMo R L and NeMo Gym show what happens when environments and rewards become services: a rollout that dies mid episode was a host out of memory from too many prompts times generations per step, and long sequences need the asynchronous generation timeout raised. The G P U is no longer the only resource that runs out. OpenEnv's tracker was not searchable when this was written, so treat it as a service integration: health check the environment server, time out steps, and version the environment image with the run.

The Neuron S D K threads are lessons in the compiled graph model. An operator that is not implemented silently runs on the C P U, and there is an environment variable that makes execution errors surface instead. Compilation failures carry N C C codes and depend on shapes and layer counts. The compiled artifact cache is part of your deployment, because without a remote cache every pod recompiles. And numerical differences from the G P U baseline are sometimes benign accumulation order and sometimes a genuine miscompile, which is exactly what the parity harness in the hardware chapter is for.

Axolotl's recurring problem is packing. Sample packing changes the attention contract to cumulative sequence lengths, so any model whose attention path does not honor it trains on cross contaminated sequences and shows it as unreasonably high loss or NaNs. Always compare one packed step against one unpacked step when you adopt a new model family. T R L's simplest G R P O trainer still contains the whole trainer rollout problem: the server and the trainer must sit on different devices, the utilization default is too high alongside a trainer, and a loss that starts at zero is expected on policy, because the clipped objective has zero gradient when the ratio is one; watch reward and K L instead.

The quantization tooling teaches that a quantized checkpoint is a three way contract between the compressor, the serving engine, and transformers. Scale and zero point dtype changes that the released V L L M could not load, dependency mismatches, and schemes that are slower than F P sixteen on a given G P U all fail as accuracy or speed, not as exceptions, which is why the deployment chapter gates on evaluation after quantization. Locust and gen A I perf teach that time to first token and time per output token are only comparable when token and arrival mean the same thing: count tokens with the model's tokenizer, never S S E chunks, and use open loop arrivals for rate sweeps. Glyner's threads are about data format, the token limit that chunking solves, and threshold tuning. LeRobot's are about dataset format versions, video codecs, and timestamp drift, because robot learning fails at the data layer more than the model layer.

Across all of them the cross cutting gotchas repeat: the CUDA, driver, PyTorch, flash attention version matrix; pip resolver conflicts between frameworks that pin overlapping ranges; chat template and tokenizer mismatches between training and serving, which are silent; F P sixteen overflow where B F sixteen would have been fine; nickel hangs caused by the wrong network interface or one rank off doing evaluation while the others wait in a collective; checkpoint format conversions; and compile caches. The debugging order that finds most bugs fastest is this: pin versions and reproduce on one G P U in eager mode; compute the memory budget before touching flags; check numerics, where a NaN on step one is a dtype or mask problem and a NaN later is learning rate or data; turn on nickel debug and find the rank missing from the collective; round trip the tokenizer, template, and parser on eight prompts; and only then touch performance flags, graphs, speculation, and packing.

What to do next. Open the triage board on the chapter page, filter by the framework you are about to use, and read its three most reacted threads. Drill the Framework Gotchas deck. Then create a pinned versions file for your stack and keep it next to the run config, because the next person to debug the system will be you in three months.
