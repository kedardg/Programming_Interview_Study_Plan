A fine-tuned model that answers a prompt in a notebook is not deployed. It is deployed when a fleet of replicas serves the real request mix inside agreed latency bounds, at a cost the business accepts, and keeps doing that when a node dies. This chapter is the last mile of a customization engagement, worked on Qwen three, with V L L M as the engine, Locust and GenAI Perf as the load generators, and E C S or E K S as the platform.

Start with the loop, because every optimization is one iteration of it. You take the supervised fine-tuned checkpoint, evaluate it against the quality bar from the customization chapter, quantize it, serve it with V L L M, load test it against your service level objectives, size the fleet from the capacity number that test produces, ship, observe, and repeat. The phrase improve deployment has to become five numbers before anyone touches a flag. Time to first token at the ninety fifth percentile, which is queue wait plus prefill, typically under half a second to a second. Time per output token at the ninety fifth percentile, one decode step, typically under thirty to fifty milliseconds because reading speed is about twenty milliseconds per token. Goodput, the requests per second that met both targets, which is the number you plan capacity around. Dollars per million tokens, from G P U hours times price divided by tokens served. And cost per request, which includes thinking tokens the user never reads. Two things people forget: the quality bar must be rechecked after every quantization or numerics change, and the request mix, prompt lengths, output lengths, and how many requests share a system prompt, determines latency more than the model does. Measure it from production logs first.

Now the recipe on Qwen three. Qwen three eight B is a dense model that fits one mid range G P U and is the natural fine-tuning target for a single domain assistant. Qwen three thirty B A three B is a mixture of experts model with about three billion active parameters per token, so it decodes at roughly the cost of an eight B model while carrying far more knowledge, the throughput choice when memory allows. Qwen three also has a hybrid thinking mode: the same weights can emit a thinking block before the answer, toggled per request, and a thinking response can be five to twenty times longer than the visible answer. Decide the thinking policy before you load test, because it changes the output length distribution you are testing.

Step one is supervised fine-tuning with Axolotl: a config naming the base model and the Qwen three chat template, your conversation data, sample packing on, a LoRA adapter of rank thirty two in B F sixteen. Then merge the adapter into the base weights, because a merged checkpoint quantizes cleanly and removes a per request lookup from the hot path. Run the task suite on the merged checkpoint; that number is the reference everything later is compared against.

Step two is quantization, the biggest deployment lever, because decode is bandwidth bound: fewer weight bytes per step means lower time per output token at small batch and more K V cache headroom at large batch. A W Q with four bit weights makes the weights about four times smaller and speeds decode two to three times at low batch with negligible loss when calibrated on in domain data; it is the default for twenty four gigabyte G P Us and the sixteen gigabyte R T X fifty eighty. F P eight halves the weight bytes and runs the matrix multiplies in F P eight tensor cores, so prefill speeds up too; that is the throughput choice on H one hundred or L forty S. You produce either with llm compressor in a few lines. Then verify three things every time: perplexity on held out domain text, the task suite within its confidence interval of the reference, and a side by side read of fifty responses for format regressions that perplexity never catches.

Step three is serving with V L L M, where a handful of flags decide latency and capacity. Max model length caps the context, and setting it to the real maximum rather than the model's maximum is often the difference between zero preemptions and constant ones, because the K V budget is sequences times length. Max num seqs is the throughput versus per token latency dial. Prefix caching is free performance whenever requests share a system prompt or history. Chunked prefill bounds the stall a long prompt causes for everyone else. The reasoning parser splits Qwen three's thinking into its own field, and a chat template argument turns thinking off on latency critical paths. The server speaks the OpenAI compatible A P I, so clients, load testers, and gateways work unchanged.

The first interactive is the quantization, batch, and S L O explorer. Pick a model, precision, G P U, tensor parallel degree, context, prompt length, and batch, and it computes weight memory per G P U, K V headroom, the maximum concurrent sequences, time to first token for the prompt, and time per output token versus batch against your target. Try Qwen three eight B in B F sixteen on the fifty eighty and watch it not fit, switch to four bit and watch it fit with room for dozens of sequences, then push the batch until per token latency crosses the target. It is a first order model within about one and a half times of real servers. Use it to pick candidates, then load test.

Load testing is the centerpiece, because a single request latency number is meaningless for a service. Latency depends on how many other requests are in flight, so the only honest measurement is a sweep over offered load with the production request mix, reporting percentiles. Open loop load sends requests as a Poisson process at a chosen rate whether or not earlier ones finished, which is how users behave; it exposes queueing, and once the arrival rate exceeds what the server drains, time to first token explodes. That is the test that finds the knee. Closed loop load keeps a fixed number of virtual users who wait for each response, so latency self regulates; it measures throughput at a concurrency level but overstates capacity. Record per request the first streamed token time, the gaps between tokens, end to end latency, and output tokens; per run, throughput, goodput, and the error rate; and report high percentiles, never means, because L L M latencies are long tailed. Sample lengths from production traces, discard the warmup, and hold each rate for minutes.

The tools: V L L M's own bench serve command sweeps rates against any endpoint and prints percentiles and goodput for your thresholds. GenAI Perf adds synthetic length distributions and streaming measurement in one command. Locust is for tests that must look like your product, with custom authentication, multi turn sessions, and a web interface; streaming time to first token is not built in, so the chapter gives a complete Locust file that times the first server sent event chunk and reports token gaps as custom metrics. k six and L L M Perf round out the options. Whichever tool, the output is one chart: time to first token and goodput versus offered rate, with the knee marked.

The second interactive simulates sixty seconds of Poisson traffic through a continuous batching server whose per step cost comes from the explorer. Set the rate, the lengths, and the maximum batch, and watch the queue form; on the right it sweeps the rate and marks the knee where goodput stops tracking offered load. Push past it and the queue grows without bound, which users experience as the service hanging. Tick closed loop and the same server shows bounded latency everywhere, which is exactly why closed loop tests mislead. The third interactive draws a latency distribution; drag the tail heavier and watch the mean barely move while the ninety ninth percentile runs away. That is why an S L O lives at a high percentile.

When a target fails, the fix depends on which one. High time to first token with fine per token latency means queueing at admission or long prefills stalling the batch: turn on prefix caching, tune the chunked prefill size, add replicas, or route long prompts to their own pool. High time per output token means the batch is too large for the bandwidth or the weights are too big: cap max num seqs, quantize, use tensor parallelism across a few G P Us, or add speculative decoding. Both rising with a climbing preemption counter means the K V cache is exhausted: lower max model length, use an F P eight cache, or run fewer sequences.

Now the platform. E C S and E K S both run containers, and the choice is how much of Kubernetes you want. Common to both: the model server is the V L L M container image, the host driver must match the C U D A version the image was built against, which is the number one it worked locally failure, and weights are best staged on S three and copied to local disk at startup. In E C S, a cluster groups capacity, capacity providers choose Fargate, which has no G P Us, or E C two G P U instances, a task definition is the pod equivalent with a one G P U requirement and a health check, and a service keeps tasks running behind a load balancer with rolling deployments and metric based scaling. Choose it when the team is small and nobody wants to operate Kubernetes. In E K S, A W S runs the control plane and you own the nodes, either managed node groups or Karpenter, which provisions right sized G P U nodes on demand. The NVIDIA device plugin lets pods request a G P U; a deployment keeps replicas and rolls updates, a service gives them one address, an ingress exposes it, and keda scales replicas on V L L M's waiting request gauge. Readiness probes gate traffic, which matters because a model server takes minutes to load. The chapter gives a complete manifest with an init container syncing weights from S three, shared memory for tensor parallelism, and a rolling strategy that never drops below the desired count. The rule: replicas raise goodput linearly and are what autoscaling adds; tensor parallelism lowers per token latency and must stay inside one node.

The fourth interactive animates the topology. Requests enter through the load balancer, the service spreads them across ready pods, and each pod batches them. Fail a pod and its readiness goes red, the service stops routing to it, and the deployment replaces it while survivors absorb the load. Scale out and keda raises the replica count, the pending pod waits for Karpenter to provision a node, and traffic rebalances once readiness passes. Autoscaling handles slow tides, not spikes, so keep warm headroom for the spike your traces show. Alternatives: SageMaker endpoints for the least operational burden, Bedrock custom model import for bursty low volume traffic billed per use, llm d or Ray Serve on E K S for prefix aware routing and disaggregated serving, and Trainium nodes through the Neuron plugin with the parity gates from the hardware chapter.

Observability closes the loop. V L L M exposes Prometheus metrics: histograms for time to first token, time per output token, and end to end latency, gauges for running and waiting requests and K V cache usage, a preemption counter, and token totals. A dashboard with those rows per model, tracing from the gateway into the replica, and a canary that compares a new checkpoint against the baseline on an hour of real traffic before rolling forward is enough to run on. Attribute G P U hours to tokens so dollars per million tokens is a live number, because that is what tells you whether the next optimization is worth doing.

Open the load test simulator, set that server, and push the rate until you find the knee, then tick closed loop and see why that test would have fooled you. Drill the Deployment deck. Then run the one week plan on your fifty eighty: serve the four bit model on day one, write the Locust file against your own prompts on day two, sweep the rate and write down the knee on day three, change one flag at a time on day four, compare F P eight and four bit on day five, containerize on day six, and write the runbook on day seven. After that, E C S or E K S is the same thing, many times, behind a load balancer.
