Every GPU kernel you will ever write answers one question: given my thread's coordinates, which piece of the data is mine? This chapter is the replacement notebook for the kernel exercises in the study plan, steps nine, eleven, and eighteen. We will build vector add, reduction, transpose, online softmax, and then climb the full matmul optimization ladder, from one percent of the vendor library to ninety four percent. Make sure the GPU chapter is fresh, because warps, coalescing, shared memory, and the roofline are assumed here.

Start with vector add, the hello world from GPU MODE lecture three. In cooda, each thread computes its global index as block index times block dimension plus thread index. That expression is the cooda idiom: block coordinate times block size plus position within the block. Memorize it. Then a guard, if i is less than n, because grids launch in whole blocks and the last block overhangs the array. Then out of i equals x of i plus y of i. Adjacent threads touch adjacent floats, so the access is perfectly coalesced. You launch one thread per element with two hundred fifty six threads per block, and the number of blocks is the ceiling of n over two hundred fifty six.

The same kernel in Triton swaps the per-thread view for a per-tile view. One program owns a block of one thousand twenty four elements and operates on whole vectors. The program id corresponds to the block index. Program id times block plus an arange corresponds to the global index, vectorized. A mask of offsets less than n corresponds to the bounds guard. Then one masked load per input and one masked store. The compiler decides how the tile maps onto threads, registers, and shared memory. Learn both: cooda to understand what the machine does, Triton to ship fused kernels fast.

Reduction is the first kernel where threads cooperate, and it is the pattern behind softmax, norms, and attention. Three generations. The naive version has every thread do an atomic add into one memory location, which serializes everything on one counter. The tree reduction stages a block's slice into shared memory, then halves the active threads each step: two hundred fifty six, one hundred twenty eight, sixty four, down to one partial sum per block, in log two of n steps, then one atomic per block. That is the classic NVIDIA reduction deck. The modern version does the tree down to one warp and then uses warp shuffles, where shuffle down sync moves values between lanes' registers directly without shared memory. The classic bug is barrier placement: sync threads must be reached by all threads of the block, so it lives outside the if. Run Compute Sanitizer's race check before trusting your version.

Transpose does zero math, which is exactly why it teaches coalescing. The naive kernel reads rows and writes columns: the read is coalesced, but adjacent threads write with a stride of N, up to thirty two transactions per warp store. The fix: stage a thirty two by thirty two tile in shared memory, transpose inside the tile where random access is cheap, and write out rows again. Declare the tile as thirty two by thirty three, the extra column of padding, so that column reads land in different banks and avoid bank conflicts. Both global memory touches are now coalesced; the bad access pattern happens only where it is free. A good transpose reaches eighty to ninety percent of pure copy bandwidth, about zero point nine six terabytes per second on your fifty eighty. That is week four of the schedule.

Online softmax is the trick that enables FlashAttention. Softmax must be computed stably: exponentiate x minus the row max, then divide by the sum, otherwise e to the x overflows F P sixteen at x around eleven. The textbook version makes three passes over the row: max, then sum, then normalize. Three trips through memory for a bandwidth bound operation. The online formulation, from Milakov and Gimelshein in 2018, fuses the first two passes by keeping a running max m and a running denominator d. For each element, compute the new max. Then rescale the old denominator by e to the old max minus the new max, and add e to the element minus the new max. That correction factor is the whole idea: every term already in d was computed against the old max, so when the max rises, multiply d once to re-reference it. The same algebra lets FlashAttention process keys and values in tiles and merge per-tile statistics without ever materializing the full attention matrix.

The fused Triton softmax, in the style of GPU MODE lecture fourteen and the Liger kernel notebooks, does the whole row in registers: one load, subtract the max, exponentiate, divide by the sum, one store. Why it beats eager PyTorch: unfused softmax is about four kernel launches and about eight N bytes of traffic; the fused kernel is one launch and about two N bytes, read once and write once. Softmax is bandwidth bound, so bytes are time. Check it against torch softmax with all close, then benchmark gigabytes per second against row length.

Now the centerpiece, the matmul ladder, following Simon Boehm's cooda matmul worklog. The core quantity is data reuse. C equals A times B does two N cubed flops on three N squared values, so each value can in principle be used N times, but only if you orchestrate the reuse. The naive kernel reuses nothing: each thread computes one element of C and streams two N values from H B M, so arithmetic intensity is about one, the far left of the roofline. Every rung of the ladder is a reuse mechanism.

Here are Boehm's numbers for F P thirty two at four thousand ninety six squared on an A six thousand. Rung one, naive: three hundred nine gigaflops per second, one point three percent of cuBLAS. Rung two, coalesced loads, swapping the thread x and y indexing so warps read rows contiguously: one thousand nine hundred eighty seven gigaflops, eight and a half percent. A six point four times speedup from an index swap. Rung three, shared memory tiling, where a thread block stages a tile of A and a tile of B into shared memory and marches across K, so H B M traffic drops by the tile size: two thousand nine hundred eighty gigaflops, twelve point eight percent. Rung four, one-dimensional register blocking, where each thread computes eight elements of C and reuses A values from registers: eight thousand four hundred seventy five gigaflops, thirty six and a half percent. Rung five, two-dimensional register blocking, each thread owning an eight by eight micro-tile of C, sixty four fused multiply adds per sixteen loads, the inner loop becoming outer products: fifteen thousand nine hundred seventy two gigaflops, sixty eight point seven percent. Rung six, vectorized float four loads: eighteen thousand two hundred thirty seven, seventy eight percent. Rung seven, autotuned tile shapes, which is what Triton's autotuner automates: nineteen thousand seven hundred twenty one, eighty five percent. Rung eight, warp tiling, an explicit warp-level tile between block and thread tiles: twenty one thousand seven hundred seventy nine gigaflops, ninety three point seven percent. cuBLAS itself: twenty three thousand two hundred fifty, with double buffering, prefetching tile k plus one while computing tile k.

Read the ladder as a hierarchy of reuse. H B M to shared memory at rung three. Shared memory to registers at rungs four and five. Better instructions at six through eight. The same decomposition, block tile, warp tile, thread tile, marching over K, is exactly what CUTLASS formalizes and what you will meet again as the Neuron kernel interface's tile model in the hardware chapter. Replicating these rungs on your fifty eighty and recording your own numbers is the step eighteen deliverable.

Past rung eight, scalar fused multiply adds run out and F P sixteen matmuls move to tensor cores. One M M A sync instruction, m sixteen n eight k sixteen, makes a whole warp cooperatively compute a sixteen by eight output tile with inputs scattered across the thirty two lanes' registers in a fixed fragment layout. You no longer address thread three's element; you lay data out so the hardware's expected fragment pattern is satisfied, usually with the load matrix instruction from shared memory. That layout bookkeeping is why CUTLASS exists, and why its core, CuTe, reduces everything to one algebraic object, the layout, a function from logical coordinates to memory offsets built from shape and stride pairs. Tiling, swizzling, and partitioning become layout algebra checked at compile time. Your hardware note: the R T X fifty eighty is consumer Blackwell, S M one twenty. Its tensor cores run warp-level M M A sync, including F P eight and F P four, but Hopper's warpgroup M M A and datacenter Blackwell's tensor memory instructions do not exist on it. Read that material as theory; CUTLASS example seventy nine targets your chip.

Triton in depth. A kernel is a grid of programs, each computing on power-of-two tiles with whole-tile loads, stores, and math. The compiler assigns tiles to warps, inserts shared memory staging and tensor core instructions, and handles coalescing and double buffering. You keep tile sizes, the grid, masking, and the algorithm. You give up warp-level tricks and fine control of shared memory. Triton wins for fused elementwise and reduction kernels and for custom attention variants; cooda wins when you need the last fifteen percent or exotic instructions.

Misconceptions and interview questions. Fusion is not about saving flops; it is about saving bytes, because most of these kernels are bandwidth bound. Shared memory tiling alone does not get you near peak; register blocking is where the big jump happens, from thirteen to sixty nine percent. And a question to be ready for: explain why the online softmax correction factor is exact, and how FlashAttention uses it across tiles.
