A chatbot maps one prompt to one response. An agent is a language model running in a loop with access to tools, and that one change turns a text completion endpoint into something that can read your files, run your code, and act in the world. This chapter is about what actually changes when a model starts acting.

Begin with the loop itself, because everything else follows from it. The agent reads a goal. It decides whether it needs information or an action from outside. Instead of answering, it emits a structured tool call. The surrounding harness parses that call, runs the real function, and appends the result to the conversation as a new observation. Then the model runs again over the whole accumulated transcript and repeats until it judges the task done. The model never executes anything itself. And everything it knows about the task lives in that growing conversation. The context window is the agent's working memory.

That framing explains the two defining constraints of agent engineering. First, each loop iteration is just another inference over the whole accumulated context, so a thirty step task pays for the transcript thirty times. Second, the context is finite. Long running agents have to manage memory by summarizing old turns, compacting tool outputs, or writing important facts to external storage and retrieving them later, or the oldest and often most load bearing instructions fall out of the window.

The animation on the page walks one real trace. The question is, what is fifteen percent of our twenty twenty three revenue in the sales file. The model cannot read files and cannot do reliable arithmetic, so it emits a read file call, receives the contents, emits a Python calculation, receives the number, and only then answers. Watch the transcript panel: every step appends, the second model call sees the first tool result, and the final answer sees everything. That transcript is the only state the agent has.

Now the mechanics of tool use. A tool is advertised to the model as a schema: a name, a natural language description, and a J S O N schema for its parameters. The description is prompt engineering. It is the only thing telling the model when this tool applies, and bad descriptions are the most common reason tools get ignored or misused. Models do this reliably for two reasons. They are fine tuned for function calling, trained on millions of request, call, result, and response traces, so emitting a call is a learned behavior. And serving engines back the format with constrained decoding: a grammar compiled from the schema masks invalid tokens at every step, so malformed output is literally impossible to sample. The inference chapter explains how that works without distorting the model's distribution.

Two practical mechanics matter. Parallel tool calls: when actions are independent, like reading three files or hitting two A P I's, a model that emits them in one turn cuts loop iterations and wall clock time, and a model that serializes needlessly is wasting the most expensive resource in the system. And errors are observations, not exceptions. A failed call, a missing file, a timeout, a stack trace, is appended to the context like any other result, and a competent agent reads it and adapts, retrying with a fix, trying another path, or reporting the blocker. Agents that recover from their own failed calls are what separate demos from products.

The Model Context Protocol, M C P, standardizes the supply side of all this. Instead of every application hand wiring its own tool definitions, an M C P server exposes tools, resources such as files or database schemas, and prompt templates over a standard protocol, and any capable client, a chat app, an I D E, an agent harness, can connect and see those tools alongside its built in ones. The flip side of standardized tools is a standardized attack surface. Anything a tool returns, a web page, a file, a database row, is untrusted text injected into the model's context, and prompt injection is exactly a tool result that tries to be read as instructions. Serious harnesses mark tool output as data, restrict which tools may run without human approval, and sandbox execution.

Retrieval augmented generation, rag, attacks a different limitation. The model's knowledge is frozen at training time, and its context is too small to hold your corpus. The idea goes back to the rag paper by Lewis and colleagues in twenty twenty. The pipeline has an offline half and an online half. Offline, you split documents into chunks, embed each chunk into a vector, and store the vectors in an index built for approximate nearest neighbor search, such as H N S W. Online, you embed the user's query with the same model, retrieve the top k nearest chunks, optionally rerank them with a cross encoder that reads query and chunk together and scores relevance far better than vector distance but is too slow to run over the whole corpus, so you retrieve a hundred and rerank down to five, and then generate with the chunks pasted into the prompt and an instruction to cite them. The rag animation on the page shows the whole thing: a document split into overlapping chunks, chunks becoming points in embedding space, the query landing as a star, the nearest chunks lighting up, the reranker reordering them, and the generator answering with citations.

Chunking is a real tradeoff, not a preprocessing detail. Small chunks of a few sentences embed precisely but strip away the context the generator needs. Large chunks of a page carry context but blur the embedding and waste prompt tokens. Pure vector search also misses exact identifiers, error codes, part numbers, and names that keyword search catches trivially, so production systems run hybrid retrieval, B M twenty five and dense search in parallel, fused with reciprocal rank fusion, then reranked. And know when not to use rag at all. If the corpus fits in the window and all of it matters, long context with prefix caching is simpler. If you are teaching behavior, format, or style rather than facts, fine tuning is the right tool, and rag is the wrong one for anything that must be cited or updated.

Planning patterns come next, and the honest version is that each one has a failure mode. ReAct, from Yao and colleagues in twenty twenty two, interleaves explicit reasoning with actions: a thought, a tool call, an observation, another thought. Its value is that the reasoning trace conditions better action choices and leaves an auditable trail; its weakness is myopia, because each step is chosen greedily and the agent can wander. Reflection or self critique adds a verification pass, and it reliably buys quality on checkable tasks like code that must compile or math with a verifier, and reliably wastes tokens on uncheckable ones, where the critic hallucinates approval. Self critique works in proportion to how much of the checking is done by something other than the model. Multi agent orchestration has an orchestrator decompose the task and dispatch worker agents, each with its own context and tools. The real win is context isolation, because workers burn tokens on exploration without polluting the orchestrator's window, and independent subtasks run in parallel. The real cost is the handoffs: every brief and every report is lossy, workers return wrong findings in the same confident voice as right ones, and an orchestrator that spawns workers it did not need pays twice.

Here is the arithmetic that explains most of agent engineering. If every step succeeds independently with probability p, a task needing n sequential steps succeeds with probability p to the n. At ninety five percent per step, a twenty step task succeeds zero point nine five to the twentieth power, which is about thirty six percent of the time. At ninety nine percent per step it is about eighty two percent. Drag the slider on the page and watch the curve collapse. There are only three responses: shorten the chain with better tools and parallel calls, raise the per step reliability with verification and constrained outputs, or add recovery so that one failure does not kill the run.

From the serving system's point of view, agent traffic is strange in three profitable ways. It is prefix heavy, because every loop iteration resends the same system prompt, tool schemas, and transcript plus a small suffix, so engines with prefix caching, SGLang's radix attention or vLLM's automatic prefix caching, recompute only the new suffix and turn what looks like quadratic cost into near linear. That is the single biggest serving win for agents. Sessions are long lived with idle gaps while the agent waits on a tool, so engines offload the session's K V cache to C P U memory or a distributed store between turns instead of holding H B M hostage. And the token economics invert: an agent task's cost is dominated by re-read input tokens, not generated ones, which is why providers price cached input tokens roughly ten times cheaper and why the size of your transcript is a cost engineering question.

Evaluation needs two levels. Task success, did the pull request merge, did the answer match ground truth, is what users care about, but it is a sparse end of episode signal that says nothing about where a thirty step run went wrong. Per step evaluations, did it pick the right tool, were the arguments valid, did it recover from an injected error, localize failures and regression test individual behaviors. Safety is mostly containment: sandboxes with no ambient credentials, human approval for irreversible actions, tool output treated as untrusted, and caps on iterations and spend. An agent is exactly as dangerous as the blast radius of its tools.

One misconception to retire: that more autonomy is better. Anthropic's Building Effective Agents makes the opposite argument, and it is right: use the simplest pattern that works, and most things people call agents should be workflows with a fixed sequence of model calls.
