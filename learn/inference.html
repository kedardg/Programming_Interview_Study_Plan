LLM Inference Systems

How a trained transformer actually serves requests: prefill and decode, the KV cache, continuous batching, PagedAttention, scheduling, and speculative decoding. This chapter is the systems counterpart of Steps 14–15 in the study plan.

1. One request, two very different phases

When a request arrives at an inference engine, the model processes it in two phases that stress the hardware in opposite ways.

Prefill runs the whole prompt through the model at once. Every layer sees all prompt tokens together, so the matrix multiplies are large and the GPU's tensor cores stay busy: prefill is compute-bound. Its cost grows roughly linearly with prompt length (quadratically in the attention term), and it produces one thing the rest of the request depends on: the first output token, plus the keys and values of every prompt token, saved for later.

Decode then generates the response one token at a time. Each step feeds only the single newest token through the model, but attention still has to look at every previous key and value. The matrices are skinny (batch × 1 token), so the GPU spends almost all its time streaming weights and cached KV from HBM rather than multiplying: decode is memory-bandwidth-bound. This asymmetry drives nearly every design decision in this chapter.

Animation: prefill vs decode

Prefill (blue) processes all prompt tokens in parallel in one pass and fills the KV cache. Decode (green) emits one token per step; each step reads the entire KV cache (highlighted) to attend over the past. Watch the cache column grow by exactly one entry per decode step — that growth is the memory cost of generation.

The two phases also map onto the two latency metrics every serving benchmark reports:

  • TTFT (time to first token) — dominated by prefill; what makes a chat feel responsive.
  • TPOT (time per output token, also called ITL, inter-token latency) — dominated by decode; what makes streaming feel fast. total latency ≈ TTFT + TPOT × output tokens.

Because decode is bandwidth-bound, a useful mental model for its floor is: one decode step cannot be faster than the time it takes to read every active byte (weights + KV cache) from HBM once. A 70B model in FP16 is ~140 GB of weights; on a GPU with 3.35 TB/s of bandwidth (H100 SXM), the floor is ~42 ms per token at batch 1 without tensor parallelism — which is exactly why batching and parallelism exist.

2. The KV cache

Why cache at all? Attention for the newest token needs softmax(q·Kᵀ)·V over all previous tokens. Without a cache, each decode step would recompute every past token's K and V by re-running the whole prompt — turning an O(n) generation into O(n²) full forward passes. The KV cache trades memory for that recomputation: after a token is processed, its per-layer K and V vectors are stored, and each new step only computes K and V for itself.

The cost of that trade is captured by one formula worth knowing cold (it is the formula behind the melchi.me calculator in Step 14):

KV bytes = 2 (K and V) × layers × KV heads × head_dim × cached tokens × batch × bytes/element

3. Batching: from static to continuous

Batch-1 decode wastes the GPU: reading 140 GB of weights from HBM to produce one token is an arithmetic intensity of well under 1 FLOP/byte against hardware that balances at hundreds. The fix is to serve many sequences at once so that each weight read is amortized across the whole batch — decode throughput rises almost linearly with batch size until the KV cache runs out of memory or the batch becomes compute-bound.

But how you batch matters as much as whether you batch:

  • Static batching groups requests, runs them in lockstep, and returns when the longest one finishes. Short requests sit idle, padded, holding memory, while stragglers finish — utilization collapses when output lengths vary (and they always vary).
  • Continuous batching (Orca's iteration-level scheduling) makes the batch a living thing: after every decode iteration, finished sequences leave and waiting requests join. No padding, no waiting for stragglers. This single idea is the backbone of every modern engine — vLLM, SGLang, TensorRT-LLM.

Animation: static vs continuous batching

Each row is a batch slot; each cell is one decode iteration. Grey = slot idle (wasted). Top: static batching waits for the longest sequence before admitting the next group. Bottom: continuous batching back-fills the moment a sequence finishes. Same requests, same hardware — count the wasted cells.

One subtlety: a newly admitted request still needs its prefill, which is long and compute-bound, and running it stalls every decoding request in the batch for that iteration. Sarathi-Serve's answer is chunked prefill: split the prompt into chunks and co-schedule a chunk alongside the batch's decode steps each iteration, smoothing the stall into a small, bounded overhead. This is why you see "chunked prefill" as a flag in vLLM and friends.

4. PagedAttention: virtual memory for the KV cache

Continuous batching created a memory problem. If each sequence pre-allocates a contiguous KV region sized for its maximum possible length, most of it is never used — the vLLM paper measured only 20–38% of KV memory doing useful work in prior systems, the rest lost to internal fragmentation and reservations. Fewer sequences fit, so the batch shrinks, so throughput falls.

PagedAttention borrows the oldest trick in operating systems: paging. The cache is carved into fixed-size blocks (e.g. 16 tokens each); a per-sequence block table maps logical positions to physical blocks allocated on demand. Waste is bounded to the last partially-filled block per sequence (near-zero fragmentation), and the same physical block can back many sequences — a shared system prompt is stored once and referenced by every request that uses it, with copy-on-write when a sequence diverges.

Animation: paged KV allocation

Left: the physical block pool. Right: three sequences and their block tables. Sequences grow token by token and grab a new block only when the current one fills; the two chat requests share the yellow system-prompt blocks until one of them writes past the shared prefix (copy-on-write, shown with a flash). When a sequence finishes, its private blocks return to the pool instantly.

Prefix sharing generalizes beyond system prompts: SGLang's RadixAttention keeps finished sequences' KV in a radix tree keyed by token prefix, so few-shot prompts, chat histories, and tree-of-thought branches all reuse cached computation automatically. Distributed versions (Mooncake) treat the KV cache as a cluster-wide resource with its own data plane.

5. Scheduling, SLOs, and goodput

Throughput alone is a bad target: a scheduler can always raise tokens/second by batching harder, at the cost of each user's latency. Production systems therefore optimize goodput — requests served within their latency SLOs (a TTFT bound and a TPOT bound) per unit of hardware (Etalon formalizes this). The levers:

  • Admission and preemption — when the cache fills, vLLM preempts whole sequences (recompute or swap their KV later) rather than OOM-ing.
  • Chunked prefill ratio — bigger chunks help TTFT of the new request, hurt TPOT of everyone else.
  • Prefill/decode disaggregation (DistServe, Splitwise, Mooncake, NVIDIA Dynamo) — run prefill and decode on separate GPU pools, each provisioned and parallelized for its own regime, shipping the KV cache between them. This removes phase interference entirely and lets you scale TTFT capacity and TPOT capacity independently; the price is moving KV over the network (NIXL is a transport layer built for exactly this).
  • Fairness — request sizes are unknown in advance; fair schedulers (VTC) account service in tokens, not requests.

6. Speculative decoding

Decode wastes compute: the big model's FLOPs are idle while bandwidth streams weights. Speculative decoding spends that idle compute to cut latency. A cheap draft model proposes k tokens; the target model scores all k in one parallel forward pass (which costs barely more than scoring one token — the pass is bandwidth-bound); accepted tokens are kept, the first rejection is resampled from a corrected distribution. The acceptance rule is constructed so the output distribution is mathematically identical to sampling the target model alone — it is a lossless speedup, typically 2–3× when draft and target agree often.

Animation: draft, verify, accept

Each round: the small model drafts 5 tokens (hollow), the large model verifies them all in one pass, accepts a prefix (green) and corrects the first miss (red→solid). Higher draft quality → longer accepted runs → fewer large-model passes per token. Drag the slider and watch tokens-per-pass change.

Variants move the draft inside the target model: Medusa adds extra prediction heads; EAGLE drafts at the feature level from the target's own hidden states (current best acceptance rates); vLLM ships n-gram, EAGLE, and draft-model speculation behind one flag.

7. Structured and constrained decoding

Serving agents and APIs means guaranteeing output shape (JSON, SQL, tool-call schemas). Constrained decoding masks invalid tokens at each step using a grammar compiled ahead of time — XGrammar precomputes pushdown-automaton masks so the per-token overhead is microseconds. The subtlety ("Guiding LLMs the Right Way"): naive greedy masking can distort the model's intended distribution; correct methods mask without changing relative probabilities of valid continuations.
