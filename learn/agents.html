LLM Agents, Tool Use & RAG

What changes when a language model stops being a text-completion endpoint and starts acting: the agent loop, tool calling, retrieval-augmented generation, planning patterns and their failure modes, and what agents do to the serving systems underneath them.

1. From chatbot to agent: the loop

A chatbot maps one prompt to one response. An agent is a model running in a loop with access to tools: it reads a goal, decides whether it needs information or an action from the outside world, emits a structured tool call instead of (or before) an answer, receives the tool's result as a new observation, and repeats until it judges the task done. The model never executes anything itself — the surrounding harness parses the tool call, runs the real function, and appends the result to the conversation. Everything the agent "knows" about the task lives in that growing conversation: the context window is the agent's working memory.

That framing explains the two defining constraints of agent engineering. First, each loop iteration is just another LLM inference over the whole accumulated context, so a 30-step task pays for the transcript 30 times (mitigated by prefix caching — §5). Second, the context is finite: long-running agents must manage memory — summarize old turns, compact tool outputs, or write important facts to external storage and retrieve them later — or the oldest, often most load-bearing, instructions fall out of the window. Compaction is lossy; every production agent framework (including the one running this very loop pattern at scale) treats "what to keep verbatim vs summarize" as a core design decision.

2. Tool use mechanics

A tool is advertised to the model as a schema: a name, a natural-language description, and a JSON Schema for its parameters. The description is prompt engineering — it is the only thing telling the model when this tool applies — and bad descriptions are the most common cause of tools being ignored or misused. At inference time the schemas are rendered into the system prompt (or a special token region), and the model is expected to emit a call in an exact format:

{"name": "read_file", "description": "Read a local file and return its contents", "input_schema": {"type": "object", "properties": {"path": {"type": "string"}}, "required": ["path"]}} // the model emits: {"tool": "read_file", "input": {"path": "sales.csv"}}

Models produce this format reliably for two reasons. They are fine-tuned for function calling — trained on millions of (request, tool call, result, response) traces so that emitting a call is a learned behavior, not a parlor trick. And serving engines back the format with constrained decoding: a grammar compiled from the JSON Schema masks invalid tokens at every step, making malformed JSON literally impossible to sample (see Inference §7 for how that works without distorting the distribution).

Two mechanics matter in practice. Parallel tool calls: when actions are independent (read three files, hit two APIs), a model that emits them in one turn cuts loop iterations and wall-clock; a model that serializes needlessly is wasting the most expensive resource in the system. Errors are observations, not exceptions: a failed tool call (file not found, timeout, stack trace) is appended to the context like any other result, and a competent agent reads it and adapts — retries with a fix, tries another path, or reports the blocker. Agents that can recover from their own failed calls are what separate demos from products.

MCP (Model Context Protocol) standardizes the supply side of all this. Instead of every application hand-wiring its own tool definitions, an MCP server exposes tools, resources (readable data like files or database schemas), and prompt templates over a standard protocol; any MCP-capable client — a chat app, an IDE, an agent harness — can connect to it and the model sees its tools alongside the built-in ones. It is deliberately boring plumbing, like LSP was for editors: the point is that a Postgres server, a GitHub server, and a browser-control server are written once and work everywhere.

The flip side of standardized tools is a standardized attack surface: anything a tool returns — a web page, a file, a database row — is untrusted text injected into the model's context, and "prompt injection" is exactly a tool result that tries to be read as instructions. Serious harnesses mark tool output as data, restrict which tools an agent may call without human approval, and sandbox execution.

3. Retrieval-augmented generation

RAG attacks a different limitation: the model's knowledge is frozen at training time and its context is too small to hold your corpus. The pipeline has an offline half and an online half:

  • Offline — split documents into chunks, embed each chunk into a vector, store vectors in an index (HNSW or IVF for approximate nearest-neighbor search at scale).
  • Online — embed the user's query with the same model, retrieve the top-k nearest chunks, optionally rerank them with a cross-encoder (which reads query and chunk together and scores relevance far better than vector distance, but is too slow to run on the whole corpus — hence retrieve-100-rerank-to-5), then generate with the chunks pasted into the prompt and instructions to cite them.

Animation: the RAG pipeline

Left: a document is split into overlapping chunks (the overlap keeps a sentence that straddles a boundary intact in at least one chunk). Middle: chunks become points in embedding space — nearby points mean similar meaning. Right: the query (star) lands in that space, the k nearest chunks light up, the reranker reorders them, and the generator answers with citations. Step through and watch which chunks actually reach the prompt.

Chunking is a real tradeoff, not a preprocessing detail. Small chunks (a few sentences) embed precisely but strip away context the generator needs; large chunks (a page) carry context but blur the embedding and waste prompt tokens on irrelevant text. Common practice: 200–800 tokens with 10–20% overlap, split on semantic boundaries (headings, paragraphs) rather than fixed character counts, and store chunk metadata (title, section) to prepend at generation time. Pure vector search also misses exact identifiers — error codes, part numbers, names — that keyword search catches trivially, so production systems run hybrid retrieval: BM25 (lexical) and dense (semantic) in parallel, fused with reciprocal rank fusion, then reranked.

4. Planning patterns — and why long chains fail

ReAct interleaves explicit reasoning with actions: the model writes a thought ("I need the revenue first"), then an action (tool call), then reads the observation, then thinks again. The pattern's value is mostly that the reasoning trace conditions better action choices and leaves an auditable trail; its weakness is myopia — each step is chosen greedily, so the agent can wander.

Plan-then-execute has the model write a full step list up front, then execute steps (often with a cheaper model or stricter loop). It resists wandering and makes progress legible, but plans go stale the moment reality disagrees with step 2 — so practical versions re-plan on failure rather than following the script off a cliff.

Reflection / self-critique adds a verification pass: generate, then critique your own output (or run tests, the best critic of all), then revise. It reliably buys quality on checkable tasks (code that must compile, math with a verifier) and reliably wastes tokens on uncheckable ones, where the critic hallucinates approval. The honest summary: self-critique works in proportion to how much of the checking is done by something other than the model.

Multi-agent orchestration — an orchestrator decomposes the task and dispatches worker agents (researcher, coder, reviewer), each with its own context and tools, then merges results. The real win is not anthropomorphic role-play but context isolation: workers burn tokens on exploration without polluting the orchestrator's window, and independent subtasks run in parallel. The real cost is the handoffs: each brief and each report is lossy, workers confidently return wrong findings in the same voice as right ones, and an orchestrator that spawns workers it didn't need pays twice.

Interactive: why long agent chains fail — compounding error

If every step succeeds independently with probability p, a task needing n sequential steps succeeds with pⁿ. At 95% per step, a 20-step task succeeds 36% of the time; at 99%, it's 82%. This single curve explains most agent engineering: shorten the chain (better tools, parallel calls), raise p (verification, constrained outputs), or add recovery so one failure doesn't kill the run.

5. What agents do to the serving system

From the inference engine's point of view (see the Inference chapter), agent traffic is weird in three profitable ways. First, it is prefix-heavy: every loop iteration resends the same system prompt, tool schemas, and transcript, plus a small suffix. Engines with prefix caching — SGLang's RadixAttention, vLLM's automatic prefix caching — recompute only the new suffix's KV, turning what looks like quadratic token cost into near-linear; this is the single biggest serving win for agents. Second, sessions are long-lived with idle gaps (the agent waits seconds or minutes on a tool), so engines offload the session's KV cache to CPU memory or distributed stores (Mooncake-style) between turns instead of holding HBM hostage. Third, the token economics invert: an agent task's cost is dominated by re-read input tokens, not generated ones, which is why providers price cached input tokens ~10× cheaper and why "how big is your transcript" is a cost-engineering question.

6. Evaluating agents

Two levels, and you need both. Task success (did the PR merge, did the answer match ground truth) is what users care about, but it is a sparse, end-of-episode signal that tells you nothing about where a 30-step run went wrong. Per-step evals — did it pick the right tool, were the arguments valid, did it recover from the injected error — localize failures and regression-test individual behaviors. Benchmarks follow the same split: SWE-bench (resolve real GitHub issues, verified by the repo's own tests) and τ-bench / BFCL-style tool-use suites (schema-correct calls under multi-turn pressure) measure ends and means respectively. Treat all public agent benchmarks with suspicion about contamination and harness effects: the harness often moves scores more than the model.

Safety is mostly containment engineering: run tools in sandboxes with no ambient credentials, require human approval for irreversible actions (payments, deletes, sends), treat all tool output as untrusted input, and cap loop iterations and spend. An agent is exactly as dangerous as the blast radius of its tools.
