Beyond NVIDIA: Trainium/NKI, TPU & the Hardware Landscape

The ideas from the GPU and Kernels chapters — memory hierarchies, tiles, rooflines — reappear on every accelerator, just with different names and different trade-offs. This chapter covers AWS Trainium and the NKI programming model in depth, Google's TPU, AMD, and how to study them without owning the hardware. It is the interactive companion to Step 16 of the plan.

2. Why alternatives exist at all

Three forces, all economic. Cost per token: inference at scale is a utility bill; if an accelerator delivers the same tokens for 30% less, that compounds into millions. Supply: top-end NVIDIA GPUs have been allocation-constrained for years; a second source is risk management. Vertical integration: AWS, Google, and Meta run the same few models at enormous scale, so a chip co-designed with the workload (and billed at cost) beats a general-purpose one at list price. For you, the engineering consequence is portability pressure: the serving stack of the future targets more than one backend, and people who can read an unfamiliar architecture doc and find the roofline quickly are rare.

One honest caveat, straight from Step 16 of the plan: read each architecture with its ISA or tuning guide — vendor peak numbers are not performance measurements. Every claim below about "peak" is a ceiling, not a promise; the Deepgram case study (§4) shows what reaching even part of that ceiling takes.

2. AWS Trainium and the NeuronCore

A Trainium chip contains NeuronCores. Where an NVIDIA SM is a sea of identical warps scheduled onto shared pipelines, a NeuronCore is a small number of heterogeneous engines, each built for one job, connected by explicit on-chip memories:

  • Tensor engine — a 128×128 systolic array for matmuls (the big FLOPs; §5 animates how systolic arrays work).
  • Vector engine — elementwise and reduction math over tiles (softmax pieces, norms, activations).
  • Scalar engine — per-element functions (exp, sqrt) streamed over data.
  • GpSIMD engine — eight general-purpose DSP cores for the odd, control-heavy ops that fit nowhere else (custom top-k, dynamic shapes).

The memory hierarchy is the real mental shift from CUDA. There is no hardware cache doing you favors: HBM (device memory) → SBUF (a 24 MB software-managed staging buffer, organized as 128 partitions) → PSUM (a small accumulator memory the tensor engine writes matmul results into). Your kernel — or the compiler — explicitly DMAs tiles HBM→SBUF, feeds the engines from SBUF, accumulates in PSUM, and copies results back. The CUDA translation table:

SBUF (24 MB, 128 partitions)Shared memory / L1Software-managed via tiles; much larger; partition dim ≤ 128 shapes every kernel
PSUMTensor-core accumulator registers / Blackwell tensor memoryA named, addressable memory you allocate buffers in
Engines (Tensor/Vector/Scalar/GpSIMD)Pipelines inside an SMIndependently programmable; overlap is explicit, not warp-scheduled
DMA queuescp.async / TMAAll data movement is explicit DMA; no load/store through a cache

Animation: a tiled matmul flowing through a NeuronCore

One C-tile of a matmul: A- and B-tiles DMA from HBM into SBUF partitions (step 1–2), the tensor engine streams them through its systolic array and accumulates partial products into PSUM across the K-loop (steps 3–5 — note PSUM fills in place, that's what an accumulator memory is for), the vector/scalar engines apply the epilogue (bias, activation) as the result copies back to SBUF, and a final DMA returns it to HBM. The pipelining insight: while the tensor engine chews tile k, the DMA engines are already fetching tile k+1 — the same double-buffering you built in the Kernels chapter, with different names.

3. The NKI programming model

NKI (Neuron Kernel Interface) is the Triton-analog for this hardware: a Python-embedded tile language. You write functions over tiles — arrays whose first ("partition") dimension is at most 128, matching SBUF's 128 partitions — and the compiler maps tile ops onto engines and schedules the DMAs. A real, annotated kernel:

import neuronxcc.nki as nki import neuronxcc.nki.language as nl @nki.jit def matmul_kernel(A, B): # A:[M,K] B:[K,N] in HBM C = nl.ndarray((A.shape[0], B.shape[1]), dtype=A.dtype, buffer=nl.shared_hbm) TM, TK, TN = 128, 128, 512 # partition dim ≤ 128 (hardware rule) for m in nl.affine_range(A.shape[0] // TM): # affine_range → compiler may for n in nl.affine_range(B.shape[1] // TN): # pipeline iterations acc = nl.zeros((TM, TN), dtype=nl.float32, buffer=nl.psum) # accumulator lives in PSUM for k in nl.affine_range(A.shape[1] // TK): a = nl.load(A[m*TM:(m+1)*TM, k*TK:(k+1)*TK]) # DMA: HBM → SBUF b = nl.load(B[k*TK:(k+1)*TK, n*TN:(n+1)*TN]) # DMA: HBM → SBUF acc += nl.matmul(a, b) # tensor engine → accumulate in PSUM nl.store(C[m*TM:(m+1)*TM, n*TN:(n+1)*TN], acc) # PSUM→SBUF→HBM return C # runs on your laptop CPU — no Trainium required: out = nki.simulate_kernel(matmul_kernel, A_np, B_np)

Compare line-for-line with your Triton matmul from the Kernels chapter: nl.load ↔ tl.load, affine_range ↔ the pid grid, PSUM buffer ↔ the fp32 acc you kept in registers. The concepts transfer; the constraint that changes your tiling is the 128-partition limit and explicitly-sized SBUF/PSUM. nki.simulate_kernel runs kernels on CPU with real numerics — which is why the plan's Step 18 exercise (port your online softmax or RoPE kernel to NKI and compare against the reference) needs no AWS account.

The NKI Library is the production kernel catalog, and its structure repeats the Inference chapter: attention ships as CTE (context encoding = prefill: big parallel matmuls) and TKG (token generation = decode: bandwidth-bound, batch-skinny) variants, because the two phases want different tilings — the same prefill/decode asymmetry, baked into kernel names. Around them: MLP/MoE kernels, QKV and output projections with fused normalization (fusion logic again), RoPE, FP8/MX quantization kernels, and NeuroTile, a tile-iterator library that abstracts the HBM/SBUF/PSUM choreography for kernel authors. LNC sharding (logical NeuronCore) lets one kernel span multiple physical cores — the library marks which kernels support it; think of it as the tile-level analog of tensor parallelism.

4. Case study: Deepgram's port, generalized

Deepgram moved Nova-3 (speech-to-text) batch inference to Trainium2 and reported 11–70% more audio processed per dollar. The engineering decisions are a checklist for porting anything to any accelerator:

  • Static shapes. The encoder and decoder were compiled separately, each for fixed input shapes. Ahead-of-time compilers for systolic hardware want static graphs; dynamic shapes either recompile (slow) or fall back. The prefill/decode split maps naturally onto two compiled artifacts — notice this is the CTE/TKG split again.
  • Zero CPU fallbacks. Any op the compiler can't map runs on the host CPU, and one fallback inside a hot loop can erase the hardware's entire advantage. "No operations fall back" was a milestone, not a given.
  • Replicas before parallelism. Eight model replicas per instance: for a model that fits on one core, data-parallel replicas beat model parallelism — no communication, perfect scaling (the Parallelism chapter's first rule).
  • Custom kernels only where it pays. NKI kernels were written for the few layers called repeatedly that drive end-to-end latency — not for the whole model. Profile first, customize the top of the profile, let the compiler handle the rest.
The accelerator port checklist: 1. Can every op compile? (count fallbacks → fix or re-express them) 2. Can shapes be static? (bucket/pad inputs; split phases into separate graphs) 3. Does the model fit per-core? (replicas > parallelism when it does) 4. What's hot? (profile → hand-write only those kernels in NKI/Pallas/etc.) 5. Measure cost per unit of work vs the GPU baseline — not peak FLOPs.

5. Google TPU: the systolic original

The TPU bet (2015, and unchanged in spirit through v7) is that if matmul is almost all the work, the chip should be mostly one giant matmul unit. The MXU is a systolic array: a grid of multiply-accumulate cells where weights are loaded once and stay put ("weight-stationary"), activations march in from the left one diagonal per clock, and partial sums flow downward, each cell adding its weight×activation as data passes through. No instruction fetch, no register files between ops — data movement is the computation, which is why systolic arrays are so area- and power-efficient for dense matmul (and why Trainium's tensor engine is also one).

Animation: a 4×4 weight-stationary systolic array

Computing y = W·x for four input columns. Weights (grey, one per cell) were pre-loaded and never move. Activations (blue) enter from the left, skewed one clock per row; each cell multiplies the passing activation by its resident weight and adds it to the partial sum (green) flowing down. After the pipeline fills, one complete output column exits the bottom every clock. Count the clocks: for an n×n array the first result takes ~2n cycles (fill), then throughput is n MACs per cell per clock with zero memory traffic inside the array.

Around the MXU: a VPU (vector unit) for everything that isn't matmul, VMEM — a software-managed on-chip buffer that plays exactly SBUF's role (HBM→VMEM→MXU) — and Pallas as the kernel language, sharing its tile-based design with Triton and NKI (the plan links both the Pallas design doc and its TPU hardware model in Step 16). At pod scale, chips connect over ICI links into 2-D/3-D torus topologies; a v4 pod wires 4096 chips, and the torus shape is why TPU collective algorithms and sharding layouts differ from NVLink-tree GPU clusters — the Parallelism chapter's topology-awareness point, at datacenter scale.

6. AMD

CDNA / Instinct MI350: AMD's datacenter line is architecturally the closest thing to NVIDIA here — compute units with matrix cores, LDS where you'd expect shared memory, HBM stacks (MI350: 288 GB, more than any contemporary NVIDIA part — the headline reason it wins deals for serving huge models single-node). The chiplet construction (XCDs on an I/O die) is the main structural difference, and the ISA is public — the plan links the CDNA 4 whitepaper and instruction set directly.

HIP / ROCm: HIP is deliberately CUDA-shaped — hipMalloc, hipLaunchKernel, warps of 64 (wavefronts) instead of 32 — so kernels port with a sed-script's worth of changes and then need re-tuning (different occupancy math, different LDS banking). ROCm is the full stack: compiler, libraries (rocBLAS, MIOpen), profilers.

The kernel libraries: Composable Kernel is AMD's CUTLASS — tiling/layout/operator primitives for building fused GEMM-family kernels; AITER packages ready inference operators (attention, MoE) the way FlashInfer does for NVIDIA; HipKittens ports the ThunderKittens tile-DSL idea to AMD. Triton targets AMD too — often the lowest-effort path to a fast custom kernel there, which is itself a lesson in why tile-level abstractions are winning.

The convergent evolution is the takeaway: every vendor landed on (1) a big matmul engine, (2) a software-managed on-chip tile buffer, (3) a Python tile-DSL to program it, and (4) a proprietary scale-up fabric. Learn the pattern once — tiles in fast memory feeding a matmul unit, overlapped with explicit data movement, measured against a roofline — and each new chip is a vocabulary lesson, not a new field.

8. Studying this without the hardware

  • NKI: pip install the Neuron tools and use nki.simulate_kernel — full kernel development on CPU. Do the Step 18 exercise: port your online-softmax or RoPE kernel, then diff your tiling against the NKI Library reference.
  • Pallas: runs in interpreter mode on CPU and compiles on GPU — you can learn the TPU kernel model on your 5080.
  • Read ISA and tuning guides, not marketing: the plan's Step 16 list (Trainium architecture docs, CDNA 4 ISA, TPU v4 paper, Ironwood docs) is ordered for exactly this.
  • Rent an hour of a trn1/trn2 or TPU VM when a kernel is sim-clean; profile it the way the GPU chapter taught — the tools differ, the method doesn't.

9. The GPU → Trainium migration playbook

Everything above is the hardware. This section is the job: you are the technical lead who has to move a customer's training or inference workload from GPUs onto Trainium, prove it is as accurate and cheaper, and turn that proof into a capacity decision someone will sign. The Deepgram checklist in §4 is the compressed version; here it is unpacked into the workflow, the debugging methodology, the profiling loop, and the evidence format that actually gets a migration approved. It assumes the serving concepts of Chapter 11 and the parallelism vocabulary of Chapter 12.

9.1 The workflow: four phases and two gates

Phase 0 — baseline before you touch anything. A migration without a GPU baseline cannot succeed, because "parity" has no referent. Freeze one evaluation harness (the customer's real evals, not a public benchmark), one benchmark harness (fixed prompt-length distribution, fixed output lengths, fixed concurrency sweep), one checkpoint, one tokenizer. Run both on the GPU fleet and record quality scores, TTFT/TPOT/throughput, and dollars per million tokens at the concurrency the customer actually runs. Every later number is a ratio against this.

Phase 1 — inventory the graph. Ahead-of-time compilers for systolic hardware want static graphs. List every op (custom attention, fused kernels, sampling tricks, LoRA adapters, quantization formats) and every dynamic dimension (sequence length, batch, number of images). Dynamic lengths become buckets: compile for 512/1K/2K/4K/8K and pad to the next bucket; prefill and decode become separate compiled artifacts (the CTE/TKG split of §3). Anything the compiler cannot map will run on the host CPU — one fallback inside the decode loop can erase the entire cost advantage, so fallbacks are counted, not tolerated.

Phase 2 — compile and run. Inference: vLLM on Neuron (the neuron device plugin) or NeuronX Distributed Inference (NxDI) for the model classes they already support; training: NeuronX Distributed (NxD) with its tensor/pipeline/data parallel primitives. Read the compiler report, not just the exit code: it lists unsupported ops, graph partitions, and compile time per bucket.

Phase 3 — the two gates. Accuracy gate: eval scores on Neuron within the run-to-run noise of the GPU baseline (§9.2). Performance gate: cost per unit of work below the GPU baseline at the customer's SLOs (§9.3). Only when both pass do you write the capacity recommendation (§9.4). Teams that skip the accuracy gate ship a cheaper model that is quietly worse; teams that skip the baseline ship a benchmark nobody trusts.

# Phase 1–2, inference path (illustrative flags; check the current Neuron release notes) pip install neuronx-cc torch-neuronx neuronx-distributed-inference vllm-neuron export NEURON_COMPILED_ARTIFACTS=./artifacts # cache compiled buckets export NEURON_CC_FLAGS="--model-type=transformer --enable-saturate-infinity" # compile once per (tp_degree, bucket set); the report lists fallbacks python -m neuronx_distributed_inference.compile \ --model meta-llama/Llama-3.1-70B-Instruct --tp-degree 32 \ --max-context-length 8192 --context-buckets 512,1024,2048,4096,8192 \ --token-gen-buckets 512,1024,2048,4096,8192 --dtype bf16 # serve with continuous batching, same client harness as the GPU baseline vllm serve meta-llama/Llama-3.1-70B-Instruct --device neuron \ --tensor-parallel-size 32 --max-num-seqs 64 --max-model-len 8192 vllm bench serve --model meta-llama/Llama-3.1-70B-Instruct \ --dataset-name sharegpt --num-prompts 2000 --request-rate 8 # identical to GPU run

9.2 Accuracy parity: a methodology, not a vibe

The question is never "are the logits identical" — they will not be, and that is fine. BF16 matmuls accumulate in different orders on a 128×128 systolic array than on tensor cores; fused kernels round at different points; the softmax may be computed with a different max-subtraction scheme. The question is whether the distribution of outputs the customer cares about is unchanged. Three layers of evidence, cheapest first:

  1. Layer-by-layer activation diff on fixed inputs. Run the same prompts through both stacks with hooks that dump every layer's output, then report per-layer max-abs and relative error. Numerics drift grows slowly and smoothly through a healthy stack; a bug shows up as a step change at one layer. Finding the first diverging layer turns a week of guessing into an afternoon.
  2. Token-level agreement under greedy decoding. Fraction of positions where both stacks pick the same argmax, and KL between their next-token distributions. Expect >99% agreement on short outputs for a clean port; long outputs diverge after the first disagreement by construction, so compare per-position distributions, not whole strings.
  3. The real evals, with error bars. Run the customer's eval suite N times on each stack (sampling temperature as in production) and compare means against the run-to-run standard deviation. Parity means "within noise" — if the GPU stack itself varies ±0.4 points between runs, a 0.3-point gap is not a finding.
# parity_harness.py — same prompt, both stacks, first diverging layer import torch, json def capture(model, inputs, tag): acts = {} hooks = [] for i, layer in enumerate(model.model.layers): # HF-style decoder hooks.append(layer.register_forward_hook( lambda m, inp, out, i=i: acts.__setitem__(i, out[0].float().cpu()))) with torch.no_grad(): logits = model(**inputs).logits.float().cpu() for h in hooks: h.remove() torch.save({"acts": acts, "logits": logits}, f"dump_{tag}.pt") def compare(gpu_path, trn_path, tol_rel=2e-2): g, t = torch.load(gpu_path), torch.load(trn_path) rows, first_bad = [], None for i in sorted(g["acts"]): a, b = g["acts"][i], t["acts"][i] max_abs = (a - b).abs().max().item() rel = ((a - b).norm() / a.norm()).item() # relative Frobenius error rows.append((i, max_abs, rel)) if first_bad is None and rel > tol_rel: first_bad = i pg, pt = g["logits"].softmax(-1), t["logits"].softmax(-1) kl = (pg * (pg.clamp_min(1e-9).log() - pt.clamp_min(1e-9).log())).sum(-1).mean().item() agree = (g["logits"].argmax(-1) == t["logits"].argmax(-1)).float().mean().item() print(json.dumps({"first_diverging_layer": first_bad, "argmax_agreement": agree, "mean_kl": kl, "per_layer": rows}, indent=1)) # Healthy port: rel error creeps 1e-3 → 5e-3 across 80 layers, argmax agreement 0.995+. # Bug: rel error 2e-3 at layer 16, 1.8e-1 at layer 17, and everything after is garbage.

A worked example. A 70B port passed the eval gate on short prompts and failed it on 6K-token prompts by three points. The harness showed relative error flat at ~3×10⁻³ through layer 16, then 1.8×10⁻¹ at layer 17's attention output — only for prompts above 4K tokens. Cause: the attention kernel used for the 8K bucket computed softmax with FP16 intermediates for the row max, which saturated for a handful of heads with large logits once positions were far apart (RoPE angles at long range amplify a few dimensions). The fix was to force BF16/FP32 for the softmax statistics in that bucket's kernel — exactly the "exponent beats mantissa" lesson of Chapter 10. Without the per-layer, per-bucket diff, the symptom ("long prompts are a bit worse") would have been blamed on the model.

The usual suspects, in the order you should check them: tokenizer and padding (left vs right padding, BOS handling, chat template) — these are not numerics and account for half of all "parity" bugs; KV-cache dtype (a cache quantized on one stack and not the other); RoPE (theta, scaling method, precision of the rotation); fused-op rounding (RMSNorm epsilon placement, SwiGLU fusion); attention softmax statistics precision; FP8/MX formats (per-tensor vs per-block scales, E4M3 vs E5M2); BF16 accumulation order (benign drift, not a bug — only a problem if someone set an unreasonable bitwise test); sampling (temperature/top-p implementations differ, so compare greedy first).

9.3 Performance parity: profile, then customize only the top of the profile

On a GPU you read Nsight; on Trainium you read the Neuron profiler, and the first thing it tells you is time per engine — how busy the Tensor, Vector, Scalar, and GpSIMD engines are, and how often they wait. The diagnostic patterns are few and recognizable:

  • Tensor engine busy, others idle, high utilization — you are compute-bound on matmuls; this is the good case (prefill, training). Remaining wins: precision (FP8/MX) and tile shapes that fill the 128×128 array.
  • Everyone idle, DMA queues full — HBM-bound, the decode regime. Wins: batch deeper (continuous batching on Neuron behaves like vLLM's), shrink bytes (KV cache dtype, weight quantization), check that buckets aren't padding decode to a far larger length than needed.
  • Vector/Scalar engines dominate — normalization, softmax, activations, RoPE are not overlapped with matmuls. This is where the NKI Library's fused kernels (QKV projection with fused norm, RMSNorm+quantize) earn their keep, and where a hand-written NKI kernel for one hot layer pays.
  • SBUF pressure / spills — tiles too large for the 24 MB staging buffer; the compiler re-fetches from HBM. Fix tile sizes or let LNC sharding split the work across two physical cores presented as one logical core.
  • Host gaps between graphs — CPU fallbacks or bucket switches. Each gap is a fallback to eliminate or a bucket boundary to move.

The decision rule for custom kernels is the Deepgram rule: write NKI only for layers that are called repeatedly and sit at the top of the profile. Every custom kernel is code the customer must maintain across compiler releases, so the bar is "this layer is ≥15% of end-to-end time and the compiler's version is >1.5× off what the NKI Library reference or a hand tiling achieves." Everything else stays on the compiler. The compile-time knobs come first because they are free: tensor-parallel degree (fit the model while keeping per-layer collectives inside the instance's NeuronLink island), LNC sharding (2 cores per logical core on Trn2), bucket sets (fewer buckets = less padding waste vs more compile artifacts), and sequence-length-aware batching.

9.4 From benchmark evidence to a capacity decision

The deliverable that ends a migration is not a slide of speedups; it is a table an infrastructure lead can act on, one row per workload, with the cost basis stated. Rows are workloads because the answer differs by workload: prefill-heavy summarization may migrate first, a latency-critical agent loop may stay on GPUs for a release, and training may move when the next checkpoint is due.

Capacity planning in plain terms. Accelerator capacity is reserved, not summoned: once the table above says "migrate," the next conversation is how many instances, in which region, for how long, and whether capacity blocks or reservations are needed to get them. Your benchmark evidence sets the number — tokens per hour per instance at the SLO, divided into the customer's forecast tokens per hour, plus headroom for peak (×1.5–2 is typical) and for the fact that a migration always uncovers one more bucket. Say the assumptions out loud: the forecast, the SLO, the parallelism degree, and the pricing basis, because the decision will be revisited when any of them changes.

9.5 Working with the Neuron team

You will hit capability gaps: an op without a kernel, a model class without an NxD recipe, a compiler release that regresses a bucket. The difference between a gap that closes in a release cycle and one that lingers is the quality of the report. File it as: minimal reproduction (the smallest graph or model that shows it, not the customer's full stack), exact shapes and dtypes per bucket, compiler and SDK versions (neuronx-cc --version, the pip freeze of the neuron packages), the profile or compiler report that shows the symptom, and the GPU reference number it is being compared against. Read the release notes for every SDK version before upgrading a customer: they list newly supported ops and known regressions, and a bucket that compiled last release may partition differently in the next. Remember the NKI Library's versioning from the study plan — neuronx-cc bundles a validated copy under nkilib, pip install nki-library overrides it with a newer branch, and NKILIB_FORCE_BUNDLED_LIBRARY restores the bundled one; pin which you are using in the customer's environment file, because "it got faster/slower after a pip install" is a real failure mode. Feed field evidence back deliberately: the gaps you document with numbers are what move service roadmaps, and the recipes you write to close them (bucket sets, parity harness, profiling checklist) are the reusable artifacts the next engagement starts from. The cost-model side of these decisions — what a point of quality is worth against a cent per million tokens — is developed in the customization chapter.
