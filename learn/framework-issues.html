Known issues and gotchas: what the issue trackers and forums say

The recurring problems people actually hit with vLLM, SGLang, verl, Miles/slime, FSDP2, Megatron-Core, NeMo RL/Gym, OpenEnv, the Neuron SDK, Axolotl, TRL, llm-compressor, Locust and GenAI-Perf, GLiNER and LeRobot — pulled from their GitHub issue trackers (via the GitHub search API, sorted by 👍 reactions), the projects' own troubleshooting docs, and forums, on 2026-11-04. Every linked issue below was returned by those queries; problem classes without a single canonical thread are marked as such. These stacks move monthly — treat version numbers as snapshots.

1. Reading an issue tracker like a technical lead

An issue tracker is the most honest documentation a framework has. The skill is reading it quickly and deciding what to do. Four signals carry most of the information: reactions (how many people hit it — the lists below are sorted by 👍), comment count (how long it stayed unresolved, or how many workarounds were traded), maintainer labels and linked PRs ("bug" + a merged PR means fixed in the next release; "feature" + no PR means wait or fork), and the version in the report (an OOM report from 0.7 says nothing about 0.11). The highest-reacted threads are often roadmaps and "day-0 support" trackers — those tell you what the maintainers are prioritizing, which is itself a planning input.

The working habit: before adopting a framework for an engagement, read its ten most-reacted open issues and its troubleshooting page; pin every version in the stack (framework, CUDA, PyTorch, flash-attn, NCCL, the container tag); and when you hit a bug, reduce it to a minimal repro with exact versions and shapes before deciding between work around (pin, flag, patch) and wait (a linked PR exists). Filing that repro is also how you get capability gaps closed — the same discipline the hardware chapter describes for the Neuron team.

Triage in 90 seconds: 1. Is it red on main for others? (search error text; sort by reactions) 2. Which version introduced it? (pin one version back = fastest unblock) 3. Is there a linked PR? (merged → upgrade; open → patch locally or wait) 4. Can I reproduce in <50 lines? (if not, it's probably my config) 5. Does the fix change a number I size on? (memory, throughput → re-benchmark)

What this teaches. Nearly every vLLM memory thread is the same arithmetic: weights + activations + KV pool must fit, and the pool is what --gpu-memory-utilization reserves — the calculator in Inference §2 predicts the error before you see it. The second cluster is format plumbing: chat template, reasoning parser and tool parser are three separate contracts that must agree with how the model was trained, which is why the eval harness should include a parse-failure rate. The third is hardware generations: consumer Blackwell and each new model family get a long community thread before the wheels catch up. The most-reacted open issue at the time of writing is a feature request for TurboQuant KV-cache quantization (#38171) — KV memory is still the pressure point.

9. OpenEnv

OpenEnv's tracker was not searchable through the API at the time of writing (the repository name in the ecosystem listings did not resolve), so this section is class-level. The reported pattern class: environments run in Docker containers and are reached over WebSocket with a Gym-style reset()/step()/state() API, so the recurring problems are the ones every containerized env has — image build and startup time on first reset(), sandbox resource limits during step(), lost connections on long steps, and schema drift between the env's action/observation types and the trainer's expectations. (commonly reported; no single canonical thread.) Treat an OpenEnv integration as a service integration: health-check the env server, time out steps, and version the environment image with the training run.

Debugging order that finds most bugs fastest: 1. Pin versions and reproduce on one GPU, one process, eager mode. 2. Memory: compute the budget (weights + KV/activations) before touching flags. 3. Numerics: bf16 everywhere? NaN on step 1 = dtype/mask; NaN later = LR/data. 4. Comms: NCCL_DEBUG=INFO; which rank is missing from the collective? 5. Formats: tokenizer/template/parser round-trip on 8 prompts. 6. Only then: performance flags, graphs, speculation, packing.
