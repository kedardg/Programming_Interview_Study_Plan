The Framework Stack: What Each Tool Is, What It Does, and How You Use It

The training, RL, inference, and accelerator frameworks you actually operate when you customize a model and take it to production: PyTorch FSDP2, Megatron-LM, Axolotl and TRL; verl, Miles, NeMo RL/NeMo Gym and OpenEnv; vLLM, SGLang and TensorRT-LLM; the AWS Neuron SDK; Ray and the checkpoint formats that tie them together; and the managed paths in Amazon Bedrock and SageMaker AI. Every other chapter explains why these systems work; this one explains what each one is, what it does for you, and how you drive it. APIs move fast — the code blocks are representative shapes, labelled illustrative; the abstractions behind them are what to learn.

1. The map: where each framework lives

A model customization program is a pipeline with five stations, and every framework in this chapter lives at exactly one of them (a few straddle two). Hold this picture before the details: data flows into an SFT trainer; the SFT checkpoint flows into an RL trainer, which cannot work alone — it needs rollout engines to generate samples and environments to score them; checkpoints flow through evals that gate releases; the winner flows into serving; and monitoring feeds production traffic back into data. Weights, rollouts, rewards and metrics are the four things that travel along the edges, and the hard engineering problems (resharding weights between trainer and engine, scaling environments, keeping evals honest) are all edge problems, not box problems.

2. Training frameworks

PyTorch FSDP2: shard every parameter, gather on demand

FSDP2 (torch.distributed.fsdp.fully_shard) is PyTorch's native implementation of ZeRO-3-style data parallelism (Chapter 12): every parameter, gradient and optimizer state is sharded across the data-parallel group, and each module's parameters are all-gathered just before its forward or backward, used, then freed. What changed from the original FSDP ("FSDP1") is the representation: FSDP2 shards per parameter as a DTensor (a tensor that carries its own placement over a DeviceMesh) instead of flattening a module's parameters into one buffer. That one change buys composability — the same DTensor machinery implements tensor parallelism, so FSDP2 + TP is a 2-D mesh rather than a special case — plus simpler checkpoints (each parameter is addressable), partial-parameter freezing (LoRA works naturally), and torch.compile compatibility.

The core concepts you configure:

  • Where to apply fully_shard: on each transformer block (so only one block's parameters are materialized at a time) and once on the root module. Granularity is the memory/communication trade: finer sharding = less peak memory, more collectives.
  • Mixed precision policy: MixedPrecisionPolicy(param_dtype=bf16, reduce_dtype=fp32) — compute in BF16, keep sharded master parameters and gradient reductions in FP32 (Chapter 13's mixed-precision recipe, made explicit).
  • reshard_after_forward: free gathered parameters after forward (re-gather in backward) to save memory at the cost of a second all-gather; set false for the last blocks or small models.
  • Activation checkpointing: wrap blocks with checkpoint_wrapper or torch.utils.checkpoint; orthogonal to sharding, composes freely.
  • DeviceMesh: init_device_mesh("cuda", (dp, tp), mesh_dim_names=("dp","tp")); apply TP with parallelize_module (Colwise/Rowwise plans) on the tp dimension, then fully_shard on the dp dimension. HSDP (replicate across nodes, shard within) is a 2-D mesh too.
# Illustrative FSDP2 + TP (PyTorch 2.5+ shapes; check your version's docs) import torch from torch.distributed.device_mesh import init_device_mesh from torch.distributed.fsdp import fully_shard, MixedPrecisionPolicy from torch.distributed.tensor.parallel import parallelize_module, ColwiseParallel, RowwiseParallel from torch.distributed.algorithms._checkpoint.checkpoint_wrapper import checkpoint_wrapper mesh = init_device_mesh("cuda", (dp_size, tp_size), mesh_dim_names=("dp", "tp")) model = build_transformer().cuda() # any nn.Module with .layers (blocks) # 1) tensor parallel inside each block: column-split up-projections, row-split down-projections for block in model.layers: parallelize_module(block, mesh["tp"], { "attn.q_proj": ColwiseParallel(), "attn.k_proj": ColwiseParallel(), "attn.v_proj": ColwiseParallel(), "attn.o_proj": RowwiseParallel(), "mlp.up_proj": ColwiseParallel(), "mlp.gate_proj": ColwiseParallel(), "mlp.down_proj": RowwiseParallel(), }) # 2) FSDP2 across the data-parallel dimension, one unit per block, then the root mp = MixedPrecisionPolicy(param_dtype=torch.bfloat16, reduce_dtype=torch.float32) for i, block in enumerate(model.layers): model.layers[i] = checkpoint_wrapper(block) # activation checkpointing fully_shard(model.layers[i], mesh=mesh["dp"], mp_policy=mp, reshard_after_forward=True) fully_shard(model, mesh=mesh["dp"], mp_policy=mp) opt = torch.optim.AdamW(model.parameters(), lr=1e-5) # optimizer state is sharded too # training loop is ordinary: loss.backward(); opt.step() — collectives are implicit # checkpoints: torch.distributed.checkpoint (DCP) saves DTensors shard-wise, reshards on load

When to use it: fine-tuning and post-training of dense models up to ~100B on a few nodes, anything LoRA/QLoRA, and any time you want plain PyTorch modules with no model rewrite. It is the default trainer behind Axolotl, TRL, verl's FSDP backend, NeMo RL's DTensor backend and TorchTitan.

Megatron-LM / Megatron-Core: the pretraining-scale toolkit

Megatron-Core is NVIDIA's library of parallel transformer building blocks (parallel embeddings and linears, fused attention via Transformer Engine, MoE layers, pipeline schedules) and Megatron-LM is the training harness around it. Where FSDP2 gives you one parallelism in native PyTorch, Megatron gives you all of them as first-class flags, each implemented with hand-optimized kernels:

Flag (illustrative)ParallelismWhat it does
--tensor-model-parallel-size 8TPColumn/row-split every linear inside the NVLink island (Ch. 12)
--sequence-parallelSPShard the LayerNorm/dropout activations along sequence between TP ranks — reclaims the activation memory TP leaves replicated
--pipeline-model-parallel-size 4 + --num-layers-per-virtual-pipeline-stagePP (interleaved)Layer stages across nodes with 1F1B / interleaved schedules to shrink bubbles
--context-parallel-size 2CPRing/Ulysses-style attention over sequence shards for long context
--expert-model-parallel-size 8EPExperts across GPUs with all-to-all dispatch (and --moe-grouped-gemm, token dropping/capacity options)
--use-distributed-optimizerZeRO-1Shard optimizer state across DP ranks (the memory win of ZeRO without sharding parameters)

Two more concepts matter in practice. The model spec (get_gpt_layer_with_transformer_engine_spec() and friends) declares which submodule implementations compose a layer — swapping attention or norm kernels is a spec change, not a model rewrite. And the distributed checkpoint format (--ckpt-format torch_dist) stores tensors with their parallel layout so a checkpoint saved at TP=8/PP=2 can be loaded at TP=4/PP=4; converting to and from Hugging Face format is a separate tool step (see §6).

# Illustrative Megatron-LM pretraining launch (8 nodes × 8 GPUs, dense 70B-class) torchrun --nnodes 8 --nproc_per_node 8 pretrain_gpt.py \ --tensor-model-parallel-size 8 --pipeline-model-parallel-size 4 --sequence-parallel \ --num-layers 80 --hidden-size 8192 --num-attention-heads 64 --group-query-attention --num-query-groups 8 \ --seq-length 8192 --micro-batch-size 1 --global-batch-size 512 \ --bf16 --use-distributed-optimizer --overlap-grad-reduce --overlap-param-gather \ --use-mcore-models --transformer-impl transformer_engine --recompute-activations \ --lr 1.5e-4 --min-lr 1.5e-5 --lr-decay-style cosine --lr-warmup-iters 2000 --train-iters 200000 \ --data-path $DATA --tokenizer-type HuggingFaceTokenizer --tokenizer-model meta-llama/Llama-3.1-70B \ --save $CKPT --load $CKPT --ckpt-format torch_dist --save-interval 500

When Megatron wins: pretraining or continued pretraining of large dense and MoE models across many nodes, anything that needs pipeline parallelism, and MoE training where grouped GEMMs and expert parallelism decide throughput. The cost is that your model must be expressed in Megatron's module zoo (or converted into it), and the learning curve is real. The RL frameworks below that target frontier scale (verl's Megatron backend, Miles, NeMo RL's Megatron backend) exist precisely so that RL can reuse these kernels.

Animation: the same linear layer under FSDP2 and under Megatron TP

Left: FSDP2 shards the weight by rows across four GPUs and must all-gather the full matrix before this layer computes, then frees it. Right: Megatron TP keeps a column slice resident on each GPU, computes a partial output locally, and all-reduces the activation. Same layer, opposite trade: FSDP2 moves parameters per step and tolerates slow interconnects between steps; TP moves activations every layer and needs NVLink. Real systems combine them on a 2-D mesh.

DeepSpeed, Axolotl and TRL: the layers above

DeepSpeed predates FSDP and implements the same ZeRO idea (stages 1/2/3) plus CPU/NVMe offload and its own pipeline engine, configured through a JSON file passed to the trainer. It remains common because Hugging Face's Trainer and Axolotl accept a DeepSpeed config directly; choose it when you need offload for a model that will not fit otherwise, or when an existing recipe uses it. FSDP2 is where new PyTorch-native work lands.

Axolotl (Chapter 13) is the YAML layer: one config names the base model, datasets and prompt format, adapter (LoRA/QLoRA), sequence packing, FSDP2 or DeepSpeed settings, and context parallelism, and axolotl train config.yml does the rest. It is the fastest path from "we have 50K examples" to a trained adapter without writing trainer code.

Hugging Face TRL is the Python-API counterpart: SFTTrainer (supervised fine-tuning with packing and chat templates), DPOTrainer (preference optimization from chosen/rejected pairs), GRPOTrainer (RL with reward functions, optionally generating with a co-located or remote vLLM), and reward-model trainers. Each is a subclass of the HF Trainer, so it inherits FSDP/DeepSpeed support via accelerate. It is the right tool for experiments up to a node or two; at frontier scale you graduate to the RL frameworks in §3.

# Illustrative TRL: SFT then GRPO with a verifiable reward from trl import SFTTrainer, SFTConfig, GRPOTrainer, GRPOConfig sft = SFTTrainer(model="Qwen/Qwen2.5-7B", train_dataset=sft_ds, args=SFTConfig(output_dir="sft", packing=True, bf16=True, max_length=4096)) sft.train() def math_reward(completions, answer, **kw): # one float per completion return [1.0 if extract_final(c) == a else 0.0 for c, a in zip(completions, answer)] grpo = GRPOTrainer(model="sft", reward_funcs=[math_reward], train_dataset=prompts_ds, args=GRPOConfig(output_dir="grpo", num_generations=8, max_completion_length=2048, use_vllm=True, bf16=True)) # use_vllm: rollouts on a vLLM server grpo.train()

3. RL post-training frameworks

RL post-training is the one workload where three different systems must cooperate inside a single training step: a trainer that holds parameters and does backward passes (FSDP2 or Megatron), a rollout engine that generates samples fast (vLLM or SGLang), and environments and reward functions that score them (Chapter 15 covers the systems theory; here is what the frameworks do about it).

verl: HybridFlow in practice

verl (from ByteDance's Seed team, built on the HybridFlow paper) is the most widely used open RL framework for LLMs. Its design has three ideas worth internalizing:

  • Single-controller programming model: one Python driver on Ray expresses the RL algorithm as ordinary sequential code — batch = rollout.generate(prompts); batch = ref.compute_log_prob(batch); batch = reward.compute(batch); actor.update(batch) — while each call fans out to a worker group of GPUs. The dataflow of PPO/GRPO stays readable; the distributed execution is hidden in the worker groups.
  • Worker groups per role: ActorRolloutRef (the policy being trained, its rollout engine, and the frozen reference model, usually co-located so they share GPUs by time-slicing), Critic (PPO only), RewardModel (optional; rule-based rewards are just Python). Each group has a backend: FSDP2 or Megatron for training, vLLM or SGLang for generation.
  • 3D-HybridEngine: the actor's weights live in the trainer's sharding (FSDP/Megatron layout) during the update and must be resharded into the engine's tensor-parallel layout for generation, in place, without a round trip through disk. verl does this each step; the cost of the reshard-and-sync is the "weight sync" bar in the timeline animation below.

Algorithms are a config switch (algorithm.adv_estimator = gae | grpo | rloo | reinforce_plus_plus), and DAPO-style refinements (clip-higher, dynamic sampling, token-level loss, overlong shaping) are flags on the actor config. Multi-turn tool-calling rollouts, LoRA RL, and MoE-with-Megatron are supported paths; recipes directory holds reproductions of DAPO, PRIME, and others.

# Illustrative verl launch for GRPO on math with a rule-based reward (config keys move; see docs) python3 -m verl.trainer.main_ppo \ algorithm.adv_estimator=grpo \ data.train_files=$HOME/data/gsm8k/train.parquet data.val_files=$HOME/data/gsm8k/test.parquet \ data.train_batch_size=512 data.max_prompt_length=1024 data.max_response_length=4096 \ actor_rollout_ref.model.path=Qwen/Qwen2.5-7B-Instruct \ actor_rollout_ref.actor.strategy=fsdp2 actor_rollout_ref.actor.optim.lr=1e-6 \ actor_rollout_ref.actor.ppo_mini_batch_size=128 actor_rollout_ref.actor.use_kl_loss=true \ actor_rollout_ref.rollout.name=vllm actor_rollout_ref.rollout.tensor_model_parallel_size=2 \ actor_rollout_ref.rollout.n=8 actor_rollout_ref.rollout.gpu_memory_utilization=0.6 \ reward_model.reward_manager=naive custom_reward_function.path=rewards/gsm8k.py \ trainer.n_gpus_per_node=8 trainer.nnodes=2 trainer.total_epochs=3 trainer.logger='["console","wandb"]'

Miles: SGLang-native, disaggregated, asynchronous

Miles descends from slime, the RL framework built by the GLM team around SGLang (rollouts) and Megatron-Core (training). Where verl began from a colocated, synchronous design and added asynchrony, the slime/Miles lineage starts from a disaggregated one: rollout engines and the trainer are separate resource pools connected by a data buffer; rollout workers keep generating (including long multi-turn agentic trajectories) while the trainer consumes batches, with bounded policy staleness and importance-weight correction. Its appeal is operational — rollout and training can be scaled and failed independently, SGLang's prefix caching and MLA/DP-attention paths are used natively for DeepSeek-class MoE rollouts, and the Megatron trainer gives frontier-scale parallelism. Choose it when rollout throughput dominates and you already run Megatron; choose verl when you want the broadest algorithm/recipe coverage and FSDP2 simplicity. Both expose the same mental model: a rollout side, a training side, a weight-sync path, a reward/environment side.

NeMo RL and NeMo Gym: environments as services

NeMo RL is NVIDIA's post-training library (successor to NeMo-Aligner): Ray-orchestrated, with DTensor (FSDP2) and Megatron backends, vLLM generation, and recipes for SFT, DPO and GRPO. Its distinctive companion is NeMo Gym, which turns the environment side into servers: a "resource server" hosts tools, a sandbox, or a reward model behind an HTTP interface; an "agent" definition describes how the policy interacts with it (single-turn verification, multi-turn tool use); and a recipe binds environments, rewards, data and the trainer. Scaling the environment is then an ordinary service-scaling problem, and the same environment serves evaluation and training — the connection the FDE role calls "defining how agent workflows, tools, environments and reward functions connect to training and evaluation".

OpenEnv: an open environment interface

OpenEnv (initiated by Meta with the PyTorch ecosystem) standardizes what an agentic environment is: a Gym-style API — reset(), step(action), state() — served over HTTP from an isolated container, with typed action/observation schemas, tool exposure (including MCP), and a hub for sharing environments. A trainer consumes an OpenEnv environment through a client; rollouts become sequences of model actions and environment observations; the reward comes back as part of the step result. The point is decoupling: environment authors (a coding sandbox, a browser task, a customer's internal workflow) publish once, and any trainer — verl, NeMo RL, TRL, Miles — can train against it.

# Illustrative: the shape of a Gym-style environment client used inside a rollout loop env = CodingEnv.from_docker_image("my-org/repo-task-env:latest") # isolated container per episode obs = env.reset(task_id="fix-flaky-test-1182") done, turns = False, [] while not done: action = policy.generate(obs.prompt) # model emits an edit / run_tests call result = env.step(action) # observation, reward, done turns.append((obs, action, result)) obs, done = result.observation, result.done reward = result.reward # terminal: tests pass → 1.0 # the trainer then masks environment tokens out of the loss and trains on model tokens only

Animation: one RL step across worker groups (verl-style)

Rows are GPU pools; bars are phases of one step. Colocated: the same GPUs time-slice generation, reference log-probs, reward, and the update, with a reshard/weight-sync between generation and training. Disaggregated (Miles-style): the rollout pool generates continuously while the trainer updates on slightly stale samples; the weight sync becomes a broadcast between pools. Either way, generation is the longest bar — the reason Chapter 15 is mostly about rollout throughput.

4. Inference engines

vLLM

vLLM is the default open-source serving engine and the default rollout engine inside RL frameworks. Its architecture (the "V1" engine) separates a front-end process — tokenization, the OpenAI-compatible API, streaming — from an EngineCore process that runs the scheduler and model executor in a tight loop. The concepts you configure map directly onto Chapter 11:

  • Scheduler: continuous batching with chunked prefill by default; --max-num-seqs and --max-num-batched-tokens bound the batch; preemption when KV runs out.
  • KV cache manager: PagedAttention blocks (--block-size), prefix caching on by default (hash of block contents → reuse across requests), --gpu-memory-utilization decides how much HBM becomes KV.
  • Parallelism: --tensor-parallel-size, --pipeline-parallel-size, --data-parallel-size (replicas; with DP attention for MLA models), expert parallelism for MoE.
  • LoRA adapters: --enable-lora --max-loras N --max-lora-rank R; requests name an adapter and the scheduler batches different adapters over the shared base (multi-adapter serving, Chapter 14).
  • Speculative decoding: --speculative-config with n-gram, draft-model, EAGLE/MTP methods.
  • Quantization: FP8 (--quantization fp8), AWQ/GPTQ/compressed-tensors checkpoints, FP8 KV cache (--kv-cache-dtype fp8).
  • Structured outputs: grammar backends (xgrammar by default) for JSON schema / regex / grammar constrained decoding.
# Illustrative serve command and Python API vllm serve meta-llama/Llama-3.1-70B-Instruct --tensor-parallel-size 4 \ --max-model-len 32768 --gpu-memory-utilization 0.92 --kv-cache-dtype fp8 \ --enable-lora --max-loras 16 --max-lora-rank 64 \ --speculative-config '{"method":"eagle","model":"yuhuili/EAGLE-LLaMA3.1-Instruct-70B","num_speculative_tokens":4}' # offline / rollout use from vllm import LLM, SamplingParams llm = LLM("Qwen/Qwen2.5-7B-Instruct", tensor_parallel_size=2, enable_prefix_caching=True) outs = llm.generate(prompts, SamplingParams(n=8, temperature=1.0, max_tokens=2048)) # RL frameworks drive this same object in-process and push new weights into it each step

SGLang

SGLang shares most of vLLM's feature list and differs in emphasis. Its runtime is built around RadixAttention — the KV cache is a radix tree over token prefixes, so any request sharing a prefix with a live or recently finished request (system prompts, few-shot headers, multi-turn history, the eight samples of a GRPO group) reuses it automatically. Its frontend language (@sgl.function with gen, select, fork) lets you write multi-call programs — branch, constrain, reuse — that the runtime schedules as one prefix-sharing tree. It has been the reference implementation for DeepSeek-class serving: DP attention (replicate the MLA attention per data-parallel rank while sharding the experts) and prefill/decode disaggregation, and the SGLang Router does prefix-aware load balancing across replicas. Constrained decoding (xgrammar/outlines/llguidance) is a flag. Choose SGLang when prefix reuse dominates (agents, RL rollouts, multi-turn) or when serving DeepSeek/MoE models at scale; both engines are excellent and most teams benchmark both.

# Illustrative SGLang launch python -m sglang.launch_server --model-path deepseek-ai/DeepSeek-V3 --tp 8 --dp 2 --enable-dp-attention \ --context-length 65536 --grammar-backend xgrammar --port 30000 python -m sglang_router.launch_router --worker-urls http://n1:30000 http://n2:30000 --policy cache_aware # the frontend language: one prefix, many branches, scheduled as a tree import sglang as sgl @sgl.function def triage(s, ticket): s += sgl.system("You are a support triager.") + sgl.user(ticket) s += sgl.assistant("Category: " + sgl.gen("cat", choices=["billing","bug","howto"]) + "\nSummary: " + sgl.gen("summary", max_tokens=64))

TensorRT-LLM

TensorRT-LLM is NVIDIA's engine for peak performance on NVIDIA hardware. Historically you built an engine (trtllm-build) — a compiled, shape-specialized graph with fused kernels — and served it via Triton or trtllm-serve; the newer PyTorch-backend flow runs models directly with the same kernels and in-flight batching, lowering the compile step. Its differentiators are the lowest-level access to FP8 and NVFP4 paths (via ModelOpt quantization), hand-tuned attention and MoE kernels, and disaggregated serving on NVIDIA Dynamo. Choose it when you own the NVIDIA fleet, the model is stable, and the last 10–20% of throughput is worth an engine-build pipeline; vLLM/SGLang remain the choice for breadth and velocity.

Animation: a request's journey through vLLM

Front-end tokenizes and enqueues; the scheduler admits the request when KV blocks are available; prefill runs in chunks interleaved with other requests' decode steps; blocks are allocated as the sequence grows (the shared system-prompt prefix is a cache hit); tokens stream back per decode step; on completion the blocks return to the pool. Every box is a concept from Chapter 11 with a config flag attached.

5. The AWS Neuron SDK

The Neuron SDK is the software stack for Trainium and Inferentia (Chapter 18 covers the hardware and NKI kernels). The mental shift from the GPU stack is that Neuron compiles graphs ahead of time: PyTorch code is traced into a graph, compiled by neuronx-cc into a NEFF executable for fixed shapes, and executed by the runtime. Dynamic shapes become buckets (a small set of compiled sequence lengths/batch sizes); anything the compiler cannot lower falls back to CPU and must be found and eliminated (the Deepgram lesson: zero fallbacks). The components:

  • neuronx-cc: the compiler. You rarely call it directly; the frontends do. Flags control optimization level, precision casting (--auto-cast), and model-type hints; the compile log and neuron-cc reports show unsupported ops and fallbacks.
  • torch-neuronx (and the newer native TorchNeuron backend): PyTorch integration — tracing (torch_neuronx.trace), XLA-style lazy execution for training, and the device abstraction.
  • NeuronX Distributed (NxD): the parallelism library. NxD Core provides parallel layers (ParallelEmbedding, ColumnParallelLinear, RowParallelLinear) and tensor/pipeline-parallel model wrappers — Megatron's ideas, for NeuronCores. NxD Inference (NxDI) ships ready model implementations (Llama, Qwen, Mixtral, DeepSeek-class), continuous batching, bucketing, speculative decoding and quantization, and is what vLLM's Neuron path calls into. NxD Training (NxDT) is the Megatron-style training harness with data/tensor/pipeline parallel and ZeRO-1.
  • vLLM on Neuron: a plugin that makes vllm serve ... --device neuron work with the vLLM API and scheduler while NxDI executes the model; you get continuous batching, OpenAI-compatible serving and multi-LoRA with Neuron underneath.
  • Neuron profiler and tools: neuron-profile for per-engine (Tensor/Vector/Scalar/GpSIMD) timelines and DMA stalls, neuron-top/neuron-ls for utilization and topology, NKI for custom kernels when the profile says a hot layer needs one, and the NKI Library of reference kernels (bundled with the compiler, overridable via pip install nki-library).
  • LNC (logical NeuronCore configuration): on Trn2, two physical cores can present as one logical core with doubled memory and compute — a compile-time choice that interacts with tensor-parallel degree.
# Illustrative compile-and-serve flow on a trn2 instance (NxD Inference + vLLM plugin) pip install neuronx-cc torch-neuronx neuronx-distributed neuronx-distributed-inference vllm-neuron # versions pinned by the Neuron release # 1) compile the model for fixed buckets (first run compiles and caches the NEFFs) export NEURON_COMPILE_CACHE_URL=s3://my-bucket/neuron-cache # share compiled artifacts vllm serve meta-llama/Llama-3.1-70B-Instruct --device neuron --tensor-parallel-size 32 \ --max-model-len 8192 --max-num-seqs 16 --block-size 32 \ --override-neuron-config '{"sequence_parallel_enabled": true, "logical_nc_config": 2, "buckets": [1024, 4096, 8192]}' # 2) profile a representative request to see where time goes neuron-profile capture -n /path/to/neff --output-dir prof/ # then view per-engine timelines # 3) parity + benchmark against the GPU baseline with the SAME harness (see hardware.html migration playbook)

What differs from the GPU workflow, concretely: a compile step you must budget for (and cache); bucketing instead of arbitrary shapes; parallelism degrees chosen with the core topology in mind (TP across 32 or 64 logical cores on trn2 is normal); and a profiling loop that looks at engine utilization rather than SM occupancy. The payoff is the cost-per-token case made in Chapter 18.

6. Orchestration, data and checkpoints

Ray: why RL frameworks are built on it

Ray provides actors (stateful processes on specific resources), tasks, an object store for passing large tensors between them, and placement groups that reserve bundles of GPUs with a packing strategy. That is exactly the vocabulary an RL framework needs: "a worker group of 8 actors, each pinned to one GPU, co-located on one node" is a placement group; "send this batch to the reward group" is an object-store transfer; "the driver calls generate() on the rollout group" is a remote method on an actor handle. verl, NeMo RL, OpenRLHF and Miles all use Ray this way — a single Python driver with a global view, worker groups doing the heavy lifting. For plain SFT you do not need Ray; torchrun (one process per GPU, rendezvous by environment variables) is enough, and clusters schedule it under Slurm or Kubernetes (Kubeflow/Volcano jobs, or SageMaker HyperPod on either).

Data and checkpoint formats

Hugging Face datasets is the lingua franca for training data (Arrow-backed, memory-mapped, streaming from S3), and tokenizers ships the fast tokenizers every framework loads by name. Checkpoints are where frameworks disagree, so know the three formats and the conversions between them:

FormatProduced byPropertiesConvert
safetensors (HF layout)transformers, TRL, Axolotl (merged), vLLM/SGLang consume itOne tensor map per shard file, no parallel layout, safe to load, the universal exchange format—
DCP (torch.distributed.checkpoint)FSDP2, TorchTitan, verl FSDP backend, NeMo RL DTensorShard-wise save, reshards on load to a different DP/TP layoutdcp_to_torch_save, framework "merge" tools → HF
Megatron dist-ckpt (torch_dist)Megatron-LM/Core, Miles, verl Megatron backendTensors stored with parallel metadata, loadable at a different TP/PPMegatron tools/checkpoint/convert.py (Megatron ↔ HF loaders/savers)

The practical rule: train in whatever sharded format your trainer wants, but every eval and every deployment consumes HF safetensors, so the "merge/convert to HF" step is part of your pipeline from day one (verl ships verl.model_merger; Axolotl merges LoRA with axolotl merge-lora). Keep the tokenizer and chat template with the weights — most "my fine-tune is worse in production" bugs are template mismatches, not weights.

LeRobot: the same stack for robots

For embodied work (Chapter 17), Hugging Face's LeRobot plays all the roles above at once: a dataset format (parquet + video + episode index on the Hub), policy implementations (ACT, Diffusion Policy, VLAs like SmolVLA and π0), and CLIs — lerobot-train, lerobot-eval, dataset visualization — plus hardware drivers for teleoperation. Its design mirrors this chapter's lesson: a standard data format and a standard policy interface are what let training, evaluation and deployment be separate, swappable systems.

7. The AWS managed paths

Self-managing the stack above is the right call for frontier-scale, bespoke or Trainium-first programs. For many customers the faster route is a managed service, and an FDE's job includes knowing when to say so.

Amazon Bedrock is the fully managed model service. For customization it offers fine-tuning and continued pre-training jobs on supported foundation models (you bring JSONL data; Bedrock runs the job and hosts the result), model distillation jobs (a teacher generates synthetic responses and a smaller student is fine-tuned on them — the on-policy distillation pattern from Chapter 14 as a managed job), and Custom Model Import, which lets you bring your own fine-tuned open weights (Llama, Mistral, Qwen and other supported architectures, in HF safetensors) and serve them through the Bedrock API on-demand or with provisioned throughput. Bedrock Evaluations (automatic, human and LLM-as-judge), Guardrails, Knowledge Bases (managed RAG) and Agents complete the picture. The trade: minimal operations and a single API, at the cost of control over serving internals (no custom kernels, fixed engine behavior) and a supported-architecture list.

Amazon SageMaker AI is the managed infrastructure layer. Training jobs run your container or framework script on managed instances (including trn1/trn2 and p5/p6 GPUs) with managed data channels, spot capacity, and distributed-training libraries; HyperPod provides persistent, resilient clusters (Slurm- or EKS-orchestrated) with automatic faulty-node replacement, checkpoint-aware resume and task governance — the right home for multi-week pretraining or large RL runs where node failures are a certainty; inference endpoints host containers (including vLLM/SGLang/TRT-LLM/Neuron images) with autoscaling, multi-model endpoints, and inference components for packing several models on one endpoint; JumpStart offers one-click open models. The trade: you still own the frameworks and their configs, but not the cluster plumbing.

Worked example: "post-train a 70B coding model with RL on tests, then serve with multi-LoRA"

Data and SFT. Curate repository tasks with executable tests (the customer's own CI history is the gold source); build an SFT set from successful trajectories; train a LoRA (rank 64) on a Llama-3.1-70B base with Axolotl on FSDP2 across 2×8 H100 — a day, not a week. Merge to HF safetensors; establish the eval baseline (pass@1 on a held-out task suite, p95 latency, cost per solved task — Ch. 14).

RL. Package the repo-task environment as an OpenEnv container (reset to a commit, step = apply edit or run tests, reward = tests pass); run verl with GRPO/DAPO: actor on FSDP2 (or Megatron if you go full-parameter), rollouts on vLLM TP=4 with prefix caching (every group shares the repo context), 8 samples per prompt, multi-turn tool calling, environment-token loss masking. Expect generation to dominate; size the rollout share of GPUs accordingly (Ch. 15). If rollout throughput is the wall and you already run Megatron, evaluate Miles's disaggregated path.

Serve. Export the RL'd policy as a LoRA over the shared base (or merge if a single tenant); serve with vLLM --enable-lora --max-loras 16 so per-team adapters batch over one copy of the 70B weights; FP8 weights and FP8 KV for cost; EAGLE speculation for latency. Benchmark the same harness on Trainium via vLLM on Neuron and let the cost-per-token table (Ch. 18) decide the fleet. Gate releases with the eval suite; stream production failures back into the task set.
