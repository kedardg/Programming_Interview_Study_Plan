1. Anatomy of a kernel: vector add in CUDA and Triton

Every CUDA kernel answers one question: given my thread's coordinates, which piece of the data is mine? Here is the complete vector add, the "hello world" from GPU MODE L3:

__global__ void add(const float* x, const float* y, float* out, int n) { int i = blockIdx.x * blockDim.x + threadIdx.x; // my global index if (i < n) // guard the ragged edge out[i] = x[i] + y[i]; // coalesced: lane k hits element k } // launch: one thread per element, 256 threads per block int threads = 256, blocks = (n + threads - 1) / threads; // ceil-div add<<<blocks, threads>>>(x, y, out, n);
  • blockIdx.x * blockDim.x + threadIdx.x is the CUDA idiom: block coordinate × block size + position within the block = global position. Memorize it.
  • The if (i < n) guard exists because grids are launched in whole blocks; the last block overhangs the array.
  • Adjacent threads touch adjacent floats → perfectly coalesced (see the coalescing animation in GPU §4).

The same kernel in Triton swaps the per-thread view for a per-tile view: one program owns a block of 1024 elements and operates on whole vectors; the compiler decides how the tile maps onto threads, registers, and shared memory.

@triton.jit def add_kernel(x_ptr, y_ptr, out_ptr, n, BLOCK: tl.constexpr): pid = tl.program_id(axis=0) # ↔ blockIdx.x offs = pid * BLOCK + tl.arange(0, BLOCK) # ↔ blockIdx.x*blockDim.x + threadIdx.x, vectorized mask = offs < n # ↔ if (i < n) x = tl.load(x_ptr + offs, mask=mask) # a whole tile at once y = tl.load(y_ptr + offs, mask=mask) tl.store(out_ptr + offs, x + y, mask=mask) grid = (triton.cdiv(n, 1024),) add_kernel[grid](x, y, out, n, BLOCK=1024)

The correspondence is exact — program_id ↔ blockIdx, arange + mask ↔ threadIdx + bounds guard — and it holds for every kernel in this chapter. CUDA gives you control of each of the 32 lanes; Triton gives you tiles and lets the compiler handle coalescing, shared memory, and pipelining. Learn both: CUDA to understand what the machine does, Triton to ship fused kernels fast.

2. Reduction: from atomics to warp shuffles

Summing an array is the first kernel where threads must cooperate, and it introduces the pattern behind softmax, norms, and attention: parallel reduction. Three generations:

  1. Naive: every thread does atomicAdd(&sum, x[i]). Correct, but all threads serialize on one memory location — throughput of a single counter.
  2. Tree reduction in shared memory: each block stages its slice into shared memory, then halves the active threads each step: 256→128→…→1 partial sum per block, in log₂(n) steps, then one atomic per block. This is the NVIDIA reduction-deck classic.
  3. Warp shuffle: the last 32 values never need shared memory at all — __shfl_down_sync moves registers between lanes directly: v += __shfl_down_sync(0xffffffff, v, 16); …, 8, 4, 2, 1. Modern reductions do shared-memory tree down to one warp, shuffles the rest.

Animation: tree reduction

16 values in shared memory. Each step, the active half adds its partner from stride away and the stride halves: 4 steps instead of 15 sequential adds. Note which threads go idle — by the last step 15 of 16 do nothing, which is why the final warp switches to shuffles and why reductions want many blocks in flight.

__global__ void reduce(const float* x, float* out, int n) { __shared__ float s[256]; int tid = threadIdx.x, i = blockIdx.x * 256 + tid; s[tid] = (i < n) ? x[i] : 0.0f; __syncthreads(); // tile fully staged for (int stride = 128; stride > 0; stride >>= 1) { // 256→1 in 8 steps if (tid < stride) s[tid] += s[tid + stride]; // no divergence *within* active warps __syncthreads(); // every step is a barrier } if (tid == 0) atomicAdd(out, s[0]); // one atomic per block, not per element }

The barrier placement is the classic bug: __syncthreads() must be hit by all threads of the block, so it lives outside the if. Run Compute Sanitizer's racecheck on your version before trusting it (Step 18 protocol, §8).

3. Transpose: fixing uncoalesced access with a staging tile

Matrix transpose does zero math — it is a pure memory-movement exercise, which is exactly why it teaches coalescing. The naive kernel reads rows and writes columns: the read is coalesced, but adjacent threads write out[x*N + y] with stride N — up to 32 transactions per warp store. The fix: stage a 32×32 tile in shared memory, transpose inside the tile (where random access is cheap), and write out rows again.

Animation: tiled transpose through shared memory

Left: source matrix — a warp reads one row of the blue tile (coalesced, 1 transaction). Middle: the tile sits in shared memory and is read column-wise — fine on-chip, and the +1 padding ([32][33]) dodges bank conflicts. Right: the warp writes a contiguous row of the output (coalesced again). Both global-memory touches are coalesced; the "bad" access pattern happens only where it's free.

__global__ void transpose(const float* in, float* out, int N) { __shared__ float tile[32][33]; // 33: pad to avoid bank conflicts int x = blockIdx.x*32 + threadIdx.x, y = blockIdx.y*32 + threadIdx.y; tile[threadIdx.y][threadIdx.x] = in[y*N + x]; // coalesced read __syncthreads(); x = blockIdx.y*32 + threadIdx.x; y = blockIdx.x*32 + threadIdx.y; out[y*N + x] = tile[threadIdx.x][threadIdx.y]; // coalesced write, transposed via smem }

Benchmark both versions against x.T.contiguous() in PyTorch and against the copy bandwidth of your 5080 (~0.96 TB/s): a good transpose reaches ~80–90% of pure copy speed. This is Week 4 of the schedule.

4. Online softmax: the trick that enables FlashAttention

Softmax must be computed stably: softmax(x)ᵢ = e^(xᵢ−m)/Σⱼe^(xⱼ−m) with m = max(x), otherwise e^x overflows FP16 at x≈11. The textbook version makes three passes over the row (max, then sum, then normalize) — three trips through memory for a bandwidth-bound op. The online formulation (Milakov & Gimelshein, the Step 9 exercise) fuses the first two passes by keeping a running max m and running denominator d, rescaling d whenever the max improves:

m ← −∞ ; d ← 0 for each xᵢ: m_new = max(m, xᵢ) d = d · e^(m − m_new) + e^(xᵢ − m_new) // rescale old sum, add new term m = m_new // one pass gives (m, d); a second pass writes e^(xᵢ−m)/d

The correction factor e^(m − m_new) is the whole idea: every term already in d was computed against the old max, so when the max rises, multiply d once to re-reference it. The same algebra lets FlashAttention process K/V in tiles and merge per-tile softmax statistics without ever materializing the full attention matrix — see Attention.

Animation: running max and rescaled denominator

One row streams left to right. The table tracks m and d after each element; when an element beats the running max, the old denominator visibly shrinks by e^(m−m_new) (flash) before the new term joins. At the end, compare with the 3-pass result: identical, one less pass over memory.

The fused Triton version (the Week 6 exercise, in the style of the GPU MODE L14 / Liger notebooks) does the whole row in registers — one load, one store:

@triton.jit def softmax_kernel(x_ptr, y_ptr, stride, n_cols, BLOCK: tl.constexpr): row = tl.program_id(0) offs = tl.arange(0, BLOCK) # BLOCK = next_pow2(n_cols) x = tl.load(x_ptr + row*stride + offs, mask=offs < n_cols, other=float('-inf')) x = x - tl.max(x, axis=0) # stable num = tl.exp(x) y = num / tl.sum(num, axis=0) # max+sum+normalize, zero extra memory trips tl.store(y_ptr + row*stride + offs, y, mask=offs < n_cols)

Why it beats eager PyTorch: unfused softmax is ~4 kernel launches and ~8N bytes of traffic; this is 1 launch and ~2N bytes (read once, write once) — and softmax is bandwidth-bound, so bytes ≈ time. Check it with torch.allclose(y, torch.softmax(x, -1), atol=1e-6), then benchmark GB/s vs row length like the Triton tutorial does.

5. The matmul ladder

Matrix multiply is the centerpiece exercise (Weeks 7–8) because it is the one kernel where you can feel every level of the hierarchy. The core quantity is data reuse: C = A·B does 2N³ FLOPs on 3N² values, so each value can in principle be used N times — but only if you orchestrate the reuse. The naive kernel reuses nothing: each thread computes one C element and streams 2N values from HBM, so AI ≈ 1 and you sit at the far left of the roofline. Every rung of the ladder below is a reuse mechanism.

Animation: shared-memory tiled matmul

One thread block owns the highlighted C tile. Each step it stages one tile of A (row panel) and one of B (column panel) into shared memory — the two flashes — then accumulates their product into C's registers while marching k across the K dimension. Each A/B value is loaded from HBM once and reused TILE times from shared memory: reuse = tile size, which is the whole trick.

__global__ void sgemm_tiled(const float* A, const float* B, float* C, int N) { __shared__ float As[32][32], Bs[32][32]; int row = blockIdx.y*32 + threadIdx.y, col = blockIdx.x*32 + threadIdx.x; float acc = 0.f; for (int k = 0; k < N; k += 32) { // march across K As[threadIdx.y][threadIdx.x] = A[row*N + k + threadIdx.x]; // stage tiles Bs[threadIdx.y][threadIdx.x] = B[(k + threadIdx.y)*N + col]; // (coalesced loads) __syncthreads(); for (int kk = 0; kk < 32; ++kk) // reuse from smem 32× acc += As[threadIdx.y][kk] * Bs[kk][threadIdx.x]; __syncthreads(); } C[row*N + col] = acc; }

The full ladder, following siboehm's worklog (FP32, 4096², A6000; replicate these on your 5080 and record your own numbers — that's the Step 18 deliverable):

Read the ladder as a hierarchy of reuse: HBM → shared memory (rung 3) → registers (rungs 4–5) → better instructions (6–8). The same decomposition — block tile / warp tile / thread tile marching over K — is exactly what CUTLASS formalizes and what you'll meet again as NKI's tile model in Hardware.

6. Tensor cores, CUTLASS & CuTe

Past rung 8, scalar FMAs run out; FP16+ matmuls move to tensor cores. One mma.sync.m16n8k16 instruction makes a whole warp cooperatively compute D = A·B + C for a 16×8 output tile with k=16, with inputs scattered across the 32 lanes' registers in a fixed fragment layout. You don't address "thread 3's element" anymore — you lay data out so the hardware's expected fragment pattern is satisfied, usually via ldmatrix from shared memory. That layout bookkeeping is the hard part, and it is why the ecosystem built abstractions:

CUTLASS is NVIDIA's template library implementing the full tiling hierarchy (block/warp/instruction tiles, pipelined stages, epilogues). CuTe, its core since 3.x, reduces all of it to one algebraic object — the Layout, a function from logical coordinates to memory offsets built from (shape, stride) pairs. Tiling, swizzling, fragment layouts, and partitioning become layout algebra (compose, divide, partition), checked at compile time. The CuTe GEMM tutorial in Step 11 walks a matmul through these layouts; after rungs 1–8 above, it reads as naming things you already built by hand.

Your hardware: the RTX 5080 is consumer Blackwell (sm_120). Its tensor cores run warp-level mma.sync, now including FP8 and FP4 — but Hopper's wgmma and datacenter Blackwell's tcgen05/tensor-memory instructions don't exist on it. CUTLASS example 79 ("blackwell_geforce_gemm", the Week 8 wildcard) targets exactly your chip; read wgmma/tcgen05 material as theory.

7. Triton in depth

Triton's model: a kernel is a grid of programs; each program computes on tiles (power-of-2 blocks) with whole-tile loads, stores, and math. The compiler assigns tiles to warps, inserts shared-memory staging and ldmatrix/mma, handles coalescing and double buffering. What you keep: tile sizes, the grid, masking, and the algorithm. What you give up: warp-level tricks (shuffles, custom fragment layouts), fine control of smem.

  • Triton wins for fused elementwise+reduction kernels (softmax, RMSNorm, LayerNorm — the Liger kernels), attention variants, quantize/dequantize epilogues: 10× less code within ~5% of hand CUDA.
  • CUDA/CUTLASS wins when the fragment layout is the problem: peak dense GEMM, exotic quantized formats (see the marlin kernels), warp-specialized pipelines.
  • Autotuning: decorate with @triton.autotune(configs=[...], key=['N']) — it benchmarks tile-size configs per input shape and caches the winner, mechanizing rung 7 of the ladder.

GPU MODE L14 (Practitioner's Guide to Triton) and the three official Triton tutorials (vector add → fused softmax → matmul) are the canonical path; they mirror sections 1, 4, and 5 of this page.

8. The practice protocol (Step 18)

Every kernel you write goes through the same gate before it counts:

# 1. Correctness — against PyTorch, with tolerance appropriate to dtype torch.testing.assert_close(mine(x), torch.softmax(x, -1), rtol=1e-4, atol=1e-5) compute-sanitizer --tool memcheck ./bench # and racecheck for smem kernels # 2. Honest benchmark — warmup, sync, CUDA events, many iters for _ in range(10): k() # warmup (JIT, clocks, caches) torch.cuda.synchronize() start, end = torch.cuda.Event(True), torch.cuda.Event(True) start.record() for _ in range(100): k() end.record(); torch.cuda.synchronize() ms = start.elapsed_time(end) / 100 # never time.time() around async launches # 3. Roofline check — GB/s or TFLOP/s vs the 5080's ~0.96 TB/s / ~220 TF # 4. Profile — ncu --set full ./bench → SOL, coalescing, occupancy (GPU §6)
  1. Implement the Step 9 set yourself: transpose, reduction, scan, online softmax. Then climb the matmul ladder one rung at a time, recording your numbers next to siboehm's.
  2. Fuse something real: the Triton softmax above, then an RMSNorm forward against Liger's.
  3. Port one kernel (online softmax or RoPE) to NKI with nki.simulate_kernel — no Trainium needed — and compare your tiling against the nki-library reference (details in Hardware).
