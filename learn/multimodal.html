Multimodal LLMs: How Models See, Hear, Watch and Touch the World

A language model only ever consumes a sequence of vectors. Every modality — pixels, waveforms, video, point clouds, sensor streams — enters by being turned into such a sequence and spliced into the same residual stream that carries text. This chapter is about the encoders, tokenizers, and fusion wiring that do the splicing, with the concepts and the code for each modality, and what it costs to serve the result. It assumes the transformer block, attention, and architecture chapters.

1. The unifying idea: everything is embeddings in the residual stream

Peel the multimodality off any model that "sees" and what remains is unchanged: tokens → embeddings → repeated mixer/MLP blocks → LM head. Multimodal capability is added by choosing where non-text information enters that pipeline and in what form. Three families cover essentially every deployed system:

  1. Encoder + projector (the LLaVA pattern). A pretrained modality encoder (a ViT for images, a Whisper-style encoder for audio) produces a grid of feature vectors; a small projector (an MLP) maps each one into the LLM's embedding dimension; the resulting "soft tokens" are concatenated with the text embeddings and the LLM runs unchanged. The LLM never sees pixels — it sees vectors that look like word embeddings and happen to carry visual content. Cheap to train (hours on a few GPUs for alignment), modular (swap encoders), and the dominant open-weight pattern: LLaVA, Qwen-VL, Pixtral, InternVL, SmolVLM, Voxtral for audio.
  2. Cross-attention / resampler (Flamingo, Perceiver, Llama 3.2 Vision). Visual features stay in a side stream; the LLM's layers gain inserted cross-attention blocks whose queries are text and whose keys/values are visual features. Often a Perceiver resampler first compresses thousands of encoder outputs to a fixed 64–256 latent tokens via learned queries. The base LLM's text behavior is untouched (gated cross-attention initializes at zero), and the sequence length does not grow with image count — but you pay for new parameters in every layer.
  3. Early fusion / native tokens (Chameleon, Gemini-class, GPT-4o-class, Gemma 3n). Images and audio are tokenized into discrete tokens by a learned codec (a VQ image tokenizer, a neural audio codec) and the single transformer is pretrained on mixed sequences from the start. One vocabulary, one model, any-to-any generation — at the cost of training from scratch on enormous interleaved corpora, and of a much harder optimization (modality competition for the shared capacity).

2. Vision

2.1 Patchify: how an image becomes a sequence

A Vision Transformer (ViT) does to an image what a tokenizer does to text, except the "tokens" are geometric. Cut the image into a grid of P×P pixel patches (P = 14 or 16 is standard), flatten each patch into a vector of 3·P² numbers, multiply by one learned projection matrix, add a positional embedding, and you have a sequence the transformer can process. A 224×224 image with 16×16 patches yields (224/16)² = 196 tokens. The arithmetic is the whole story of vision-LLM cost: tokens scale with area, so doubling resolution quadruples the sequence.

That quadratic growth is why every modern VLM carries a token-reduction strategy on top of the encoder:

  • Any-resolution tiling (LLaVA-NeXT, InternVL): split a large image into 336- or 448-pixel tiles, encode each, plus one downsampled global thumbnail. Preserves fine detail (OCR, charts) at the cost of thousands of tokens.
  • Pixel unshuffle / spatial merging (InternVL, Qwen2-VL): concatenate every 2×2 block of neighboring patch features into one vector and project it — a 4× token reduction before the LLM.
  • Learned compression (Perceiver resampler, Q-Former in BLIP-2): a fixed number of learned queries cross-attend to all patch features; 576 patches become 64 tokens regardless of resolution.
  • Native dynamic resolution (Qwen2-VL): keep the image's own aspect ratio, vary token count per image, and use 2D rotary positions (next section) so the LLM knows where each patch sat.

# Minimal ViT patch embedding (what every vision encoder starts with) import torch, torch.nn as nn class PatchEmbed(nn.Module): def __init__(self, img=224, patch=16, in_ch=3, dim=768): super().__init__() self.n = (img // patch) ** 2 # 196 tokens for 224/16 # A conv with kernel=stride=patch IS the "flatten + linear" of each patch self.proj = nn.Conv2d(in_ch, dim, kernel_size=patch, stride=patch) self.pos = nn.Parameter(torch.zeros(1, self.n, dim)) # learned 1D pos (ViT) or use 2D-RoPE def forward(self, x): # x: (B, 3, 224, 224) x = self.proj(x) # (B, dim, 14, 14) x = x.flatten(2).transpose(1, 2) # (B, 196, dim) ← a sequence, like text return x + self.pos # LLaVA-style projector: encoder features → LLM embedding space class Projector(nn.Module): def __init__(self, enc_dim=1024, llm_dim=4096): super().__init__() self.mlp = nn.Sequential(nn.Linear(enc_dim, llm_dim), nn.GELU(), nn.Linear(llm_dim, llm_dim)) def forward(self, feats): # (B, 576, 1024) from a CLIP/SigLIP ViT-L/14 @ 336px return self.mlp(feats) # (B, 576, 4096): 576 "soft tokens" # Splice image tokens into the text sequence at an <image> placeholder def merge(text_ids, image_feats, embed, image_token_id): # text_ids: (T,), image_feats: (576, llm_dim), embed: nn.Embedding of the LLM text_emb = embed(text_ids) # (T, llm_dim) pos = (text_ids == image_token_id).nonzero()[0, 0] seq = torch.cat([text_emb[:pos], image_feats, text_emb[pos + 1:]], dim=0) return seq # (T - 1 + 576, llm_dim) → straight into the LLM blocks

Three things to notice in the code. The conv-with-stride is literally patchify; nothing exotic. The projector output has the LLM's hidden size and no other constraint — the LLM has to learn that these vectors mean "pixels", which is what stage-1 alignment training does. And merge is plain concatenation: the LLM's forward pass does not know which positions came from an image, which is why the serving engine must track that mapping to build the right attention mask, positional ids, and prefix-cache keys (vLLM's multimodal path does exactly this).

2.2 Where the encoder's knowledge comes from: contrastive pretraining

The ViT inside almost every VLM is not trained on ImageNet labels; it is CLIP or SigLIP — trained on hundreds of millions of (image, caption) pairs to produce embeddings where matching pairs are close and non-matching pairs are far. The objective is the InfoNCE loss: for a batch of N pairs, compute the N×N matrix of cosine similarities between every image and every caption, and treat each row (and each column) as an N-way classification whose correct answer is the diagonal. SigLIP replaces the softmax over the batch with an independent sigmoid per pair, which scales to larger batches and removes the need for a global normalization across devices. The result is an encoder whose features are already semantically aligned with language — which is why a two-layer MLP is enough to connect it to an LLM.

Animation: InfoNCE pulls the diagonal up

An 8×8 image–caption similarity matrix. Training raises matching pairs (diagonal) and pushes down everything else; the loss shown is the symmetric cross-entropy over rows and columns. After convergence, an image's nearest caption is its own — and, crucially, the embedding space has become a shared language-visual space.

3. Audio

Sound is a 1-D signal sampled 16,000–48,000 times per second — far too many numbers to feed a transformer raw. Every audio pipeline first moves to a time–frequency representation: slide a short window (25 ms, hop 10 ms) across the waveform, take the FFT of each window (STFT), keep the magnitudes, and bin frequencies on the mel scale (perceptually spaced, ~80–128 bins). A minute of audio becomes a 6000×80 "image" — which is exactly how the models treat it.

Animation: waveform → STFT frames → mel spectrogram

Top: a synthetic waveform (a chirp plus a low tone). A 25 ms window (highlighted) slides by 10 ms hops; each position produces one spectral column, drawn at the bottom with low frequencies at the bottom and mel-warped bins. Note the rising chirp becomes a diagonal streak and the steady tone a horizontal line — the encoder sees this, not the waveform.

From the spectrogram there are two routes into an LLM, and the choice decides whether the model can only listen or also speak:

3.1 Continuous encoders (understanding)

A Whisper-style encoder — two strided convolutions that downsample 2× in time, then a transformer stack — turns the mel frames into ~50 feature vectors per second. That is still a lot of tokens for an LLM (a 30-second clip is 1500), so a further downsampling (stack k adjacent frames, or a Q-Former/resampler) brings it to ~5–12 tokens per second before a projector maps them into the LLM. Qwen-Audio, Voxtral, and SALMONN follow this recipe; it is the audio twin of LLaVA, and training proceeds identically (align the projector, then instruction-tune on transcripts and spoken-QA data). Because the encoder is Whisper-like, these models inherit strong speech recognition for free.

This is also the architecture of production speech-to-text systems like the Deepgram pipeline in the hardware chapter: an encoder over fixed-length mel windows and an autoregressive text decoder. Their Trainium port's key move — compiling encoder and decoder separately for static shapes — only works because the mel front end fixes the input shape (pad or chunk audio to a known length), which is a general lesson for serving audio: control the shape at the spectrogram boundary.

# Mel spectrogram front end (torchaudio) — the input to every speech encoder import torchaudio, torch wav, sr = torchaudio.load("clip.wav") # (1, samples), e.g. sr=16000 wav = torchaudio.functional.resample(wav, sr, 16000) mel = torchaudio.transforms.MelSpectrogram( sample_rate=16000, n_fft=400, win_length=400, hop_length=160, # 25 ms window, 10 ms hop n_mels=80)(wav) # (1, 80, frames) frames ≈ seconds*100 log_mel = torch.log(mel.clamp(min=1e-10)) # Whisper normalizes to roughly [-1, 1] # Whisper-style encoder front: 2 convs halve the frame rate, then a transformer class AudioEncoderFront(torch.nn.Module): def __init__(self, n_mels=80, dim=1024): super().__init__() self.c1 = torch.nn.Conv1d(n_mels, dim, 3, padding=1) self.c2 = torch.nn.Conv1d(dim, dim, 3, stride=2, padding=1) # 100 → 50 frames/s def forward(self, log_mel): # (B, 80, T) x = torch.nn.functional.gelu(self.c1(log_mel)) x = torch.nn.functional.gelu(self.c2(x)) # (B, dim, T/2) return x.transpose(1, 2) # (B, T/2, dim) → transformer blocks # Downsample ×4 by stacking frames before the projector (50 → 12.5 tokens/s) def stack_frames(x, k=4): # x: (B, T, dim) B, T, D = x.shape; T = T - T % k return x[:, :T].reshape(B, T // k, D * k) # (B, T/4, 4*dim) → Projector(4*dim → llm_dim)

3.2 Discrete codec tokens (generation)

To make a language model produce audio, you need audio to be a vocabulary. Neural codecs (SoundStream, EnCodec, and successors like Mimi in Moshi) learn exactly that: an encoder compresses the waveform to a low-rate latent (e.g. 75 or 12.5 frames per second), a quantizer snaps each latent to entries of learned codebooks, and a decoder reconstructs the waveform from the codes. The quantizer is the clever part — residual vector quantization (RVQ): the first codebook (say 1024 entries) picks the nearest code; the residual error is quantized by a second codebook; its residual by a third; and so on for 8–32 stages. Each stage adds fidelity, so the first codebooks carry phonetic/semantic content and later ones carry timbre and detail.

With audio as discrete tokens, AudioLM-style models generate speech autoregressively; Moshi goes further to full-duplex conversation by modeling the user's audio stream and the model's own audio-and-text streams in parallel at 12.5 Hz, so it can listen and talk simultaneously with ~200 ms latency. The architectural question of "how many codebooks per timestep and in what order" (flattened, delayed/interleaved, or predicted by a small depth transformer) is the audio equivalent of multi-token prediction in the architectures chapter.

Animation: residual vector quantization

A 2-D latent (★) is approximated stage by stage: each codebook (colored dots) quantizes the current residual, the chosen code is added to the running reconstruction (◆), and the residual shrinks. Four stages with 8-entry codebooks encode the point with 4×3 = 12 bits; the error after each stage is shown. Real codecs use 1024-entry codebooks and 8–32 stages on ~128-D latents.

# Residual vector quantizer forward pass (inference path; training adds commitment/codebook losses + EMA updates) class RVQ(torch.nn.Module): def __init__(self, dim=128, n_codebooks=8, codebook_size=1024): super().__init__() self.books = torch.nn.ParameterList( [torch.nn.Parameter(torch.randn(codebook_size, dim)) for _ in range(n_codebooks)]) def forward(self, z): # z: (B, T, dim) latent from the codec encoder residual, recon, codes = z, torch.zeros_like(z), [] for book in self.books: d = torch.cdist(residual, book[None]) # (B, T, codebook_size) distances to every code idx = d.argmin(-1) # (B, T) token ids for this stage q = book[idx] # (B, T, dim) chosen codes recon = recon + q residual = residual - q # next stage quantizes what is left codes.append(idx) # straight-through estimator so gradients reach the encoder during training recon = z + (recon - z).detach() return recon, torch.stack(codes, -1) # codes: (B, T, n_codebooks) → 8 tokens per frame

4. Video

Video is the modality that breaks naive scaling. Treat each frame as an image and the token count is frames × tokens-per-frame: one minute sampled at 1 fps with 196 tokens per frame is already 11,760 tokens; at 2 fps with 448-px frames it is 94,080 — longer than most context windows and, per the KV formula, about 1.5 GB of cache on an 8B model in BF16. Everything in video-LLM design is about spending that budget wisely:

  • Temporal sampling: sparse uniform sampling (8–64 frames) for short clips; adaptive keyframe selection for long ones.
  • Tubelets / 3D patches: patchify across time as well as space (2×16×16), so two frames share one token — the video-native ViT (ViViT, VideoMAE) and Qwen2-VL's approach.
  • Temporal pooling: average or attention-pool neighboring frames' tokens before the LLM (Video-LLaMA, LLaVA-Video).
  • Streaming memory: for hour-long video, keep a compressed memory of past tokens (a few hundred) plus full detail for the current window — the same hierarchy as long-context text methods.

Positions in three dimensions: M-RoPE

Once tokens come from a (time, height, width) grid, a 1-D position index throws away the geometry. Qwen2-VL's M-RoPE splits the rotary dimensions into three groups and gives each token three position ids: t (frame index), h (patch row), w (patch column). Text tokens use the same value for all three (so M-RoPE reduces to ordinary RoPE on text), and tokens after a video continue counting from the video's maximum id. The attention score between two patches then depends on their offsets in all three axes — "same row, three frames later" is a geometric relation the model can express directly, and resolution or frame-rate changes do not scramble positions.

# M-RoPE position ids for a text + video + text sequence def mrope_positions(n_text_before, T, H, W, n_text_after): ids = [] # each entry: (t, h, w) p = 0 for _ in range(n_text_before): # text: t = h = w = running index ids.append((p, p, p)); p += 1 base = p for t in range(T): # video patches: 3-D grid offsets from base for h in range(H): for w in range(W): ids.append((base + t, base + h, base + w)) p = base + max(T, H, W) # resume text after the largest extent for _ in range(n_text_after): ids.append((p, p, p)); p += 1 return torch.tensor(ids) # (L, 3) → three RoPE rotations on three slices of head_dim # Worked example: 1 min @ 1 fps, 224px/16 → T=60, H=W=14 → 11,760 video tokens; with 2-frame tubelets + 2×2 merge → 1,470

5. 3D and spatial understanding

Images are projections; the world is 3-D. Models that must act in it (the robots in the RL & Robotics chapter) need geometry, and there are three ways to get it into an LLM.

5.1 Point clouds and the permutation problem

A LiDAR scan or a depth camera gives an unordered set of (x, y, z[, color]) points. A set has no sequence order, so any tokenizer must be permutation-invariant: processing the same points in a different order must give the same result. PointNet does it with shared per-point MLPs plus a symmetric max-pool; PointNet++ and Point-BERT add locality by farthest point sampling (pick well-spread center points), grouping each center's k nearest neighbors into a local patch, and encoding each patch with a small PointNet — producing, say, 512 "point tokens" from 8,192 points. Those tokens are to a point cloud what ViT patches are to an image, and from there the LLaVA recipe applies: PointLLM, 3D-LLM, and LL3DA project point tokens (or 3-D features lifted from multi-view images) into an LLM for captioning, grounding ("the red chair left of the table"), and question answering about scenes.

Animation: farthest point sampling and grouping

400 points (a 2-D slice of a cloud). Each FPS step picks the point farthest from all centers chosen so far — spreading centers evenly regardless of density. "Group" then draws each center's k nearest neighbors; each group becomes one token via a mini-PointNet (per-point MLP → max-pool), which is order-independent by construction.

# Point tokenizer: FPS centers → kNN groups → mini-PointNet per group (permutation invariant) def farthest_point_sample(xyz, n_centers): # xyz: (N, 3) N = xyz.shape[0]; idx = torch.zeros(n_centers, dtype=torch.long) dist = torch.full((N,), float("inf")); far = torch.randint(N, (1,)).item() for i in range(n_centers): idx[i] = far dist = torch.minimum(dist, ((xyz - xyz[far]) ** 2).sum(-1)) # distance to nearest chosen center far = dist.argmax().item() return idx class PointTokenizer(torch.nn.Module): def __init__(self, k=32, dim=384): super().__init__(); self.k = k self.mlp = torch.nn.Sequential(torch.nn.Linear(3, 128), torch.nn.GELU(), torch.nn.Linear(128, dim)) def forward(self, xyz, n_tokens=512): # (N, 3) → (n_tokens, dim) centers = xyz[farthest_point_sample(xyz, n_tokens)] # (n_tokens, 3) d = torch.cdist(centers, xyz) # (n_tokens, N) nbrs = xyz[d.topk(self.k, largest=False).indices] # (n_tokens, k, 3) local = nbrs - centers[:, None] # center each group return self.mlp(local).max(dim=1).values # max-pool over k: order-invariant

5.2 From many images to a 3-D model

When the sensor is a camera, 3-D must be inferred. NeRF represents a scene as a neural function from (position, viewing direction) to (color, density), fit by rendering rays and matching the training photos — beautiful, slow to render. 3-D Gaussian Splatting replaces the implicit function with millions of explicit anisotropic Gaussians that are rasterized directly, giving real-time rendering and fast training; it is now the default for scene reconstruction. Neither is itself an LLM component, but their outputs (a renderable scene, novel views, depth) feed 3-D-LLMs, and feed-forward successors (DUSt3R-style networks that regress point maps from image pairs in one pass) are increasingly the "encoder" for spatial reasoning: images in, metric 3-D out, project to the LLM.

5.3 Why VLMs are bad at space, and what fixes it

Standard VLMs are trained on captions, which rarely say "0.4 m left of". Benchmarks like VSI-Bench and SpatialRGPT show strong models failing at relative distance, counting, and left/right under rotation. The fixes are data and inputs: add depth as an extra channel or extra tokens (from a monocular depth estimator), add camera pose, train on synthetic spatial QA generated from 3-D scenes, and — the embodied route — train on robot trajectories where wrong spatial answers produce visibly failed actions. Vision-Language-Action models consume exactly these spatially-grounded representations; the handoff is in the next chapter.

7. The training recipe (and what it costs)

Nearly every encoder+projector model is trained in the same three stages, each cheaper than you would guess:

  1. Alignment (projector only). Freeze the LLM and the encoder; train the projector on ~0.5–1M image–caption pairs to predict the caption. The LLM learns to read "vector-shaped pixels". Hours on 8 GPUs.
  2. Instruction tuning (projector + LLM). Unfreeze the LLM (often with LoRA — see training chapter) and train on ~1M multimodal instructions: VQA, OCR, charts, grounding with box coordinates as text, multi-image and interleaved documents. Optionally unfreeze the encoder at low LR late in training. This stage decides the model's resolution policy (tile counts, max tokens) — the resolution curriculum typically starts low and increases.
  3. Preference / RL. DPO on hallucination-contrast pairs (answers that mention objects absent from the image are "rejected"), and increasingly RL with verifiable rewards on counting, OCR, and spatial tasks.

Early-fusion models skip all this and instead pay for full pretraining; their recipe problem is balancing modalities (loss weighting, separate learning rates per modality, z-loss for stability) so that text quality does not regress. In Axolotl terms, the open-weight families on its list (Llama-Vision, Qwen2-VL, Pixtral, LLaVA, SmolVLM2, InternVL, Voxtral) are fine-tuned through the same YAML with a processor that handles image/audio inputs and a chat template that inserts the placeholder tokens; the knobs that matter are max image size/tiles, whether the vision tower is frozen, and sample packing (which must respect that image tokens are a contiguous block).

8. Evaluation and the characteristic failure modes

  • Language-prior hallucination: the LLM answers from what captions usually say rather than what is there ("a man riding a bike" when there is no bike). Measured by POPE-style object-presence probes; mitigated by contrastive decoding and preference data.
  • Counting and spatial relations: soft tokens blur instances; fine-grained geometry is lost in merging. VSI-Bench, CV-Bench.
  • Small text (OCR) and charts: resolution-bound; any-res tiling exists for this. DocVQA, ChartQA, TextVQA.
  • Long video: needle-in-a-haystack over frames; Video-MME, LongVideoBench.
  • Expert reasoning over images: MMMU (college-level, multi-discipline) is the headline VLM benchmark; MathVista for figures.
  • Audio: word error rate for ASR; AudioBench / AIR-Bench for spoken understanding; for speech generation, intelligibility (ASR round-trip WER), speaker similarity, and MOS.

9. Omni models and serving

"Omni" models (GPT-4o/Gemini-class; open: Qwen2.5-Omni, Gemma 3n) accept text, image, audio, and video and emit text and speech. Two architectural choices make real-time speech-to-speech possible: a streaming audio encoder (causal or chunked, so understanding begins before the user stops talking) and interleaved generation where the model emits text tokens and audio codec tokens in a fixed cadence (Qwen2.5-Omni's "thinker–talker" split: the thinker produces text and hidden states, a lightweight talker turns them into audio codes in parallel). The latency budget for a natural conversation is about 300 ms from end-of-speech to first audio — which is prefill of the last audio chunk plus the first decode steps, so every trick in the inference chapter (chunked prefill, speculative decoding, small-batch TPOT) is load-bearing here.

On the serving side, multimodal requests change the workload shape rather than the engine: the encoder runs as a separate stage (often on the same GPU before prefill, cacheable by image hash), visual tokens make prefill long and decode short, and prefix caching must key on image content, not just text. The KV budget is the first thing to size: a single 1344-px image with 16-px patches and no merging adds 7,056 tokens — on Llama-3-70B that is 7,056 × 160 KB ≈ 1.1 GB of cache per request before any text. vLLM's multimodal support (Step 12 of the plan) handles placeholder expansion, encoder caching, and the per-modality processors so that these requests flow through the same continuous-batching scheduler as text.
