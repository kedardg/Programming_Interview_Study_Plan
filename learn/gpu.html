GPU Architecture & the Execution Model

What a GPU actually is, how work and data move through it, and the one chart — the roofline — that predicts whether any kernel can go faster. This chapter is the hardware foundation for Steps 5–8 of the study plan; Kernels builds on it.

1. Why GPUs: latency machines vs throughput machines

A CPU is a latency machine. It spends most of its silicon making one instruction stream finish as soon as possible: big caches, branch predictors, out-of-order windows, prefetchers. A GPU is a throughput machine. It strips almost all of that out and spends the silicon on thousands of simple arithmetic lanes, then hides every stall — a memory access, a dependency — by instantly switching to another thread that is ready. The individual thread runs slower than on a CPU; the aggregate runs orders of magnitude faster, provided you give it enough independent work.

The quantitative version is Little's law: concurrency = latency × throughput. An H100's HBM delivers ~3.35 TB/s at ~500 ns of latency, so to keep the memory system saturated the chip must have roughly 3.35 TB/s × 500 ns ≈ 1.7 MB of memory requests in flight at every instant. No single thread can do that; tens of thousands of threads can. Everything in this chapter — warps, occupancy, coalescing — exists to manufacture and sustain that concurrency.

  • CPU strategy: avoid the stall (caches, prediction).
  • GPU strategy: tolerate the stall (switch to other warps). The hardware scheduler is the "cache".

2. The hardware: SMs and the memory hierarchy

A GPU is a grid of Streaming Multiprocessors (SMs) — 132 on an H100, 84 on your RTX 5080. Each SM contains:

  • CUDA cores — scalar FP32/INT32 ALUs (128 per SM), executing one operation per lane per clock.
  • Tensor cores — small matrix-multiply units (4 per SM) that compute an entire m×n×k matrix product per instruction. For FP16/FP8/FP4 math these deliver 8–16× the FLOPs of the CUDA cores, which is why every deep-learning kernel funnels work into them.
  • Registers — 256 KB per SM, private per thread, ~1 cycle. The fastest memory on the chip and the scarcest: a thread using many registers lowers how many threads fit (occupancy).
  • Shared memory / L1 — up to 228 KB per SM (H100), ~20–30 cycles. This is on-chip SRAM that you manage explicitly from a kernel: the staging area for tiling (and the "SRAM" in the FlashAttention paper).
  • L2 cache — 50 MB on H100, shared by all SMs, ~200 cycles.
  • HBM / GDDR (device memory) — 80 GB HBM3 at 3.35 TB/s on H100; 16 GB GDDR7 at ~0.96 TB/s on the 5080. ~400–600 cycles. When a paper says "memory-bound", it means bound by this level.

Animation: a load descends the memory hierarchy

A warp issues a load. Watch it miss in each level and descend to HBM while the cycle counter runs — then see the same access hit in shared memory after a kernel stages the tile there. The ~20× latency gap between shared memory and HBM is the entire reason tiled kernels exist.

Two numbers per level — capacity and bandwidth — define the game: each level downward gains ~100–1000× capacity and loses ~10× bandwidth. Fast kernels move data up the pyramid once and reuse it many times before letting it fall back down.

3. SIMT: grids, blocks, warps, and divergence

You launch a kernel as a grid of thread blocks; each block is assigned to one SM and never migrates. Inside the SM, the hardware splits the block into warps of 32 threads, and the warp — not the thread — is the real unit of execution: one instruction is fetched and issued for all 32 lanes at once. This is SIMT (single instruction, multiple threads): you write scalar code per thread, the machine runs it 32 lanes at a time.

The model has one sharp edge: warp divergence. If threads of the same warp take different branches, the warp executes both paths serially, masking off the lanes that didn't take each path. A 50/50 branch inside a warp halves throughput; a 32-way switch can cost 32×. Divergence between warps is free — only intra-warp divergence serializes.

Animation: lockstep execution and divergence

16 lanes of a warp (abbreviated from 32) run three straight-line instructions in lockstep, then hit if (lane % 2 == 0). The warp runs the if-side with odd lanes masked (dark), then the else-side with even lanes masked, then reconverges. Count issued instructions: 3 + 2×2 + 1 instead of 3 + 2 + 1 — the masked slots are pure waste.

Occupancy and latency hiding. Each SM holds many resident warps (up to 64). When a warp stalls on a 500-cycle HBM load, the scheduler issues from another ready warp on the very next clock — stalls are hidden, not avoided. Occupancy is the fraction of resident-warp slots you actually filled; it is capped by whichever per-SM resource your block exhausts first (registers per thread, shared memory per block, threads per block). High occupancy isn't a goal in itself — it's spare parallelism the scheduler can use to hide your latency. Memory-bound kernels need lots of it; register-heavy matmuls deliberately run at ~25% occupancy because each warp has so much independent work in registers.

Animation: latency hiding with resident warps

Each row is a resident warp: green = issuing compute, orange = waiting on memory. With 1 warp the SM sits idle during every load; with enough warps there is always someone ready and the issue slots (top bar) stay full. Drag the slider to find the point where the memory latency is fully hidden.

4. Memory coalescing

DRAM moves data in large transactions (32–128 bytes), not single words. When the 32 threads of a warp load 4-byte values from consecutive addresses, the hardware coalesces them into as few as one 128-byte transaction. When they load with a stride, every lane needs its own transaction: same instructions, up to 32× more memory traffic. Coalescing is the first thing to check in any memory-bound kernel, and the reason matrix layouts (row-major vs column-major, who indexes what) dominate naive-kernel performance — it alone is the 6.5× jump between kernels 1 and 2 of the matmul ladder in Kernels.

Animation: coalesced vs strided access

16 lanes issue one load each; the bottom strip is memory in 128-byte segments. Consecutive addresses light up one segment → one transaction. Strided addresses touch many segments → many transactions for the same useful 64 bytes. The wasted fraction of each transaction is drawn hollow.

Shared-memory bank conflicts are the on-chip sibling: shared memory is split into 32 banks (one 4-byte word wide, interleaved). If multiple lanes of a warp hit different addresses in the same bank, the accesses serialize. The classic fix — pad a tile to [32][33] — shifts a column access off the 32-stride so every lane lands in a different bank; you'll use it in the transpose exercise.

5. The roofline model

One chart predicts the speed limit of every kernel. Define arithmetic intensity (AI) = FLOPs performed ÷ bytes moved to/from device memory. Then:

attainable FLOP/s = min( peak FLOP/s , AI × memory bandwidth )

Plotted on log-log axes this is a slanted roof (bandwidth-limited region) meeting a flat roof (compute-limited region). The corner — the ridge point — is peak FLOPs ÷ bandwidth: ~295 FLOP/byte for an H100 (FP16 tensor cores), ~230 for the 5080. A kernel left of the ridge cannot be fixed with more math units; it needs to move fewer bytes (tiling, fusion, quantization). A kernel right of the ridge is compute-bound and needs tensor cores, not bandwidth.

Worked example — FP16 matmul. Multiplying two N×N FP16 matrices: 2N³ FLOPs, and at minimum 3 × 2N² bytes (read A and B, write C). So AI = 2N³ / 6N² = N/3. At N=4096, AI ≈ 1365 — far right of the ridge: big matmuls are compute-bound and can hit ~peak tensor-core FLOPs. Counter-example — decode-step GEMV (batch-1 LLM decode): 2 FLOPs per weight, 2 bytes per weight → AI ≈ 1. That's ~300× left of the ridge: an H100 decoding batch-1 runs at ~0.3% of its peak FLOPs, and no kernel cleverness changes that — only batching (more FLOPs per byte) or quantization (fewer bytes per FLOP) moves the point. This single plot explains most of the Inference chapter.

6. Profiling: measure, don't guess

The roofline tells you the limit; the profiler tells you where you are. The Step 8 workflow:

  • Benchmark honestly first (in PyTorch: warm up, torch.cuda.synchronize(), CUDA events — not time.time() around async launches).
  • Nsight Systems (nsys) for the timeline: gaps between kernels, H2D copies, CPU launch overhead. Many "slow kernels" are actually launch gaps.
  • Nsight Compute (ncu) per kernel. Read in order:
    1. Speed-of-light (SOL) section — % of peak for compute and memory. Low/low means latency-bound (not enough parallelism); high memory + low compute means bandwidth-bound; the pair tells you which wall you're on.
    2. Memory workload analysis — achieved bandwidth, transactions per request (coalescing!), L2 hit rate.
    3. Occupancy & launch stats — achieved vs theoretical occupancy, and what limits it (registers? shared memory?).
    4. Warp state / stall reasons — long scoreboard = waiting on memory; barrier = unbalanced work at __syncthreads().
  • Compute Sanitizer for correctness (compute-sanitizer --tool memcheck ./app) — before believing any speedup.

On your 5080, let ncu read performance counters: run with sudo or set NVreg_RestrictProfilingToAdminUsers=0 (see the RTX 5080 notes in the plan).
