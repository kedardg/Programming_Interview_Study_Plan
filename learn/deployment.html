Deploying and Load-Testing LLM Services on AWS: ECS/EKS, vLLM, quantization, TTFT

The last mile of a customization engagement: taking a fine-tuned model from a checkpoint to a service that meets its latency and cost targets under real load. This chapter walks the loop end to end with Qwen3 as the worked model — SFT, quantize, serve with vLLM, load-test time-to-first-token with Locust and GenAI-Perf, then run it on ECS or EKS and keep it healthy. It is the systems counterpart of Inference and the production tail of Customization & Evals.

1. The deployment loop and what "better" means in numbers

A model is not deployed when it answers a prompt in a notebook. It is deployed when a fleet of replicas serves the expected request mix inside agreed latency bounds at a cost the business accepts, and keeps doing so when a node dies. Everything in this chapter is one iteration of the same loop:

SFT'd checkpoint → evaluate (quality bar) → quantize → serve (vLLM) → load-test against SLOs → size the fleet ($) → ship → observe → repeat

"Improve deployment" has to be translated into five numbers before anyone touches a flag, otherwise every optimization is a matter of taste. They are the same quantities the inference chapter defines, now with targets attached:

Two things people forget: the quality bar from the eval methodology has to be re-checked after every quantization and every serving change that touches numerics (FP8 KV cache, speculative decoding with a different sampler, a new kernel), and the request mix — prompt length, output length, how many requests share a system prompt — determines every latency number more than the model does. Measure it from production logs before you benchmark anything.

2. The recipe, worked on Qwen3

Qwen3 is a good worked example because the family spans the two deployment shapes you meet most: Qwen3-8B, a dense model that fits one mid-range GPU and is the natural SFT target for a single-domain assistant, and Qwen3-30B-A3B, a mixture-of-experts model with about 3B active parameters per token — near-8B decode cost with far more knowledge, the throughput choice when memory allows. (Qwen3-32B dense is the quality ceiling of the mid tier and needs 80 GB in BF16 or 48 GB at W4A16.) Qwen3 also ships a hybrid thinking mode: the same weights can emit a <think>…</think> block before answering, toggled per request. That matters for deployment arithmetic: a thinking response can be 5–20× longer than the visible answer, so TPOT and cost per request are dominated by tokens the user never reads. Decide the thinking policy (off, on, budgeted) before you load-test, because it changes the output-length distribution you are testing.

2a. Fine-tune (SFT) with Axolotl and merge the adapter

The training chapter covers the why; here is the minimal config shape for a LoRA SFT that you will later quantize and serve. Train the adapter, then merge it into the base weights — vLLM can serve unmerged LoRAs, but a merged checkpoint quantizes cleanly and removes a per-request adapter lookup from the hot path unless you specifically want multi-adapter serving.

# axolotl config (illustrative; check the Axolotl docs for current keys) base_model: Qwen/Qwen3-8B chat_template: qwen3 datasets: - path: data/support_conversations.jsonl type: chat_template field_messages: messages sequence_len: 8192 sample_packing: true adapter: lora lora_r: 32 lora_alpha: 64 lora_dropout: 0.05 lora_target_linear: true bf16: true gradient_checkpointing: true micro_batch_size: 2 gradient_accumulation_steps: 8 num_epochs: 2 learning_rate: 1.0e-4 lr_scheduler: cosine warmup_ratio: 0.03 output_dir: ./out/qwen3-8b-support-lora # train, then merge the adapter into the base weights for deployment axolotl train config.yml axolotl merge-lora config.yml --lora-model-dir ./out/qwen3-8b-support-lora # → ./out/qwen3-8b-support-lora/merged/

Before quantizing, run the task suite on the merged BF16 checkpoint. That number is the reference every later step is compared against.

2b. Quantize: W4A16 (AWQ) for memory-bound decode, FP8 for throughput

Quantization is the single biggest deployment lever because decode is bandwidth-bound: fewer weight bytes per step means lower TPOT at small batch and more KV headroom for larger batches (the quantization chapter derives this). Two formats cover almost every case:

  • W4A16 with AWQ (weights 4-bit, activations BF16): ~4× smaller weights, decode speedup close to 2–3× at low batch, negligible quality loss on most tasks when calibrated with in-domain data. The right default for memory-constrained GPUs (24 GB L4/A10G, the 16 GB RTX 5080) and for latency-sensitive, low-concurrency services.
  • FP8 (W8A8) on Hopper/Ada/Blackwell: halves weight bytes and runs the matmuls in FP8 tensor cores, so prefill speeds up too — the throughput choice on H100/L40S/B200. Per-tensor dynamic scaling is simplest; blockwise scales track outliers better.

GPTQ is the other weight-only workhorse (Hessian-aware rounding; slightly better at 4-bit on some models, slower to calibrate); vLLM serves AWQ, GPTQ, FP8, and the compressed-tensors formats produced by llm-compressor through the same flag. A representative llm-compressor run:

# pip install llmcompressor (illustrative API; see the llm-compressor docs) from llmcompressor import oneshot from llmcompressor.modifiers.awq import AWQModifier from llmcompressor.modifiers.quantization import QuantizationModifier MODEL = "./out/qwen3-8b-support-lora/merged" # (a) W4A16 AWQ: 4-bit weights, group size 128, calibrated on ~512 in-domain samples oneshot(model=MODEL, dataset="data/calib.jsonl", num_calibration_samples=512, max_seq_length=2048, recipe=[AWQModifier(targets="Linear", scheme="W4A16", ignore=["lm_head"])], output_dir="./out/qwen3-8b-support-awq-w4a16") # (b) FP8 dynamic (W8A8): no calibration data needed oneshot(model=MODEL, recipe=[QuantizationModifier(targets="Linear", scheme="FP8_DYNAMIC", ignore=["lm_head"])], output_dir="./out/qwen3-8b-support-fp8")

What to verify after quantizing — all three, every time: (1) perplexity on held-out domain text (expect < 1–2% relative change for FP8, < 3–5% for W4A16; a jump means a calibration problem or an outlier-heavy layer that should be excluded); (2) the task suite from your eval bar within its confidence interval of the BF16 reference (the number that matters); (3) a side-by-side sample read of 50 responses for format regressions — JSON validity, tool-call syntax, language drift — which perplexity never catches. For MoE models like 30B-A3B, quantize experts and keep the router in higher precision; vLLM's MoE kernels support FP8 and AWQ expert weights.

2c. Serve with vLLM

The flags that decide latency and capacity, and what each does to the numbers in §1 (exact names are illustrative — check vllm serve --help for your version):

# single GPU, W4A16, chat product with prefix reuse and Qwen3 thinking parsed out vllm serve ./out/qwen3-8b-support-awq-w4a16 \ --served-model-name support-8b \ --quantization awq_marlin \ # or: fp8 | compressed-tensors (auto-detected from the checkpoint) --max-model-len 16384 \ # cap context: KV budget = max-num-seqs × max-model-len worst case --max-num-seqs 128 \ # concurrent sequences in the batch (throughput vs TPOT) --gpu-memory-utilization 0.92 \ # fraction reserved for weights + KV; leave headroom for CUDA graphs --enable-prefix-caching \ # shared system prompts / multi-turn: huge TTFT win --enable-chunked-prefill --max-num-batched-tokens 4096 \ # bound the stall long prompts cause decoders --reasoning-parser qwen3 \ # split content into a separate field --enable-lora --max-loras 8 --max-lora-rank 32 \ # only if serving multiple adapters --port 8000 # 30B-A3B MoE on 2×L40S (TP=2), FP8, with EAGLE-style speculative decoding vllm serve Qwen/Qwen3-30B-A3B-FP8 --tensor-parallel-size 2 --max-num-seqs 256 \ --speculative-config '{"method":"eagle3","model":"...","num_speculative_tokens":3}' # illustrative

The server exposes the OpenAI-compatible API, so clients, load-testers, and gateways work unchanged:

curl -s localhost:8000/v1/chat/completions -H 'Content-Type: application/json' -d '{ "model": "support-8b", "messages": [{"role":"system","content":"You are the support assistant."}, {"role":"user","content":"My order 4471 has not arrived."}], "stream": true, "max_tokens": 300, "chat_template_kwargs": {"enable_thinking": false} # Qwen3: thinking off for latency-critical paths }'

Rules of thumb for the flags: --max-num-seqs is the throughput/TPOT dial (more sequences = higher aggregate tokens/s, slower per-token until compute-bound); --max-model-len × --max-num-seqs × KV bytes/token must fit in what --gpu-memory-utilization leaves after weights, or vLLM will preempt (recompute) sequences under load — watch the preemption counter in §5; chunked prefill trades a little TTFT for stable TPOT and is on by default in recent versions; prefix caching is free performance whenever requests share a prefix.

3. Load testing: finding the knee before your users do

A single-request latency number is meaningless for a service. Latency depends on how many other requests are in flight, so the only honest measurement is a sweep over offered load with the production request mix, reporting percentiles. Two ways to generate load, and they answer different questions:

  • Open-loop (Poisson arrivals at a request rate λ): requests arrive whether or not earlier ones finished — the way users actually behave. It exposes queueing: once λ exceeds what the server drains, the queue grows without bound and TTFT explodes. This is the test that finds the knee and the capacity number you plan around.
  • Closed-loop (fixed concurrency N): each virtual user waits for its response before sending the next. Latency stays bounded because load self-regulates; it measures throughput at a concurrency level, not what happens under overload. Useful for the batch-size sweep, misleading as a capacity test.

Metrics to record per request: TTFT (first streamed token), TPOT/ITL (mean and p95 of gaps between tokens), end-to-end latency, output tokens; per run: throughput (requests/s, output tokens/s), goodput (requests/s meeting both SLOs — the number that goes in the capacity plan, from the Etalon paper in the plan), and the error/timeout rate. Report p50/p95/p99, never means. Workload realism: sample prompt and output lengths from production traces (BurstGPT and ShareGPT distributions are the public stand-ins), include the real share of prefix-sharing requests, and set the thinking policy you will ship. Discard the first 30–60 s (warmup: CUDA graphs, caches) and run each rate for at least 2–3 minutes of steady state.

Tools, with the commands that matter

vLLM's built-in benchmark is the fastest way to a rate sweep against any OpenAI-compatible endpoint:

Locust is what you reach for when the test has to look like your product: custom auth, multi-turn sessions, a mix of endpoints, a web UI for the team, distributed workers. Streaming TTFT is not built in, so measure it yourself from the first SSE chunk. A complete, runnable user class:

# locustfile.py — run: locust -f locustfile.py --host http://localhost:8000 import json, time, random from locust import HttpUser, task, between, events PROMPTS = [l.strip() for l in open("prompts.txt") if l.strip()] # sampled from production SYSTEM = "You are the support assistant for Example Co." class ChatUser(HttpUser): wait_time = between(0.5, 2.0) # closed-loop think time; use --spawn-rate/--users for concurrency @task def chat(self): body = {"model": "support-8b", "stream": True, "max_tokens": 256, "messages": [{"role": "system", "content": SYSTEM}, {"role": "user", "content": random.choice(PROMPTS)}], "chat_template_kwargs": {"enable_thinking": False}} t0 = time.perf_counter(); ttft = None; n_tok = 0; last = t0; gaps = [] with self.client.post("/v1/chat/completions", json=body, stream=True, catch_response=True, name="chat (stream)") as r: if r.status_code != 200: r.failure(f"HTTP {r.status_code}"); return for line in r.iter_lines(): if not line or not line.startswith(b"data:"): continue payload = line[5:].strip() if payload == b"[DONE]": break delta = json.loads(payload)["choices"][0].get("delta", {}) if delta.get("content"): now = time.perf_counter() if ttft is None: ttft = now - t0 else: gaps.append(now - last) last = now; n_tok += 1 total = time.perf_counter() - t0 if ttft is None: r.failure("no tokens"); return r.success() # custom metrics show up as their own rows in the Locust UI / CSV events.request.fire(request_type="LLM", name="ttft_ms", response_time=ttft * 1000, response_length=0, exception=None, context={}) if gaps: events.request.fire(request_type="LLM", name="tpot_ms", response_time=1000 * sum(gaps) / len(gaps), response_length=0, exception=None, context={}) events.request.fire(request_type="LLM", name="tpot_p95_ms_sample", response_time=1000 * sorted(gaps)[int(0.95 * (len(gaps) - 1))], response_length=0, exception=None, context={}) events.request.fire(request_type="LLM", name="e2e_ms", response_time=total * 1000, response_length=n_tok, exception=None, context={}) # Open-loop in Locust: use a constant-throughput pacer instead of think time, e.g. # from locust import constant_throughput; wait_time = constant_throughput(0.5) # 0.5 req/s per user # and scale users to reach the target rate; or drive rates with the --headless -u/-r flags from a sweep script.

4. ECS and EKS basics for ML engineers

Both services run containers on AWS; the choice is about how much of Kubernetes you want. Start with what is common: the model server is a container image (the official vllm/vllm-openai image or your own built on it), the host needs an NVIDIA driver compatible with the CUDA version the image was built against (use the AWS GPU-optimized AMIs or EKS's GPU AMI; mismatches are the number-one "it worked locally" failure), and model weights are either baked into the image (fast cold start, huge image), pulled from Hugging Face at start (slow, needs a token and egress), or — best for production — staged on S3 and copied to local NVMe at startup or mounted via a shared volume.

ECS in one page

  • Cluster: a logical group of capacity. Capacity providers decide where tasks run: Fargate (serverless, no GPUs — fine for the gateway, not for the model) or EC2 instances you own (GPU instance families: g6/g6e for L4/L40S, g5 for A10G, p4d/p5 for A100/H100, trn2 for Trainium with the Neuron runtime).
  • Task definition: the pod equivalent — image, CPU/memory, resourceRequirements: [{type: "GPU", value: "1"}], environment, log driver, health check. A task is one running copy.
  • Service: keeps N tasks running behind an Application Load Balancer target group, does rolling deployments, and scales on CloudWatch metrics (Application Auto Scaling). Service Connect/Cloud Map give service discovery.
// ECS task definition fragment (illustrative) { "family": "vllm-support-8b", "requiresCompatibilities": ["EC2"], "networkMode": "awsvpc", "containerDefinitions": [{ "name": "vllm", "image": "vllm/vllm-openai:latest", "command": ["--model","/models/support-8b-awq","--served-model-name","support-8b", "--max-model-len","16384","--max-num-seqs","128","--enable-prefix-caching","--port","8000"], "resourceRequirements": [{"type":"GPU","value":"1"}], "memory": 32768, "portMappings": [{"containerPort": 8000}], "mountPoints": [{"sourceVolume":"models","containerPath":"/models"}], "healthCheck": {"command":["CMD-SHELL","curl -f http://localhost:8000/health || exit 1"],"interval":30,"startPeriod":300}, "logConfiguration": {"logDriver":"awslogs","options":{"awslogs-group":"/ecs/vllm","awslogs-region":"us-east-1","awslogs-stream-prefix":"vllm"}} }], "volumes": [{"name":"models","host":{"sourcePath":"/opt/models"}}] }

Choose ECS when the team is small, the service is a handful of replicas, and nobody wants to operate Kubernetes. It is simpler, cheaper to run, and the ALB + auto-scaling story is enough for most single-model products.

EKS in one page

  • Control plane: managed Kubernetes API, etcd, scheduler — AWS runs it. You own the data plane: node groups (managed groups of EC2 instances) or Karpenter, which provisions right-sized nodes on demand from pod requirements, including GPU instance types, and removes them when idle.
  • GPU nodes need the NVIDIA driver (GPU AMI) and the NVIDIA device plugin DaemonSet so pods can request nvidia.com/gpu: 1; the GPU Operator bundles driver, plugin, DCGM metrics, and MIG config.
  • Workload objects: a Pod runs containers; a Deployment keeps N replica pods and does rolling updates; a Service gives them one stable address; an Ingress (AWS Load Balancer Controller → ALB) exposes it; HPA scales replicas on metrics; KEDA scales on external/custom metrics such as queue depth or vLLM's own gauges; readiness/liveness probes gate traffic; a PVC (EFS/EBS/FSx for Lustre) or an init container syncing from S3 provides weights; Secrets hold the HF token.

Replicas versus tensor parallelism: replicas raise goodput and TTFT capacity linearly and are what autoscaling adds; TP lowers per-token latency for a model that fits one GPU only at the cost of inter-GPU bandwidth — use TP to meet a TPOT target or fit a model, replicas for everything else. Keep TP inside one node (NVLink); never let Kubernetes spread a TP group across nodes. Choose EKS when you run several models, need GPU sharing/MIG, want Karpenter's bin-packing, or the platform already lives on Kubernetes.

Animation: the service topology under load, a failed pod, and a scale-out

Requests enter through the ALB, the Service spreads them across ready pods on GPU nodes, each pod batches them. Fail a pod: its readiness probe goes red, the Service stops routing to it, the Deployment replaces it, and the survivors absorb the load (watch their queues). Scale out: KEDA raises the replica count on queue depth, the pending pod has no GPU to land on, Karpenter provisions a new node (the slow part — minutes, plus weight download), and traffic rebalances once readiness passes. The lesson for capacity planning: autoscaling handles slow tides, not spikes; keep enough warm headroom for the spike your traces show.

Alternatives, one paragraph each

Amazon SageMaker endpoints host the same container with managed autoscaling, A/B variants, and CloudWatch integration — the least operational burden when you do not already run a cluster; the trade is less control over scheduler flags and a per-instance premium. Bedrock Custom Model Import takes your fine-tuned open weights (Llama/Mistral/Qwen families, subject to support) and serves them fully managed, billed per use — the right answer for bursty or low-volume traffic where a warm GPU would sit idle. Ray Serve, KServe, llm-d on EKS add multi-model routing, prefix-aware scheduling across replicas, and disaggregated prefill/decode (llm-d is purpose-built for the disaggregation pattern). NVIDIA Dynamo is the datacenter-scale disaggregated serving stack with its own KV transfer layer. Trainium nodes run vLLM through the Neuron plugin: static shapes and bucketed lengths, compiled artifacts baked into the image, and the parity gates from the hardware chapter's migration playbook before any traffic shifts.

5. Observability, canaries, and cost

vLLM exposes Prometheus metrics at /metrics; the ones a dashboard needs, by question:

QuestionMetrics (names illustrative for recent vLLM)
Are we meeting latency?vllm:time_to_first_token_seconds, vllm:time_per_output_token_seconds, vllm:e2e_request_latency_seconds (histograms → p95 in PromQL with histogram_quantile)
Are we saturated?vllm:num_requests_running, vllm:num_requests_waiting, vllm:kv_cache_usage_perc (or gpu_cache_usage), vllm:num_preemptions_total
How much work?vllm:prompt_tokens_total, vllm:generation_tokens_total, request counts by finish reason
Is the cache helping?prefix-cache hit rate (queries vs hits), spec-decode acceptance rate when enabled
Is the hardware healthy?DCGM: GPU utilization, memory, temperature, XID errors; node-level network and disk

A Grafana board with those four rows per model, plus request tracing (OpenTelemetry headers propagated from the gateway so a slow request can be followed into a replica), is enough to run on. Rollouts: ship a new checkpoint or quantization as a canary (one replica or a weighted ALB target group), compare its TTFT/TPOT and a sampled quality judge against the baseline for an hour of real traffic, then roll forward or back — the maxUnavailable: 0 strategy above keeps capacity through the swap. Cost: attribute GPU-hours to tokens (and to tenants or features via request labels) so $/M tokens is a live number, not a quarterly estimate; it is the metric that tells you whether the next optimization is worth doing.

6. Runbook checklist and a one-week local plan

Before traffic

  • Quality: task suite on the exact served artifact (quantized, merged) within CI of the BF16 reference; 50-sample format read.
  • Capacity: open-loop sweep with the production length mix; knee rate and goodput recorded; fleet sized at ≤ 60–70% of knee at forecast peak.
  • Config: max-model-len = real maximum; KV budget fits with zero preemptions at the knee; prefix caching on; thinking policy set.
  • Platform: GPU AMI/driver ↔ CUDA image verified; weights staged on S3 and warmed; readiness probe delay covers model load; shared memory sized for TP.
  • Ops: dashboards for the five numbers; alerts on p95 TTFT/TPOT, waiting requests, preemptions, error rate; canary path and rollback rehearsed.

One week on the RTX 5080 before touching AWS (the plan's Week-10 exercise, extended): Day 1 — serve Qwen3-8B W4A16 locally with vLLM, hit the API, read /metrics. Day 2 — write the Locust file above against your own prompts, verify TTFT measurement against vllm bench serve on the same run. Day 3 — the rate sweep; plot TTFT p95 and goodput, find the knee, write the number down. Day 4 — change one thing at a time (prefix caching off/on, max-num-seqs 32/64/128, chunked-prefill size) and re-sweep; keep a table. Day 5 — swap FP8 vs W4A16 (the 5080 has FP8 tensor cores) and re-run the eval suite and the sweep. Day 6 — containerize it (vLLM image + your weights volume), run the same test against the container. Day 7 — write the runbook. You now have the capacity number, the config, the test harness, and the image; ECS or EKS is "the same, N times, behind a load balancer".
