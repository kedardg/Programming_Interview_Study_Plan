Model Playbooks: gpt-oss-20b, Qwen3-4B and Qwen3.8-27B — every technique, end to end

Three open-weight models, chosen because each stresses a different part of the toolchain: a 16 GB-class mixture-of-experts whose expert weights ship in 4-bit MXFP4 (gpt-oss-20b), a small dense model you can fine-tune every way on one consumer GPU (Qwen3-4B), and a 27B hybrid whose layers are mostly Gated DeltaNet rather than attention (Qwen3.8-27B). For each one this chapter walks the whole loop from the customization ladder — prompting, SFT (full, LoRA, QLoRA), preference tuning, GRPO/RFT, distillation, continued pre-training — into quantization, vllm serve, load testing, and AWS deployment, with the same subsections for every model so the differences stand out. The numbers come from the gallery fact sheets (dated), the model cards, and the first-order models of the training and deployment chapters; anything version-sensitive is labeled.

3.1 gpt-oss-20b

a) Format gotchas: Harmony and reasoning effort

gpt-oss was trained on the harmony response format and will not behave without it. A conversation is a sequence of messages with roles system, developer, user, assistant and tool, and assistant messages carry a channel: analysis (the chain of thought, never meant for end users), commentary (tool calls and preambles), and final (the visible answer). The system message sets Reasoning: low | medium | high, which is the whole "reasoning effort" API — a longer analysis channel before the final channel, i.e. more tokens and more latency per request, exactly the System 2 budget trade. Two consequences for fine-tuning and serving:

  • Training data must be rendered with the harmony template (the Hugging Face chat template does this; the openai-harmony library is the reference renderer). If you fine-tune on plain "user/assistant" strings without channels, you train the model to skip the analysis channel and break the serving parser. Keep the analysis channel in the loss only if you have reasoning traces you trust; otherwise mask it and train on final (and commentary for tool calls).
  • Serving must parse harmony: vLLM's --reasoning-parser openai_gptoss splits analysis from final, and --tool-call-parser openai turns commentary tool calls into OpenAI-style tool_calls. The gotchas chapter lists the recurring failures — "unexpected tokens in message header", "expected 2 output messages, got 7" — which are almost always a template mismatch between what was trained and what the server renders.

Tokenizer/template parity rule for all three models: render one training example with the exact tokenizer and template the server will use, decode it, and diff it against what vllm serve sends the model for the same chat. Do it before every training run; it is the most common silent failure in the cross-cutting gotchas.

b) SFT: LoRA on 4-bit experts, or full fine-tune after dequantizing

The decisive fact: the MoE expert weights are MXFP4 and account for most of the 21B parameters. For LoRA/QLoRA you keep them quantized and frozen and attach adapters; for a full fine-tune the whole model must be dequantized to BF16 (≈42 GB of weights, then gradients and optimizer state on top — the calculator above puts that at an 8×H100 job with ZeRO-3). Two LoRA target choices exist, and they matter:

  • Attention-only LoRA (q/k/v/o projections in all 24 layers): small, stable, enough for format/style/tool-call fine-tunes. Adapters train on top of the 4-bit experts untouched.
  • Expert LoRA: PEFT's target_parameters path attaches low-rank updates to the fused expert tensors (mlp.experts.gate_up_proj, mlp.experts.down_proj) — needed when the behaviour you want lives in the experts (domain knowledge, new languages). It is heavier (the adapter is per-expert) and the dequantization kernel for training on MXFP4 matters: with Mxfp4Config(dequantize=True) the experts are upcast to BF16 at load (≈42 GB — no longer a 16 GB job); keeping them MXFP4 during training requires the Triton MXFP4 kernels and a Hopper/Blackwell GPU. On the 5080, attention-only LoRA with the experts left in MXFP4 is the realistic path. verify

# TRL — the same run as code (illustrative; pin transformers/peft/trl versions)
from transformers import AutoModelForCausalLM, AutoTokenizer, Mxfp4Config
from peft import LoraConfig, get_peft_model
from trl import SFTTrainer, SFTConfig
from datasets import load_dataset

tok = AutoTokenizer.from_pretrained("openai/gpt-oss-20b")
model = AutoModelForCausalLM.from_pretrained(
    "openai/gpt-oss-20b", torch_dtype="auto", device_map="auto",
    quantization_config=Mxfp4Config(dequantize=False),   # keep experts 4-bit; dequantize=True needs ~42 GB
    attn_implementation="kernels-community/vllm-flash-attn3",  # Hopper; else "eager"/sdpa
)
peft_cfg = LoraConfig(r=16, lora_alpha=32, lora_dropout=0.05,
                      target_modules=["q_proj","k_proj","v_proj","o_proj"],
                      # expert LoRA instead/also: target_parameters=["mlp.experts.gate_up_proj","mlp.experts.down_proj"]
                      task_type="CAUSAL_LM")
model = get_peft_model(model, peft_cfg); model.print_trainable_parameters()

ds = load_dataset("json", data_files="sft.jsonl")["train"]   # messages with harmony roles/channels
cfg = SFTConfig(output_dir="out/gptoss-lora", per_device_train_batch_size=1, gradient_accumulation_steps=16,
                learning_rate=1e-4, lr_scheduler_type="cosine", warmup_ratio=0.03, num_train_epochs=2,
                max_length=4096, packing=True, bf16=True, gradient_checkpointing=True, logging_steps=10,
                assistant_only_loss=True)                    # mask everything but assistant turns
SFTTrainer(model=model, args=cfg, train_dataset=ds, processing_class=tok).train()

Budget: ~2k–20k examples; 1–2 epochs; LR 1e-4 for LoRA (3e-5 for full); on one 80 GB GPU attention-LoRA at 4k tokens runs a few thousand examples per hour; on the 5080, micro-batch 1 with checkpointing and sequence 2–4k. Packing is fine (block-diagonal masks, see sample packing); keep the harmony special tokens intact when packing.

c) Preference tuning: DPO / ORPO

    type: chat_template.default

DPO needs a frozen reference; with a LoRA policy the reference is the base with adapters disabled, so no second copy of the 12.8 GB weights — which is why DPO fits where full SFT does not. ORPO folds the preference term into SFT (no reference) and is the cheaper first try. Keep the analysis channel out of the preference loss unless the preferences are about the reasoning.

d) RL: GRPO / RFT

The multi-turn RFT recipe applies unchanged — rejection-sampled SFT warm start, then GRPO with verifiers — with two gpt-oss-specific constraints. First, the rollout engine must serve gpt-oss correctly: vLLM does (MXFP4 kernels on Hopper/Blackwell, harmony parsing), so verl/TRL rollouts through vLLM work in principle, but the gotchas chapter records that verl's Megatron-Bridge backend did not train gpt-oss at the time of writing (issues 3794, 5224) — use the FSDP backend with a LoRA policy. Second, weight sync: the trainer holds BF16 adapters while the engine serves MXFP4 experts; syncing LoRA weights into vLLM (rather than merged weights) is the path that avoids re-quantizing experts every step. The reasoning channel is part of the sampled trajectory: mask the tool outputs, keep the model's own analysis and final tokens in the loss, and set Reasoning: low during rollouts unless the task needs long chains (rollout length dominates step time).

# TRL GRPOTrainer with vLLM rollouts (illustrative shape)
from trl import GRPOTrainer, GRPOConfig
cfg = GRPOConfig(output_dir="out/gptoss-grpo", use_vllm=True, vllm_mode="colocate",
                 num_generations=8, max_completion_length=1024, per_device_train_batch_size=8,
                 learning_rate=1e-6, beta=0.0, bf16=True, gradient_checkpointing=True)
trainer = GRPOTrainer(model=model_with_lora, reward_funcs=[code_reward, format_reward],
                      args=cfg, train_dataset=prompts, processing_class=tok)
trainer.train()

e) Distillation

gpt-oss-120b → gpt-oss-20b is the natural pair: same harmony format, same recipe, 5.1B vs 3.6B active. Sequence-level distillation (SFT the 20B on 120B outputs at Reasoning: high, keeping the analysis channel) transfers reasoning style cheaply; on-policy distillation (student samples, teacher scores per token) needs both models' logprobs — the 120B teacher is itself a one-80 GB-GPU model in MXFP4, so a 2-GPU job. Decide with the eval bar, not by default.

f) Continued pre-training

CPT means full fine-tuning on raw domain text, which for gpt-oss means dequantized experts and the full memory bill; after CPT you re-quantize experts to MXFP4 for serving and must re-check parity (MXFP4 is a lossy format; the model was trained for it, your CPT weights were not). For most domain-knowledge goals, expert-LoRA with a replay mixture is the pragmatic alternative (see the CPT section).

g) Merge / export

Attention-only LoRA merges cleanly into the BF16 attention weights, leaving MXFP4 experts untouched — export is a normal merge_and_unload() plus the original expert tensors. Expert LoRA has no clean merge: dequantize experts → add the low-rank update → re-quantize to MXFP4 → verify parity, or serve the adapter unmerged (vLLM multi-LoRA on MoE experts is version-dependent — verify). When in doubt, serve unmerged.

h) Quantization for serving

Do not re-quantize the experts: they are already MXFP4 and AWQ/GPTQ calibration on top would be lossy for nothing. What you can still do is FP8 for the attention and dense parts on Hopper/Blackwell (small gain, since the experts dominate bytes) and KV-cache FP8 (--kv-cache-dtype fp8) to double the sequence budget — worth it at 128K contexts. On Ampere and older, vLLM dequantizes MXFP4 to BF16 at load (≈42 GB weights; not a 24 GB-GPU model there) — this is the single most common "it ran on H100 but not on A10G" surprise.

i) Serving

vllm serve openai/gpt-oss-20b \ --max-model-len 32768 --max-num-seqs 64 --gpu-memory-utilization 0.90 \ --reasoning-parser openai_gptoss --tool-call-parser openai --enable-auto-tool-choice \ --enable-prefix-caching --kv-cache-dtype fp8 # fp8 KV optional; omit on consumer Blackwell if unsupported # SGLang equivalent python -m sglang.launch_server --model-path openai/gpt-oss-20b --reasoning-parser gpt-oss --tool-call-parser gpt-oss # set effort per request through the system prompt (or the API's reasoning_effort field where exposed) curl localhost:8000/v1/chat/completions -H 'Content-Type: application/json' -d '{"model":"openai/gpt-oss-20b", "messages":[{"role":"system","content":"Reasoning: low"},{"role":"user","content":"Summarise the ticket."}],"max_tokens":300}'

Concurrency math at 48 KiB per token: on the 5080, 16 GB × 0.9 − 12.8 GB weights ≈ 1.6 GB for KV ≈ 34k cached tokens — e.g. 8 sequences at 4k, or 1 at 32k; FP8 KV doubles it. On an 80 GB GPU ≈ 59 GB of KV ≈ 1.26M tokens: hundreds of concurrent 4k sequences, where the MoE's 3.6B active parameters make decode cheap per token but the all-expert weight read (≈10 GB) is paid once per step regardless of batch — batch aggressively. Multi-LoRA serving (--enable-lora --max-loras 4) works for attention adapters; expert adapters are the verify case.

j) Load-test targets

First-order floors from the deployment model: decode reads ≈ 10 GB of expert weights + ≈ 2.3 GB BF16 dense weights per step, so TPOT floor ≈ 12.3 GB ÷ bandwidth: ≈ 13 ms on the 5080 (960 GB/s), ≈ 4 ms on H100 (3.35 TB/s); real TPOT at batch 1 is 1.5–2× the floor. TTFT for a 2k-token prompt: tens of ms on H100, 100–300 ms on the 5080. Measure first: TTFT p95 under an open-loop sweep (vllm bench serve --request-rate), then TPOT vs batch, then the effect of Reasoning: high — it multiplies output tokens by 3–10×, which is a product decision, not a serving one.

k) AWS deployment

Instance: g6e (L40S 48 GB) is the sweet spot for one replica with room for KV; g6 (L4 24 GB) works for low concurrency; p5 (H100) when you want 100+ concurrent sequences per replica or FP8 KV at 128K. EKS pod: one GPU per pod, readinessProbe on /health, 60–120 s startup (MXFP4 load + CUDA graphs), KEDA on vllm:num_requests_waiting. Trainium: gpt-oss is an MoE with MXFP4 experts and attention sinks; NeuronX Distributed Inference's MoE support covers Mixtral/DeepSeek-style experts, but MXFP4 expert weights would need dequantization to a Neuron dtype (BF16/FP8) and sinks need a custom attention kernel — treat it as a migration-playbook candidate with a parity gate, not a drop-in. verify

l) Known issues (from the Gotchas chapter)

  • vLLM: harmony header errors and "expected 2 output messages, got 7" (template/parser mismatch); FA3 not detected on consumer Blackwell (RTX 5090) — sinks need FA3, so the 5080 may take the slower attention backend; MXFP4 kernels dequantize on pre-Hopper GPUs.
  • verl: gpt-oss not training on the Megatron-Bridge backend; use FSDP + LoRA.
  • Cross-cutting: chat-template parity between training and serving is where gpt-oss fine-tunes most often silently fail.

3.2 Qwen3-4B

a) Format gotchas: hybrid thinking

Qwen3 is one model with two modes. With enable_thinking=True (the default) it emits <think>…</think> before the answer; with enable_thinking=False the template inserts an empty think block and the model answers directly; /think and /no_think in a user turn switch per message. Three rules from the Qwen docs and the gotchas: sample thinking mode at temperature 0.6 / top-p 0.95 / top-k 20 (greedy loops); in multi-turn data strip historical <think> blocks from previous assistant turns (the template does this); and for fine-tuning decide explicitly whether your targets contain thinking — a dataset without it, trained with thinking enabled in the template, teaches the model to emit empty think blocks (fine for a non-reasoning assistant, wrong for a reasoning one). The 2507 refresh split the line into Qwen3-4B-Instruct-2507 (non-thinking, 262k context) and Qwen3-4B-Thinking-2507; pick the base that matches the data you have.

b) SFT: everything fits on one GPU

4B parameters is the size where the whole ladder runs on a 16–24 GB card: full fine-tune needs ≈ 16 bytes/param ≈ 64 GB (so an 80 GB GPU or 2–4 GPUs with ZeRO/FSDP), LoRA on the 8 GB BF16 base fits 16 GB at 4k tokens with checkpointing, QLoRA (NF4 base ≈ 2.5 GB) leaves most of a 16 GB card for activations and long sequences. Targets: all linear projections (q,k,v,o,gate,up,down) — on a dense model there is no reason to restrict LoRA to attention.

Hyperparameters that hold for Qwen3 dense: LoRA r 16–64, α = 2r, LR 1e-4–2e-4 (QLoRA) / 1e-5–3e-5 (full), 2–3 epochs on 5k–50k examples, sequence 4k–8k with packing. Time: QLoRA on the 5080 ≈ 1–2k examples/hour at 4k tokens; full FT on one H100 ≈ 10k examples/hour.

c) Preference tuning

DPO with a LoRA policy (reference = adapters off) fits the 5080 in QLoRA form; β 0.05–0.1, LR 5e-6 (full) / 5e-5 (LoRA), one epoch over 5–20k pairs. ORPO when you have no SFT stage to spare. For a thinking model, decide whether preferences are judged on the final answer only — then mask the think block from the loss so you are not accidentally preference-tuning the reasoning length.

d) RL: GRPO / RFT — the model to learn RL on

Qwen3-4B is small enough to run the whole trainer–rollout machine on one 24–48 GB GPU in colocated mode (vLLM holding ≈ 8 GB BF16 weights plus KV, the trainer holding a LoRA policy and its optimizer), and big enough that GRPO on verifiable math/code rewards visibly moves pass@1. Rollout engines support it everywhere (vLLM, SGLang; verl, TRL, slime/Miles). Recipe: filter prompts by solve rate, k = 8, 512–1k completion tokens for math, thinking enabled in rollouts (that is what you are training), KL β 0 or tiny, LR 1e-6 — then the multi-turn RFT recipe for agent tasks. The gotchas record a slime example hanging on weight update for exactly this model — read it before your first run.

e) Distillation

Qwen3-4B is the classic student: Qwen's own release used strong-to-weak distillation from Qwen3-32B / 235B into the small models. Reproduce at your scale with sequence-level distillation (SFT on teacher outputs with thinking) and, if logprobs are available, on-policy distillation — the distillation section has the losses. For a cost target this usually beats RL on the 4B directly.

f) Continued pre-training

A 4B full CPT run is a 64 GB-memory job per data-parallel rank (so FSDP across 2–4 GPUs or one 80 GB card), with 10–20% replay of general data and a low LR (1e-5). The 6ND arithmetic: 4B × 2B domain tokens ≈ 4.8e19 FLOPs ≈ 17 H100-hours at 40% MFU — cheap enough to try before deciding on a bigger model.

g) Merge / export

axolotl merge-lora (or PEFT merge_and_unload) → safetensors; QLoRA adapters merge into the BF16 base (re-load the base in BF16 first, never merge into the NF4 weights); export GGUF via axolotl export for llama.cpp on CPU/edge; keep the adapter unmerged when you plan multi-LoRA serving.

h) Quantization for serving

Checks after quantizing (eval section): held-out task score within noise, perplexity delta < 2–3%, and a thinking-mode sanity run — 4-bit models sometimes loop in long think blocks. W4A16 takes the 8 GB base to ≈ 2.5 GB and roughly halves TPOT on bandwidth-bound decode; FP8 halves weights with near-zero accuracy cost on Hopper.

i) Serving

(or compressed-tensors, auto-detected) # multi-adapter: --enable-lora --lora-modules support=out/qwen3-4b-lora-support legal=out/qwen3-4b-lora-legal --max-loras 4 # disable thinking per request: "chat_template_kwargs": {"enable_thinking": false} # SGLang: python -m sglang.launch_server --model-path Qwen/Qwen3-4B --reasoning-parser qwen3 --tool-call-parser qwen25

Concurrency math at 144 KiB per token — the highest of the three, because 36 layers × 8 KV heads × 128 dims is a lot of cache for a 4B model: on the 5080 with BF16 weights ≈ 6.4 GB for KV ≈ 45k tokens (≈ 11 sequences at 4k); with W4A16 weights ≈ 12 GB for KV ≈ 85k tokens; FP8 KV doubles either. On 80 GB ≈ 500k tokens. This is why a small dense model can be more cache-bound than gpt-oss-20b, and why GQA/MLA matter even at 4B (KV-cache section).

j) Load-test targets

Floors: BF16 8 GB ÷ 960 GB/s ≈ 8.3 ms TPOT on the 5080, W4A16 ≈ 2.6 ms, H100 BF16 ≈ 2.4 ms; TTFT for 2k prompt ≈ 30–80 ms on H100, 150–400 ms on the 5080. Thinking mode is the variable to control: at 1–3k thinking tokens per answer, p95 end-to-end latency is dominated by reasoning length, so load-test both modes and report them separately.

k) AWS deployment

g6 (L4 24 GB) is enough for a replica; g6e for long contexts; scale with replicas, not TP (a 4B model does not need it). EKS: 1 GPU/pod, 20–40 s startup, HPA/KEDA on waiting requests. Trainium: Qwen3 dense is a standard GQA transformer — NxD Inference's Llama/Qwen2-style path applies; the migration playbook parity harness is the gate, and the gotchas list a Qwen2.5-14B Neuron issue to read first.

l) Known issues

3.3 Qwen3.8-27B

a) Format gotchas: a hybrid with thinking, vision and an MTP head

The gallery fact sheet: 64 layers in a 3:1 pattern — 48 Gated DeltaNet layers and 16 gated-attention layers — partial RoPE, one MTP layer, 262,144-token context, 248k vocabulary, native vision-language, Apache-2.0, released 2026-08-14. The chat side is Qwen's thinking template (same enable_thinking mechanics as Qwen3-4B, same sampling rules) plus image inputs; the gotchas record a thinking-plus-tool-parser loop on the sibling Qwen3.8-Flash-Next and tool-call leakage with hybrid models when prefix caching and MTP are combined — so the parity diff of training template vs served template, and a tool-call round-trip test, are mandatory before load testing.

b) SFT: what changes when 48 of 64 layers are DeltaNet

Three things differ from a dense transformer. Memory: 27B BF16 ≈ 54 GB, so LoRA needs an 80 GB GPU (54 GB weights + activations), QLoRA (≈ 14 GB NF4) fits 24 GB comfortably and the 5080 only at short sequences; full fine-tune ≈ 430 GB → an 8×H100 FSDP job. Targets: the DeltaNet layers have their own projections (q/k/v/gate/output and the short-conv) and the 16 attention layers have gated attention; lora_target_linear: true catches all of them, but explicitly listing q_proj,k_proj,v_proj,o_proj,gate_proj,up_proj,down_proj would miss DeltaNet-specific module names — check model.named_modules() for the hybrid block's names before trusting a target list. Kernels: training the DeltaNet layers needs the chunked linear-attention kernels (the fla / flash-linear-attention path that Qwen3-Next introduced); without them training falls back to slow reference code or fails to load — the Axolotl/PEFT support status for this family is what the gotchas chapter tracks. verify

Long-context fine-tunes are where this model earns its cache advantage — 64 KiB per token of state versus 144 KiB for the 4B dense model — but training activations at 32k+ tokens need sequence parallelism (training systems).

c) Preference tuning

Same DPO/ORPO configs as Qwen3-4B with the memory of a 27B: LoRA policy + adapters-off reference on one 80 GB GPU, or QLoRA on 48 GB. β 0.1, LR 5e-5 (LoRA), one epoch.

d) RL: GRPO / RFT on a hybrid

The constraint is the rollout engine. vLLM and SGLang serve the Qwen3-Next/3.5/3.8 hybrid family (DeltaNet state cache + KV for the attention layers; MTP speculative decoding), so GRPO rollouts run — but weight sync from a trainer to an engine holding hybrid state, prefix caching over DeltaNet state, and MTP during rollouts are each a recorded issue class ("hybrid models + prefix caching + MTP: tool-call leakage, wrong needle results"). Practical settings: disable prefix caching and MTP in the rollout engine for RL, LoRA policy with the FSDP backend in verl, k = 8, completion length by task; the memory bill is 54 GB (engine, BF16) + 54 GB (trainer base) + KV + optimizer — a 2×H100 colocated job or disaggregated pools (topologies). Expect rollout to dominate even more than usual: 262k-token contexts invite long trajectories.

e) Distillation

Qwen3.8-27B is a teacher for Qwen3-4B (sequence-level or on-policy, as above) and a student of larger Qwen3.x models. Distillation across architectures (hybrid → dense or the reverse) works at the sequence level trivially and at the logit level fine (shared tokenizer family — check the vocabularies: 248k vs 151k means logit-level KD needs a vocabulary mapping or a shared tokenizer).

f) Continued pre-training

Full CPT on 27B is an 8×H100 FSDP job per 6ND (27B × 10B tokens ≈ 1.6e21 FLOPs ≈ 570 H100-hours at 40% MFU); the hybrid's training throughput at long sequences is better than a dense 27B (linear-time DeltaNet layers), which is the point of the architecture.

g) Merge / export

Standard PEFT merge into BF16; for the MTP head keep its weights alongside (speculation needs them at serving time); GGUF export for hybrids depends on llama.cpp's support for the DeltaNet block — verify.

h) Quantization for serving

W4A16 (AWQ/GPTQ) and FP8 apply to the linear projections of both layer types; llm-compressor's modifiers target Linear modules, so the DeltaNet projections are covered, but the short-conv and gating paths stay in BF16 and the recurrent state is never quantized (the hybrid's cache is small anyway). Calibrate with long sequences (the state statistics differ from short-prompt calibration) and run the needle-in-a-haystack check after quantizing — the gotchas chapter records wrong needle results in hybrid + caching combinations, and a quantized state path can add to that. 27B W4A16 ≈ 14–15 GB: fits the 5080 for inference.

i) Serving

vllm serve Qwen/Qwen3.8-27B \ --max-model-len 131072 --max-num-seqs 64 --gpu-memory-utilization 0.90 \ --reasoning-parser qwen3 --tool-call-parser hermes --enable-auto-tool-choice \ --speculative-config '{"method":"mtp","num_speculative_tokens":2}' # the Qwen3-Next lineage's MTP path — verify the method name for 3.8 # prefix caching over hybrid state: enable only after the tool-call/needle regression tests pass (see gotchas) # W4A16 on a 16–24 GB GPU: vllm serve out/qwen38-27b-awq --max-model-len 32768 --max-num-seqs 16 # SGLang: python -m sglang.launch_server --model-path Qwen/Qwen3.8-27B --reasoning-parser qwen3 --speculative-algorithm NEXTN

Concurrency math at 64 KiB per token: the hybrid's per-token cost is lower than the 4B dense model's (16 attention layers' KV plus fixed DeltaNet states), so on an 80 GB GPU with BF16 weights (54 GB) the remaining ≈ 18 GB holds ≈ 290k tokens — a few 128k-context sequences or ~70 at 4k; W4A16 on 24 GB leaves ≈ 7 GB ≈ 110k tokens. MTP speculation gives 1.5–2× decode speedup when acceptance is high (chat, code) and little on hard reasoning.

j) Load-test targets

Floors: BF16 54 GB ÷ 3.35 TB/s ≈ 16 ms TPOT on H100 (so TP = 2 for interactive use, ≈ 8 ms); W4A16 ≈ 14 GB ÷ 960 GB/s ≈ 15 ms on the 5080. TTFT scales with prompt length almost linearly for the DeltaNet layers (no n² term), which is this model's advantage at 100k+ prompts — load-test with a long-prompt distribution, not the default 1k.

k) AWS deployment

p5 (H100 80 GB) with TP = 1 for throughput or TP = 2 for latency; g6e (L40S 48 GB) with W4A16; for 262k contexts, p5 with FP8 KV. EKS pod sizing follows the concurrency math above; startup 2–4 min (54 GB load + CUDA graph capture for hybrids). Trainium: the NKI Library's experimental catalog contains Gated DeltaNet and linear-scan kernels (hardware chapter), so the building blocks exist, but end-to-end Qwen3.8 serving on Neuron (hybrid state cache, MTP, vision) is a port, not a flag — run the migration playbook with the needle and tool-call tests as parity gates. verify

l) Known issues

  • vLLM: hybrid models + prefix caching + MTP — tool-call leakage, wrong needle results, MTP crash; Qwen3.5 tool calls lost with XML tool_call; DeltaNet hybrids are young — state that is not a plain KV block interacts badly with prefix reuse.
  • SGLang: thinking + tool parser loops on token 0 (Qwen3.8-Flash-Next); HiCache consistency with PP.
  • Axolotl / TRL: hybrid-layer fine-tuning support is the thing to check in the issue tracker before you start.

7. Hands-on plan on an RTX 5080 (16 GB)

  1.   2.   3. Week C — Qwen3.8-27B: inference only: W4A16 at 16–32k context, the needle and tool-call regression tests, MTP on/off, long-prompt load tests to see the hybrid's TTFT advantage. QLoRA at short sequences is possible but tight; everything else — LoRA, DPO, GRPO, CPT — is a rented H100 (one for LoRA/DPO, two for GRPO, eight for full fine-tunes).
